# ステージの構造

ステージは AI-DLC ワークフローの最小単位です。1 つのステップで*何が*起きるかを表します。ハーネスエンジニアが加える他のすべての変更は、このステージファイルの上に成り立ちます。だから、まず読むべきはこの章です。読み終えるころには、どの `.md` ステージファイルを開いても、各部分を誰が読むのかが分かり、どのフィールドはファイルを編集して変えられ、どの挙動はフレームワークのコードで固定されているのかを理解できるようになります。

ステージファイルは、YAML のフロントマターを持つ 1 つの Markdown ファイルです。フロントマターはグラフのノードを宣言します。そのステージが消費・生成するアーティファクト、リードエージェント、実行方法を記します。本文はエージェントが従う散文です。両方を 1 つのファイルに置くのは意図的で、この章の残りでその理由を解きほぐします。

---

## 2 人の読み手、1 つのファイル

ステージファイルには 2 人の読み手がいて、両者は決して重なりません。

- **パーサー**は YAML フロントマターだけを読みます。構造化されたグラフのエントリ（エッジ、リードエージェント、実行モード）を作り、本文はまったく無視します。
- ステージを実行する**エージェント**は本文だけを読みます。散文のステップに従ってアーティファクトを生成し、フロントマターには一切触れません。

両方を 1 つのファイルに収めると、ファイルを開いたときにグラフのエッジと実行ステップを並べて見られます。ステージを読むレビュアーは両方を一度に見られます。どのアーティファクトを生成するのか*と*、それを生成する指示の両方です。これを分割すると、つまりグラフ用に YAML ファイルを 1 つ、エージェント用に散文ファイルを 1 つ置くと、このインラインの可視性が失われます。この性質こそ、ステージをレビュー可能にしているものです。

この分割は、自分が何を編集しているのかを知る鍵です。フロントマターのフィールドを変えると、*グラフ*を変えたことになります（依存エッジ、リードするエージェント、実行モード）。本文を変えると、*作業*を変えたことになります（エージェントが実際に行うこと）。この 2 つは独立しています。

実際のステージは `core/aidlc-common/stages/<phase>/<slug>.md` に書かれます。たとえば `stages/inception/domain-design.md` です。この章と並べて 1 つ開いてみてください。読み終えるころには、その形に見覚えがあるはずです。

## フロントマターをひと目で

フロントマターは YAML キーの平坦なブロックです。一部は機械的で（`slug`、`phase`）、隣のステージからコピーします。いくつかは本当の判断を伴い、ステージを書いたり編集したりする前に理解しておく価値があるのはそちらです。

| フィールド | 何を決めるか | 判断のポイント |
|-------|-----------------|-------------------|
| `requires_stage` | 依存と順序のエッジ | このステージは別のステージの出力を本当に消費するのか、それとも後に実行される必要があるだけか。 |
| `consumes` | このステージが読むアーティファクト | アーティファクトごとに、`required` か、ブラウンフィールド/グリーンフィールドを `conditional_on` とするか、`cited` か。 |
| `consumes[].cited` | 存在するとき、出力が引用しなければならない任意の入力 | ある任意の入力が、存在するときは必ず出力がそれに基づく、というものがあるか。あれば `cited: true` を付けます。すると `upstream-coverage` チェックがその引用を求めます。 |
| `produces` | このステージが書くアーティファクト | これらは他のステージが見つける前方エッジです。 |
| `lead_agent` / `support_agents` | ステージを実行する担当 | 1 つのペルソナが所有し、サポーターが視点を加えます。 |
| `mode` | コミュニケーションのトポロジー | `inline`（コンダクターのコンテキストの中の声）、`subagent`（ハブアンドスポークのディスパッチ）、`pipeline`（連鎖）、`mob`（区切られたラウンドでのメッシュ）。 |
| `for_each` | 反復するかどうか | インスタンスがインスタンスごとの実行を駆動するアーティファクトを指定します。 |
| `reviewer` / `review_artifact` | 独立した品質レビュー | レビュアーを宣言するなら、レビューの対象となる必須の Markdown 出力を 1 つ指定します（レビュー記録はそれに紐づき、ゲートもそれを指定します）。`produces` の順序には決して頼りません。 |

とくに判断の難しい点をいくつか補足します。

- **`consumes[].required` はグローバルではなく、有効なプランの範囲に限られます。** `required: true` は「生成側のステージが*この*ワークフローで実行されるなら、この consume は満たされなければならない」という意味であって、「生成側が常に実行される」という意味ではありません。スコープは意図的に上流のステージを飛ばすので、平坦なグローバル要件はそうしたスコープを構造的に無効にしてしまいます。ステージの本文は入力が欠けた場合を優雅に扱います（「if produced」のような散文です）。
- **`consumes[].conditional_on` はブラウンフィールド/グリーンフィールドの分岐を表します。** `conditional_on: brownfield` と記された consume は、ワークフローがブラウンフィールドのときだけ必須です。無条件の consume では、このフィールドをまったく省きます。`always` という値はありません。
- **`mode` はコミュニケーションのトポロジーです。** 本文が実行されるあいだ誰が誰と話すかを表します。`inline` は短いステージをコンダクター自身のコンテキストで実行し、サポーターは取り込まれた声になります。`subagent` はリードを新しいコンテキストに委譲し（Construction のコード生成のような長いステージ）、サポーターが宣言されていれば、それぞれを互いに見えないスポークとしてディスパッチします。`pipeline` はサポーターを宣言された順に連鎖させ、各自が上流のすべての作業を見ます。`mob` はすべてのサポーターをリードの下書きに対して並行で実行し、区切られた反論ラウンドを 1 回行います。*誰が*参加するかは `support_agents`、*どう*参加するかは `mode` です。`pipeline` と `mob` は空でない `support_agents` を必要とします。
- **`for_each` は反復のアーティファクトを指定します。** Unit ごとに 1 回実行される 5 つの Construction ステージは `for_each: unit-of-work` を宣言します。他のステージはこのフィールドを省き、1 回だけ実行します。集約はグラフから推論され、宣言されません。
- **`lead_agent` と `support_agents` は `core/agents/*.md` に対して検証されます。** ハードコードされた一覧はありません。エージェントの追加は、そのファイルをそのディレクトリに置くことを意味します（[エージェントの追加](03-adding-an-agent.md)を参照）。

これはオリエンテーションであって、契約ではありません。型・制約・AI-DLC が後で追加する予約名前空間のフィールドを含む完全なフィールド表は、開発者リファレンスの[フィールドリファレンス — いつ使うか](../reference/15-stage-definition.md#field-reference-when-to-use)を読んでください。

## 3 区画の本文

フロントマターの下、本文は 3 つの区画を持ち、常にこの順です。`## Steps`、`## Sensors`、`## Learn`。`domain-design.md` を見ると、3 つすべてが埋まっています。

- **`## Steps`** はエージェントが従う命令形の散文です。ペルソナを読み込み、先行コンテキストを読み、質問ファイルを作り、アーティファクトを生成し、承認ゲートを提示します。ここにステージのドメイン作業が置かれ、グラフに触れずに*ステージの振る舞いを*変えるときに最もよく編集する区画です。
- **`## Sensors`** はローカルな要約を簡潔に示します。出力がどこに着地するか、フロントマターの `sensors:` 一覧を映す `Imports:` 行、そして `upstream-coverage` がインポートされているとき `consumes:` を映す `Upstream targets:` 行です。意図的に省いたセンサーや、構造化出力の所有のような、ステージ固有の例外はここに保ちます。共通の振る舞いは `stage-protocol-sensors.md` に置かれます。Sensors は[Sensors](06-sensors.md)で詳しく扱います。
- **`## Learn`** は `stage-protocol-learnings.md` の 13 節にある条件付きの学習ループ契約を指します。`directive.protocol_modules` に `learnings` が並ぶときだけ、作業中は `directive.memory_path` にある 4 見出しの日記を保ち、人間のゲートの前に学習ステップを踏みます。このステップは、エージェントがステージ内で修正を受けた後にだけ、人に何かを尋ねて、保持されたものを残します。いつ尋ねるか、そしてブートストラップ・単独実行・Unit ごとの免除は、モジュールが所有します。モジュールが無いときは、日記を保たず、ステップを飛ばします。ワークフロー時の学習がステージ本文を書き換えることは決してありません。

3 つの区画が固定されているので、ステージのセンサー束縛と学習ループのポインターは常に自分の居場所を持ち、1 つ加えても本文の構造を組み替えずに済みます。完全な本文モデルと各区画に何が入りうるかは、[3 区画の本文モデル](../reference/15-stage-definition.md#three-compartment-body-model)にあります。

心に刻む価値のある境界が 1 つあります。ステージファイルはフレームワークのアーティファクトで、その形は不変です。本文の `## Steps` / `## Sensors` / `## Learn` という構造は、ワークフローによって書き換えられることはありません。ワークフロー内で認められた唯一の編集は、学習ループがフロントマターの `sensors:` インポート一覧に新しいセンサー id を追記することです。ステージファイルで変えるそれ以外のすべては、ハーネスエンジニアとして意図的に変えるものです。

## グラフから見た consumes と produces

依存グラフはどこにも直接書かれていません。すべてのステージにまたがる `consumes` と `produces` の宣言から立ち現れます。ステージの `produces` 一覧はその前方エッジです。別のステージが「`scope-document` を生成するのは誰か」と尋ねると、答えはそれを宣言したステージです。ステージの `consumes` 一覧はその後方エッジです。`required` なアーティファクトは、その生成側がこのプランにあるなら、このステージの実行時に存在しなければなりません。任意のものは、存在するときに読まれます（上記のプラン範囲の規則です）。

`requires_stage` は依存を明示し、純粋な順序も符号化します。2 つの役割を担います。

1. **意味的なデータ依存** — 「私はアーティファクト X を消費し、それはステージ Y が生成する」ので、Y を `requires_stage` に入れます。
2. **表示順のエッジ** — 同じフェーズにあってデータ依存はないが順序が固定の 2 つのステージ。アルファベット順のタイブレークに頼るのではなく、弱いエッジを書いて、計算された表示順が安定して着地するようにします。

ステージを書いたり移したりするとき、この 3 つの一覧がそれをワークフローに配線します。正しく書けば、ステージは正しいスコープに、正しい順序で、入力が満たされた形で現れます。真新しいステージを配線する仕組みは、[ステージの追加](02-adding-a-stage.md)で一歩ずつ扱います。

## stage-graph.json はコンパイルで作られる — 手で編集しない

ソースビルドでは、生成された Claude の投影が
`dist/claude/.claude/tools/data/stage-graph.json`
からグラフを実行します。`dist/` は `bun scripts/package.ts` が実体化する、無視されるローカル出力です。インストールされたランタイムは同じ相対ファイルを `.claude/tools/data/` の下に持ちます。この JSON は**ビルドアーティファクト**であって、ソースファイルではありません。ステージファイル群の YAML フロントマターが正本で、JSON はそれをコンパイルして得られるものです。

流れはこうです。

```
edit stage .md YAML  →  compile  →  stage-graph.json  →  runtime reads it
```

`core/` でステージのフロントマターを編集したら、`bun scripts/package.ts` を実行します。これはグラフをすべての生成ツリーにコンパイルします。そしてコミットするのは `core/` の編集だけにします。生成ツリーは無視され、CI がソースからまた作るからです（`bun scripts/package.ts --check` は 2 回ビルドしてバイト比較します）。インストール済みのプロジェクトツリーでは、`aidlc engine graph compile` がそのツリーの `stage-graph.json` を再生成し、`aidlc engine graph compile --check` が古くなっているときを教えます。

```text
$ aidlc engine graph compile --check
stage-graph.json is out of date. Run `aidlc engine graph compile` to regenerate.
```

ここから従う規則は、**`stage-graph.json` を手で編集しない**ことです。YAML を編集し、再コンパイルします。手編集は次のコンパイルで上書きされるか、ドリフトチェックに引っかかります。コンパイルコマンドとドリフトガードは[オーサリングフロー](../reference/15-stage-definition.md#authoring-flow)に記されています。

## ステージが*含む*もの、*行う*もの

この章はステージファイルが*含む*もの、つまりその形式についてです。ステージが実行時に*行う*ことについては、別の契約があります。承認ゲート、質問フロー、状態のチェックボックス、完了メッセージです。その振る舞いの契約はドメインを問わずどのステージでも同じで、[Stage Protocol](../reference/04-stage-protocol.md)に置かれています。ステージ本文が「承認ゲートは stage-protocol.md に従う」と言うとき、指しているのはその契約です。

頭の中では 2 つを分けておいてください。ステージの*定義*（この章と[リファレンス 15](../reference/15-stage-definition.md)）はファイル形式です。ステージの*プロトコル*（[リファレンス 04](../reference/04-stage-protocol.md)）は、どのステージの作業も包み込む実行時の振る舞いです。定義は編集します。プロトコルはほとんど触りません。

フロントマターと本文を結びつけた、注釈付きの完全な例は、[具体例](../reference/15-stage-definition.md#worked-example)を参照してください。
