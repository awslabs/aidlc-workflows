# Team Knowledge

ナレッジは、エージェントが作業前に読むドメインのコンテキストです。あなたのコーディング標準、アーキテクチャの好み、ドメイン用語集、チームが落ち着かせたパターンです。ハーネスの中で、あなたがエージェントの読むファイルを足すことで形づくる唯一の部分であり、フレームワークが強制する制約ではありません。この章では、エージェントにそのコンテキストを与えるワークフローを辿ります。ファイルをどこに置くか、どのエージェントが見るか、そしてナレッジとルールのあいだの判断です。

[Rules and the Learning Loop](05-rules-and-the-loop.md) を読んだなら、その違いを通して覚えておいてください。ルールはフレームワークが強制する恒常的な決定であり、ナレッジはエージェントが作業中に重みづけする参照資料です。どちらもエージェントの振る舞いを形づくりますが、別の面にあり、読み込まれ方も異なります。

---

## 2 つの層: フレームワークのナレッジとあなたのナレッジ

AI-DLC のナレッジは 2 つの層に分かれ、あなたが編集できるのはそのうち 1 つだけです。

**Tier 1 — 方法論ナレッジ**は、この実装に `.claude/knowledge/` 配下で同梱されます。各エージェントがステージを走らせるのに使う方法論の参照を保持します。`aidlc-architect-agent/architecture-guide.md`、`aidlc-developer-agent/code-generation-guide.md`、そして `aidlc-shared/` にあるエージェント横断の資料です。**ここは触らないでください。** これらは AI-DLC のファイルです。1 つにローカルな編集を加えると、次の `aidlc config` のリフレッシュがコンフリクトで止まり、ファイルを退避するか `--force` で同梱ファイルを取り戻すまで続きます。ここに足したファイルは保たれますが、AI-DLC 自身のファイルに紛れます。自分の資料は Tier 2 に置いてください。

**Tier 2 — チームナレッジ**はあなたのものです。スペースレベルの `aidlc/knowledge/`（`aidlc/spaces/<space>/knowledge/` の略記）にあり、そのスペースの `memory/`、`codekb/`、`intents/` と同階層です。だからスペース内のすべての intent にわたって積み上がり、1 つの intent の記録に閉じ込められません。あなたの会社固有の標準、ポリシー、慣習を保持します。フレームワークはこれを決して上書きしません。エンジンは最初の `/aidlc` で空の `aidlc/knowledge/` ディレクトリを作るだけで、中身はあなたに委ねます。ここが、あなたが埋めるディレクトリです。（恒常的な慣行をフレームワークに *強制* させたいなら、それは参照資料ではないので、代わりにスペースのメモリレイヤー `aidlc/spaces/<active-space>/memory/` に置きます。）

2 つの層の分割は、このガイドのほかの部分が立脚するデータとコードの線を、ナレッジに適用したものです。フレームワークは自身の方法論を所有し、あなたは自分のコンテキストを所有し、アップグレードは一方を他方に触れず入れ替えられます。両方の層の完全なディレクトリ構成は [Knowledge System → Two-Tier Architecture](../reference/10-knowledge-system.md#two-tier-architecture) にあります。

## チーム全体か、エージェント固有か

Tier 2 は、慣習としてエージェントのレイアウトに従います。`aidlc-shared/` ディレクトリ 1 つに加え、エージェントごとに 1 つのディレクトリを、すべてスペースレベルの `aidlc/knowledge/` の下に置きます。ファイルをどこに置くかが、どのエージェントがそれを読み込むかを決めます。

| 置き場所 | 読み込むエージェント | 用途 |
|-----------|-----------|------------|
| `aidlc/knowledge/aidlc-shared/` | **すべて**のエージェントが、毎ステージで | 横断する標準。命名規約、commit フォーマット、プロジェクトのドメイン用語集 |
| `aidlc/knowledge/<agent>-agent/` | **その**エージェントだけが、ステージで作業するとき。リードとして、インラインステージのサポートエージェントとして、または単独でディスパッチされたとき | 1 つの役割のためのドメインコンテキスト。アーキテクトのためのアーキテクチャパターン、devsecops のためのセキュリティポリシー |

ディレクトリ名は、エージェントの slug と正確に一致していなければなりません。たとえばアーキテクトなら `aidlc-architect-agent/` で、`architect/` と略してはいけません。ディレクトリ名のタイプミスは、ファイルが黙って無視されるもっとも多い理由です。フレームワークはエージェント自身のディレクトリを名前で歩き、何も見つからず、エラーなしで通り過ぎます。エンジンはこれらのサブディレクトリを作りません。`aidlc/knowledge/` はブートストラップ時は空なので（下記参照）、各ディレクトリを正確な slug で自分で作ります。

`aidlc-shared/` に手を伸ばすのは、ある標準が本当に 14 のエージェントすべてに当てはまるときだけにしてください。アーキテクトにだけ重要でほかには無関係なパターンは `aidlc-architect-agent/` に属し、そこでアーキテクチャステージにコンテキストを加え、ほかのすべてのエージェントのウィンドウを薄めません。User Guide の [Adding Company Standards worked example](../guide/08-knowledge.md) は、端から端までの全体のウォークスルー（ディレクトリを作り、書き、検証する）を運びます。最初のファイルを書く前に一度読む価値があります。

各ディレクトリが何のためのものかのエージェントごとの表は、[Knowledge System → Adding Team Knowledge](../reference/10-knowledge-system.md#adding-team-knowledge) を参照してください。

## エージェントがナレッジを読み込む仕組み

ナレッジファイルを登録したり、どこかに配線したりはしません。正しいディレクトリにそれがあることが、登録そのものです。ステージが始まると、コンダクターは決まった 6 ステップの順でコンテキストを読み込み、あなたの Tier 2 ファイルはステップ 4 と 5 で入ります。

1. ルール — 解決された `aidlc/spaces/<active-space>/memory/` チェーン（最初に読み込む）
2. Tier 1 共有方法論 — `.claude/knowledge/aidlc-shared/`
3. Tier 1 エージェント方法論 — `.claude/knowledge/<agent>-agent/`
4. **Tier 2 チーム共有** — `aidlc/knowledge/aidlc-shared/`
5. **Tier 2 チームエージェント固有** — `aidlc/knowledge/<agent>-agent/`
6. 前ステージの成果物 — 現ステージが消費すると宣言する出力

ステップ 4 と 5 は、ディレクトリが存在してファイルを含むときだけ発火します。だからチームナレッジのないプロジェクトは、単にそれらを飛ばします。インラインステージと mob ステージのリードでは、エージェントはペルソナの直後、Tier 1 方法論の前にあなたの Tier 2 ファイルを読み、ファイルの一覧が長すぎるときは、あなたのものより先に Tier 1 ファイルが落とされます。読み込みは毎ステージの開始で起きるので、ファイルを編集すると次の `/aidlc` 実行で効き、クリアするキャッシュも再起動も要りません。ファイルの削除も同じく直接的です。消すと、以降の実行はそれを見なくなります。同期を保つレジストリはありません。

心に刻む価値のある帰結が 1 つあります。エージェントはナレッジファイルを**文字どおり、等しい重みで**読みます。古い、または矛盾するファイルは、積極的にエージェントを誤らせます。現行のものと同じ権威を帯びるからです。Tier 2 ツリーを、剪定が要るコードのように扱ってください。retro での短いレビューが、それを正直に保ちます。

ステップごとの完全な契約、優先順位のルール、シーケンス図は、[Knowledge System → 6-Step Knowledge Loading Order](../reference/10-knowledge-system.md#6-step-knowledge-loading-order) にあります。

## ナレッジか、ルールか

ハーネスエンジニアのもっとも多い間違いは、意図がルールなのにナレッジへ手を伸ばす、またはその逆です。両者は交換可能ではなく、上の読み込み順がその理由を示します。ルールは、フレームワークが実行前にコンパイルする strict-additive なチェーンとして最初に解決します。ナレッジは、エージェントがステージ中に重みづけする参照資料です。

役に立つ判定法があります。**指示が破られたときに人間のレビュアーがステージの出力を却下するなら、それはルールに属します。** レビュー時に背景として使うなら、それはナレッジです。

| ナレッジに手を伸ばすとき… | ルールに手を伸ばすとき… |
|---------------------------|------------------------|
| エージェントが参照すべき参照資料を供給している | エージェントが従わねばならない振る舞いの決定を述べている |
| 「私たちが使うパターンはこれ」 | 「X は決してするな」/「Y は必ずせよ」 |
| 内容が情報的で文脈的 | 内容が規定的で譲れない |
| 長文のプロセ、表、図でよい | 短く、命令形で、1 行ずつがよい |
| 例: API Gateway 標準、ドメイン用語集 | 例:「PII をログしない」「すべてのデータアクセスは repository レイヤーを通す」 |

だから、チームが API をどう設計するかを記した文書はナレッジです。`aidlc/knowledge/aidlc-architect-agent/` に置きます。「すべてのアーキテクチャ決定は少なくとも 2 つの代替案を記録せよ」のような譲れないものはルールです。スペースのメモリレイヤー（`aidlc/spaces/<active-space>/memory/`）に属し、そこでフレームワークがエージェントにそれを守らせます。レイヤーチェーン全体でルールを書き、学習ループに修正をルールへ昇格させることについては、[Rules and the Learning Loop](05-rules-and-the-loop.md) を参照してください。User Guide の [Knowledge vs Rules table](../guide/08-knowledge.md) は、同じ判断をより多くの例で扱います。

## Tier 2 ツリーはどこから来るか

チームが作ります。最初の `/aidlc` で、エンジンは空のディレクトリ 1 つ（`aidlc/knowledge/`）を作り、そこで止まります。ツリーの足場を組んだり、エージェントごとのサブディレクトリを作ったり、README を置いたりはしません。Tier 2 のレイアウト（`aidlc-shared/` に加えてエージェントごとに 1 ディレクトリ）は、ペルソナが探す慣習であり、エンジンが書く構造ではありません。あなたは、コンテンツがあるディレクトリを作ります。ローダーは各エージェント自身のディレクトリを名前で歩くので、ローダーが期待する正確な slug で作ってください（`architect/` ではなく `aidlc-architect-agent/`）。タイプミスのある名前は、エラーなしで黙って飛ばされます。

ディレクトリの中に命名規約はありません。どの `.md` ファイルも読み込まれます。説明的で 1 ファイル 1 トピックの名前（`architecture.md` のような広い名前より `api-gateway-standards.md`）は、ローダーには要求されませんが、四半期の剪定をはるかに楽にします。ディレクトリのために始点となる README が欲しければ、Tier 1 が手でコピーして入れられる任意のテンプレートを同梱しています。[Knowledge System → Template System](../reference/10-knowledge-system.md#template-system) を参照してください。

このガイドのほかの部分との境界について一言。ここであなたが埋めるエージェントディレクトリは、エージェントがそのペルソナファイルで宣言するのと同じものです。[エージェントを追加する](03-adding-an-agent.md)とき、その Tier 2 ナレッジディレクトリは `aidlc/knowledge/<new-agent-slug>/` です。チームが作るディレクトリで、同じステップ 4 と 5 で読み込まれます。[overview](00-overview.md) のメンタルモデルが成り立ちます。ステージがエージェントを名指し、エージェントがナレッジを読み、そのすべてを、データの編集で形づくります。コードは書きません。

## Spaces: 2 チーム以上のためのナレッジ

上のすべては、1 チームを前提にしています。**2 チーム以上がプロジェクトを共有する**とき、AI-DLC は各チームのメソッド、ナレッジ、記録を、それぞれの **space** に保ちます。同じ形の `aidlc/spaces/<name>/`（`memory/`、`knowledge/`、`codekb/`、`intents/`）です。この章を通して使ってきた `aidlc/knowledge/` の略記は、本当は `aidlc/spaces/<active-space>/knowledge/` です。1 チームなら、そのアクティブスペースは常に `default` で、違いは表に出ません。（[User Guide の Spaces and Intents の章](../guide/03-spaces-and-intents.md)はエンドユーザー向けの案内で、この節はハーネスエンジニアリングの観点です。）

これは、あなたが書くナレッジとルールにとって次のことを表します。

- **チームナレッジはスペースごとです。** あなたが埋める `aidlc/knowledge/aidlc-<agent>-agent/` ファイルは、1 つのスペースの中にあります。2 つめのチームは、自分の空の `knowledge/` ツリーを得て埋めます。あなたのファイルは境界を越えて漏れず、相手のファイルがあなたのエージェントのコンテキストを薄めることもありません。
- **メソッドレイヤーもスペースごとです。** `aidlc/spaces/<active-space>/memory/` のルール（`org.md` → `team.md` → `project.md`）は、アクティブスペースの中で解決します。新しいスペースはフレームワークのベースラインから種付けされ（`org.md` がコピーされ、空の `team.md` / `project.md` が新規に作られる）、新しいチームはフレームワークの既定から始め、別チームの慣行を継がず、自分の慣行を獲得します。
- **スペースを `core/` で書くことはありません。** スペースはランタイムのチームデータで、インストール済みプロジェクトで `/aidlc space create <name>` で作ります。チームナレッジをフレームワークのソースから分けるのと同じ、データとコードの線です。複数チームを支えるために `core/` に足したり再生成したりするものはありません。その能力はエンジンに同梱されています。

この章のメンタルモデルは、各スペースの中で変わらず成り立ちます。ステージがエージェントを名指し、エージェントがナレッジを読み、そのすべてを、データを編集して形づくります。スペースは *誰の* データかをスコープするだけです。だから 2 チームが 1 つのプロジェクトで AI-DLC を走らせても、コンテキスト、慣行、記録が衝突しません。
