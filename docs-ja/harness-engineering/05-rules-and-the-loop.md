# Rules and the Learning Loop

ルールは、チームがすべてのワークフローに持ち込む常設の決定です。「いつもこうやる」というもので、そうでなければ実行ごとの冒頭で説明し直すことになります。ハーネスエンジニアとしては 2 通りで書きます。ルールファイルを直接編集するか、**学習ループ**にワークフロー内の修正を持続的なルールへ昇格させるかです。この章は、ユーザーガイドの[Rules and the Learning Loop](../guide/09-rules-and-the-learning-loop.md)の章のオーサリング側の相棒です。ユーザーガイドはループを概念的に扱い、銀行の例を端から端まで歩きます。ここでの焦点は運用的です。何のためにどのファイルを編集するか、ルールを重ねたとき strict-additive モデルがどう振る舞うか、そして 1 回限りの修正が常設のルールになるようループをどう回すかです。

ルールは制御ループのフィードフォワードの半分です。エージェントが作業する*前*に読む散文です。[Sensors](06-sensors.md)はフィードバックの半分です。書き込みの*後*に発火する決定論的なチェックです。ルールは相棒としてセンサーを指定できます。2 つの半分は対になるよう設計されています。

## 5 つの層と、どのファイルを編集するか

ルールは `core/memory/` の下に Markdown ファイルとして置かれます（空間メモリ層のための、書かれたソースです）。スコープごとに 1 ファイルです。`scope:` フロントマターフィールドはありません。この実装はスコープをファイル名から導くので、選ぶファイル*が*、書くスコープです。

| 適用したいルールの範囲 | 編集先 | スコープ |
|---|---|---|
| あなたの組織のすべてのプロジェクト | `org.md` | org（フレームワーク既定） |
| あなたのチームが実行するすべてのプロジェクト | `team.md` | team |
| この 1 つのプロジェクト | `project.md` | project |
| 1 つのフェーズのすべてのステージ | `phases/<phase>.md` | phase |

プラグインもハウスルールを持ち込めます。それらは、プラグインが指定するファイル（またはインストール時に選ばれるファイル）と、対象のフェーズファイルの末尾に、自分だけの 1 節として着地し、チーム自身のルールはその上の節に留まります。[プラグインの作成](10-authoring-a-plugin.md)を参照してください。

4 つのフェーズファイルは `phases/ideation.md`、`phases/inception.md`、`phases/construction.md`、`phases/operation.md` です（initialization はブートストラップ専用で、ルールファイルを出荷しません）。5 つ目の層、ステージごとのルール（`aidlc-stage-<slug>.md`）は将来のリリースのために予約されています。まだ書けません。

どのファイルに手を伸ばすかは、2 つの判断が駆動します。

- **`org.md` はフレームワークが出荷します。** すべてのプロジェクトが継承する既定を運びます。トランクベース開発、walking-skeleton のポリシー、スコープごとのテストの姿勢です。上流として扱ってください。たいていのハーネスエンジニアはそれをそのままにし、team か project で書きます。
- **project スコープは持続的な逸脱のためで、何でもかんでものためではありません。** `project.md` に手を伸ばすのは、*この*プロジェクトがチーム全体の実践から安定して離れるときだけにしてください。チームが squash するところで rebase するモノレポ、テストの下限を飛ばすレガシープロジェクトなどです。そのルールがチームの実行するすべてのプロジェクトを助けるなら、それは `team.md` に属します。

各ファイルは、話題ごとの見出しの下の平坦な散文です。`## Way of Working`、`## Testing Posture`、`## Deployment`、`## Code Style` などです。それが属する見出しの下に箇条書きを加えてルールを足します。完全なファイル名対スコープの表とリゾルバーの仕組みは、規範的な契約です。[Rule System § ファイル名から導くスコープ](../reference/08-rule-system.md#filename-derived-scope)と[§ レイアウト](../reference/08-rule-system.md#layout)です。

### リポジトリ全体に Guard Policy を保つ

これらのファイルの 1 つの見出しは、散文ではなく構造化された設定として読まれます。`## Guard Policy` です。この空間の作業でガードがどこまで退くかを、2 つの点で決めます。人間が何かを承認・確認した後に入力が変わったとき何が起きるか（承認後に編集されたプラン、レビュー後に編集されたレビュー済みドキュメント、現在の要約確認なしに保存された出力）です。`strict` はその承認を再開し、`relaxed` と `off` は変更を 1 度記録し、人間に 1 行で伝え、続行します。プラン承認後に動いたワークスペースのソースは、どの値でも記録して続行します。そしてどの権限フェンスが保たれるかです。`strict` は何も下げず、`relaxed` は `plan-approval` と `review-freeze` を下げ、`off` はその 2 つに加えて `state-transition` と `reviewer-scope` を下げます。`human-presence` はこの語で下がりません。既定では、各 intent はそのスコープの値を取ります。チャットから下げるには、人が自分の言葉で頼んでコンダクターが setter を実行するか、スイッチ（`/aidlc --guard-policy relaxed` または `guard policy off`）をタイプしてエージェントがその行について同じ setter を実行します。全員に `strict` を保つには、`team.md`（または `org.md`、1 つのプロジェクトには `project.md`）の見出しの下に 1 行を置きます。

```markdown
## Guard Policy

Mode: strict
```

どの層の `Mode: strict` も、スコープ既定と intent 自身の行に勝ちます。その後、`relaxed` や `off` へのチャットやフラグの切り替えは、このファイルを示す一文で拒否され、実行中の intent に対する次のガバメントチェックが、ファイルをソースとして示す `GUARD_POLICY_SET` 行として変更を記録します。`Mode: relaxed` と `Mode: off` は、値がスコープから来たすべての intent にポリシーを設定し、それを宣言する最も狭い層が勝ちます（`project.md`、次に `team.md`、次に `org.md`）。人が 1 つの intent について設定した値はそれを保ちます。節を空のままにしても何も変わりません。他の値は、ファイルと 3 つの許される値を示す検証エラーです。この行は `## Testing Posture` と同じ `Field: value` の文法で読まれ、コメントアウトされた行も含みます。HTML コメントの中の `Mode:` は何も宣言しません。

`strict` を持つ層は `/aidlc config set guard.<fence> off` を拒否し、拒否でメモリファイルを示し、その行が立っているあいだ、先に下げられたフェンスを強制的に on に戻します。保持された `Guards Off` のエントリは残り、メモリ行がもう strict を保たなくなった後にだけ再び効きます。マシン全体のキルスイッチはなお優先します。フェンスを `on` にすることは引き続き許されます。

退役した見出し `## Change Control` は 1 リリースだけ読まれるので、メモリファイルが改名より前からある空間は動き続けます。1 つのファイルが両方を運ぶとき、新しい見出しの下の節が勝ちます。

## Strict-additive: 層は積み重なり、どれも静かに上書きしない

連鎖は今日 4 つの層を通じて解決され、5 つ目は予約されています。

```
org -> team -> project -> phase      (stage: reserved, not authorable yet)
```

モデルは **strict-additive** です。適用されるすべてのルールが一度にエージェントのコンテキストに現れます。実行時に落とされたり抑えられたりするものはありません。org の既定、team の実践、project の特殊化は連結されます。ステージがフロントマターですでに `phase:` を宣言しているので、対応するフェーズルールが付きます（ステージが他のすべてをインポートするのと同じ pull オーサリングの向きです）。各ステージにどのファイルが適用されるかは、グラフがコンパイルされるときにそのグラフノードに焼き込まれ、ランタイムは連鎖を再び歩きません。選ばれたファイルの現在のテキストが各ステージ配信の前に読まれます（[学習は次のステージ配信から適用される](#learnings-apply-from-the-next-stage-delivery)を参照）。[Rule System § strict-additive 実行時モデル](../reference/08-rule-system.md#strict-additive-runtime-model)と[§ 5 層継承](../reference/08-rule-system.md#five-layer-inheritance)を参照してください。

書き手としてのあなたは、ここから次のことを読み取れます。`overrides:` ブロックも、設定する `enforcement:` キーワードもありません。狭い層が広い層に静かに勝つことはありません。代わりに、書いたすべての層がエージェントのビューに同時に存在します。それが書き方を変えます。ルールは、それが適用されるべきスコープで肯定的に述べ、上の層と積み重なることを信じます。上の層を抑えるスイッチに手を伸ばす必要はありません。

### 衝突は学習の書き込み前に検査され、実行時には解決されない

実行時に何も上書きしないので、広いスコープのルールと*矛盾する*ルールは、リゾルバーがほどけない問題になります。学習ループのプロトコルは、選択が決定論的な書き手に届く前に、orchestrator に節レベルの LLM 検査を実行させることでそれに対処します。team または project スコープの学習が、ある `## Heading` の下に加えられようとするとき、orchestrator は提案されたテキストを `org.md` の同じ見出しと比べます。矛盾を見つけると、org の一文を示し、3 つの選択肢を提示します。**revise**、**skip**、または org ルールの所有者への **escalate** です。衝突のない選択か、ユーザーがエスカレートした選択だけが進みます。project ティアの書き込みは org に対してだけ検査します。team 対 project の違いは正当な project の特殊化であって、ポリシー違反ではないからです。

決定論的な `aidlc-learnings.ts persist` の書き手は `org.md` を読まず、この比較を独立に強制しません。受け取った選択を受け入れます。この検査は監査の補助であって、強制の境界ではありません。Practices-discovery はもう 1 つの受け入れゲートですが、org 衝突の検査は実行しません。その昇格は、ユーザーの確認で正当化される決定論的な節の置き換えです。project ルールは、生成された `(affirmed YYYY-MM-DD)` 接尾辞を無視して、同じテキストがその節に無いときだけ `Mandated` または `Forbidden` の下に追記されます。変わらないルールを再確認すると、既存のテキストと日付が保たれます。2 つの読み取り専用の `/aidlc --doctor` 行が、事後に状態を示します。**rule-drift** 行は、team または project の内容が埋まった org の見出しと重なる見出しを示し（人が確かめるべき矛盾の候補）、ライフサイクルで古くなったファイルは別に stale-suppressed として報告されます。**paired-coverage** 行は、実際に解決されるセンサーを指定するルールがいくつあるかを報告します。どちらも補助的で、終了コードを決して変えません。[Rule System § rule-drift 検出](../reference/08-rule-system.md#rule-drift-detection)を参照してください。

## 学習ループの運用

ルールが書かれるもう 1 つの道は、ファイルをまったく開かないことです。ワークフロー中にエージェントを修正し、ゲートでその修正を確認すると、フレームワークがそれをあなたのために書きます。それが学習ループです。たいていのステージ実行は何も加えず、それは健全です。ループが出てくるのは、人がステージでエージェントを修正したとき、または次回のために何かを保つよう頼んだときだけです。

仕組みは[ユーザーガイドの章](../guide/09-rules-and-the-learning-loop.md)で扱います。ハーネスエンジニアの視点は、ループが何を生み、どこに着地するかです。

1. **日記はステージ中に記録します。** コンダクター（有効なステージを実行するライブの `/aidlc` セッション）は、`<record>/<phase>/<stage>/memory.md`（intent の記録ディレクトリ `aidlc/spaces/<space>/intents/<YYMMDD>-<label>/` の下）に観察ログを保ちます。4 つの見出しの下にエントリを置きます。Interpretations、Deviations、Tradeoffs、Open questions です。これはあなたのために自動で作られ保たれます。手で編集しないでください。これはステージのエージェントの推論の記録で、その中のものは人に提示されません。
2. **修正は 1 度だけ尋ねられます。** 人がエージェントを修正した（Request Changes、または作業中に自分の言葉での修正）ステージで、次回も成り立つ形の修正なら、承認ゲートの前にエージェントが「You asked me to <their change>. Keep that for next time?」と、`Yes, for this project`、`Yes, for the team`、`No` 付きで尋ねます。何も修正されていなければ、何も尋ねられません。はっきり保つよう頼まれた注記は、質問なしで保たれます。[どう見えるか](../guide/09-rules-and-the-learning-loop.md)はユーザーガイドが示します。
3. **保たれるものを書きます。** 保たれた修正は日付付きの実践行として着地します。人はファイルパスも見出しも選びません。人の選択がファイルを決め、エージェントが見出しを振り分けます。

### 保たれた学習がどこに着地するか

確認された学習は実践そのものです。practices-discovery が確認するのと同じ空間メモリファイル（`aidlc/spaces/<active-space>/memory/team.md` / `memory/project.md`）に着地し、別個の `*-learnings.md` の面はありません。人の選択がファイルを決めます。

| 人の選択 | 着地先 | 監査イベント |
|---|---|---|
| Yes, for this project（と、保つよう頼んだ注記） | `aidlc/spaces/<active-space>/memory/project.md` | `RULE_LEARNED` |
| Yes, for the team | `aidlc/spaces/<active-space>/memory/team.md` | `RULE_LEARNED` |
| No | なし | なし |

既定のスコープは **project**、最も狭いものです。**Yes, for the team** は、教訓がこのプロジェクトを超えて適用されるとき、学習を `memory/team.md` に広げます。org へ広げる道はありません。org の実践はフレームワークが出荷するか、別のプロセスで組織が書くので、ループは org スコープで決して書きません。既定を狭く保つと、1 つのプロジェクトの驚きが、うっかり組織全体のルールになることを防ぎます。学習ループと practices-discovery は、この同じファイルに 2 つの異なるライフサイクルで書きます。ループは日付付きのエントリを 1 つずつ追記し、practices-discovery は節全体を確認します。リゾルバーは、きれいな整数の連鎖 org → team → project → phase でファイルを並べます。

### 学習がルールではなくチェックのとき（`SENSOR_PROPOSED`）

保つ価値のあるものが*繰り返しの手作業チェック*のこともあります。ステージの出力の同じ隙間を見張り続けるようなものです。その種類の学習をゲートで確認すると、フレームワークはそれをルールではなくセンサー束縛として扱います。2 つの書き込みのインストールをアトミックに行います。`.claude/sensors/` の下にセンサーのマニフェストを雛形で作り、新しいセンサーの id を、発端となったステージの `sensors:` インポート一覧に追記し、`SENSOR_PROPOSED` 監査行を残します。これがフレームワークのリリース外でのステージファイルへの、認められた唯一の編集です。インポート一覧だけが増え、ステージ本文は決して触られません。そこから、[Sensors](06-sensors.md)の力でマニフェストを手で肉付けします。ループは束縛を雛形で作り、あなたがチェックを書きます。

### 学習は次のステージ配信から適用される

ゲートで捕まえた学習は、すでに選ばれたルールファイル（`project.md` か `team.md`）に着地し、エンジンは各ステージ配信の前に選ばれたファイルのテキストを読み直します。だからルールは、現在の実行の次の適用可能なステージと、以降のすべてのワークフローでエージェントに届きます。待つのは選択そのものです。真新しいルールファイルがディレクトリの走査に入り、新しいセンサーが束ねられるのは、次にステージグラフがコンパイルされるときだけです。

手で書くときも同じです。ワークフロー途中で `team.md` を編集すると、進行中の実行の次のステージ配信に届きます（すでに実行されたステージをさかのぼって変えることはありません）。センサーの設定はルールのテキストとは違います。その一部はコンパイル済みグラフに置かれ、一部は発火時にまた読まれ、その分割は書き込みフック、ゲートのパス、インストールの形で異なります。センサーの編集（新しいセンサー、またはすでに束ねられたものの変更）を予測可能に効かせるには、ステージグラフを再コンパイルします。再コンパイルでも届かない例外が 1 つあります。ネイティブインストールでは、同梱センサーのワーカーは id で選ばれるので、同梱マニフェストの `command` を編集しても違うものは実行されません。そこでチェックを変えるには、自分のセンサー id が要ります。
