# コミットの来歴

> 対象読者: Tier 2/3（チーム導入者、フレームワーク貢献者）。

この章は、コミットの来歴サブシステムの正式なリファレンスです。任意の git コミットまたは diff の範囲から、その変更されたパスを所有するレビュー済みの作業単位への、永続的な逆引きです。3つの部分から成ります。committed reviewed-source evidence（レビュアーが承認したものの、すべてのクローンとともに移動するよう intent レコードに書かれたスナップショット）、読み取り専用のリゾルバ `aidlc attest resolve`（帰属、ドリフトの分類、明示された信頼の根拠）、そして `SOURCE_COMMITTED` の監査アンカー（enrichment のみ。リゾルバは決してそれを読みません。`aidlc attest anchor` によって、またはオプトインのセッション開始時のスイープによって書かれます）です。関連リンク: [State Machine](12-state-machine.md)（`SOURCE_COMMITTED` が加わるイベント分類法）、[Hooks and Tools](06-hooks-and-tools.md)（`aidlc-attest.ts` のツールエントリ）、監査フォーマットのレジストリ（`knowledge/aidlc-shared/audit-format.md`）、そして [Guide: CLI Commands](../guide/12-cli-commands.md) のユーザー向けコマンドのウォークスルー。

---

## 1. 課題

Code Generation はすでに、各レビュー済みの unit を、それがレビューした正確なソースに束縛しています。unit ごとの `REVIEW_COMPLETED` レシートは、その unit がクレームしたパスとマニフェストのバイトにわたる `Unit Source Fingerprint` を運びます（[Guide: State and Audit — source-bound review receipts](../guide/10-state-and-audit.md#source-bound-review-receipts) を参照）。欠けていたのは *逆方向* です。後からランディングする（しばしば squash、rebase、または無関係な変更とバンドルされる）コミットが与えられたとき、どのレビュー済みの unit（と intent）が各変更パスを所有し、コミットされた内容はレビューされたものと依然として一致するのか。その逆引きがなければ、コミットの下流にあるもの（パイプライン、監査人、リリースノート、1年後に履歴を読む人）は、「ここのすべてのソース変更はレビュー済みの unit に辿れるか」に答えられません。

## 2. 脅威モデル

解決は、日常的に混同される2つの問いに答えます。その区別が設計のすべてです。

- **完全性（Integrity）** — *ランディングしたバイトは、あるレシートが承認したバイトと等しいか。* 内容だけから無条件に答えます。検証は、レシートの `Unit Source Fingerprint` にハッシュされるバイトを必要とするので、改ざんはパスを `drifted`/`unverifiable` に移すことしかできません。パスを誤って検証済みにすることは決してできません。
- **真正性（Authenticity）** — *そのレシートは、実際に起きたレビューによって生成されたか。* レコードのレイアウトでは、これに答えられません。レシート、マニフェスト、evidence はリポジトリ内の通常のファイルなので、リポジトリに書き込める者は誰でも、それが承認するソースと同じ変更セットの中を含め、レシートを書けます。ディスク上の何も、それを本物のレビューと区別しません。

したがって、レポートはチェックした以上を決して主張しません。すべてのレポートは、自身の帰属の実際の根拠を名指しする `trust{}` オブジェクトを、4段の梯子で運びます。

| `trust.level` | 意味 | 除外するもの |
|---------------|---------------|-------------------|
| `informational` | レコードは **ワーキングツリー** から読まれました。同じコミットのクローンが再現しないかもしれないローカルな診断です。レコードがクエリ対象のリポジトリ内に存在しえないことが証明できるときにのみ到達します（§10）。 | なし。 |
| `reproducible` | レコードは **git ツリー** から読まれたので、同じ `(base, head)` はどのクローンでも永遠に同一に解決します。しかしクエリされた範囲自体がレコードのパスを書く（`trust.selfAttested`）ので、その変更が、それを判断するレシートを書いた可能性があります。 | 非決定論性。レコードへの事後の編集は、過去のレポートを変えられません。 |
| `independent` | reproducible で、**かつ** 依拠したレシートがテスト対象の変更から来ていません。範囲がレコードのパスに触れないか、`--record-ref` がその変更が書けないレコードソースを固定したかのどちらかです。 | 自己承認。変更が自身の判定をでっち上げることはできません。 |
| `signed` | independent で、**かつ** 判定が依拠するすべての権限を持つ入力が **署名された** コミットで届きました。依拠する各 unit について、そのレシートを運ぶ監査シャード **と**、そのレシートのフィンガープリントが選ぶ evidence ファイルの両方（git `%G?` が `G`/`U`。生のコードは入力ごとに `trust.signatures` に報告され、少なくとも1つは存在しなければなりません）です。 | 匿名のレコード書き込み。各承認がキーを名指しします。 |

2つのアンカー（どちらも、変更の側ではなく **検証者** の側が供給するものです）が、レポートを梯子で上げます。

- **`--record-ref <ref>`** は、レシート、マニフェスト、evidence を、クエリされたコミットのツリーではなく `<ref>` のツリーから読みます。テスト対象の変更が動かせないもの（保護されたブランチ、レコード専用の ref、レビューシステムが維持するミラー）に向けます。これが `independent` を意味あるものにし、自分で書いた承認を剥ぎ取るものです。レコードが固定されると、でっち上げられたレシートはレコードソースに単に存在せず、そのパスは `drifted` または `unattested` を報告します。
- **`--require-trust <level>`** は、そのレベルをゲートにします。達成されたレベルがそれに届かない限り、exit **3** します（`--fail-on` と共有）。

**スコープ内。** レビュー後の内容ドリフト（`drifted`）。欠けている、一致しない、または gitignore されたものだけの evidence（`unverifiable`、fail closed）。単一の所有者を名指ししないレシートの順序（`indeterminate`、fail closed）。*署名された* evidence を選ぶ署名なしのレシート（`signed` はレシートもカバーするので、レベルは `independent` にフォールバックします）。自身を承認するレシートを書く変更（`reproducible` に上限付けられ、`--record-ref` で排除されます）。レコードがクエリされたコミットと異なるチェックアウト（レポートに影響できません。レコードはツリーから読まれます、§4）。古い判定を変えるためのレコードの事後の書き換え（同じ理由で不可能）です。

**スコープ外。** 固定されたレコード ref に書き込める者、またはレコードコミットの署名を偽造できる者は、リゾルバが honour するレシートを生成できます。*誰が承認を書けるか* を確立するのは、このツールではなく、ホスティングプラットフォームの仕事です（ブランチ保護、必須の署名、レビューゲート）。起きたが杜撰だったレビューも、依然としてレビューです。そして解決は、レビューされた unit が *正しい* unit だったかについては何も言いません。

**デフォルトの姿勢。** どちらのアンカーもなければ、レポートは **informational なメタデータ** です。完全性については正確で、権限については沈黙します。検証者が信頼のルートを名指しし、レベルを要求したときにのみ、**強制の仕組み** になります。その選択はチェックを実行する者のものです。だからそれは組み込みのポリシーとして固定せず、フラグとして提供します。`trust{}` が常に出力にあるので、保存されたレポートが、それを生成したアンカーより強いものとして読まれることは決してありません。

## 3. 設計上の制約

3つの制約が設計の残りを形作ります。それぞれが馴染みのある仕組みを除外します。

1. **ほとんどのコミットは手動です。** ユーザーは素の `git commit` で、どのマシンからでも、いつでも（しばしば変更を生んだセッションのずっとあとに）コミットします。したがって hook やセッション時のキャプチャは *土台* になりえません。セッションで観測されるものは、よくても enrichment です。
2. **フィンガープリントだけでは unit を名指ししません。** レシートの `Unit Source Fingerprint` は *何が* レビューされたかを証明しますが、素のクローンとコミット範囲から始める検証者は、明示的でコミットされた帰属の構造なしに、変更されたパスからそのレシートへ辿る術を持ちません。
3. **コミットメッセージはチャネルではありません。** チームが自身のコミット形式を所有します。トレーラー、チケットの接頭辞、メッセージの慣行は信頼できず、決して解析されません。

## 4. 帰属モデル

帰属は **コミットされた内容の純粋な関数** です。コミットのツリーに加えて、intent レコードの *git ツリー*（監査シャード、unit の `source-manifest.json`、そして以下のコミットされた evidence）です。ワーキングツリー、ローカルの状態、解決される ref 以外の ref、hook が発火したこと、環境変数、メッセージのテキストには何も依存しません。2つの帰結があります。

- **どのクローンも解決できます。** テスト対象のコミットだけを持つ素のチェックアウトは、クローンが初期化しないままにするサブモジュールの下を除き、著述したマシンと同一のレポートを生成します。その場合、コミットのリストにはその中のファイルのエントリがありません。
- **決定論性。** 同じ `(base, head)` のペアは常に同じ帰属を生み、何年後も続きます。より多くの unit をレビューすること、レコードを amend すること、チェックアウトで evidence を編集することは、以前のコミットが解決する先を遡及的に変えられません。同じことが *除外* にも当てはまります。ハーネスのシェルは、範囲のベースツリーのコミットされた `<dir>/tools/data/harness.json` によって確立されるので、チェックアウトでハーネスをインストールまたはアンインストールしても、過去のコミットの `.claude/**` パスを `excluded` と `unattested` の間で反転させることはできず、変更が自身の除外を宣言することもできません。

レコードソースは、デフォルトでクエリされたヘッド自身のツリーで、`--record-ref`（§2）で上書きされます。それをツリーから読むことが、上記の2つの性質を真にします。ワーキングツリーが参照されるのは、レコードがクエリ対象のリポジトリにまったく存在しえない唯一のレイアウト（レコードのルートがテスト対象のリポジトリの外にあるマルチルートワークスペース）だけで、そのレポートは `informational` で、そう言う `warnings[]` のエントリを運びます。

所有は、engine が完了時に使うのと同じレシートの意味に従います。各 unit について、**最新の READY `REVIEW_COMPLETED`** レシート（`Verdict: READY`、`Unit`、`Stage`、`Unit Source Fingerprint` を運ぶもの）が権威的です。レシートはタイムスタンプ、次にシャード内の位置、次にシャードのインデックスで順序付けられます。同じ unit に対する、同じタイムスタンプで *異なる* シャードにある2つの READY レシートは順序付けられず、fail closed します（`indeterminate`、§6）。複数の unit がクレームするパスは、最新のクレーム者に属します（「より新しいレビュー済みのクレームが、意図的な共有ファイルの統合を所有できる」という完了の同じ規則が当てはまります）。そして2人のクレーム者が最新のタイムスタンプを共有するとき、「最新」は単一の所有者を名指ししないので、そのパスも名前順では解決せず、`indeterminate` として fail closed します。

所有するレシートごとに、パスのクレームは、利用できる最も強いソースから、順に来ます。

| `claimsSource` | 意味 |
|----------------|---------|
| `manifest` | unit の `source-manifest.json` が、evidence ヘッダーに記録されたマニフェストダイジェストにハッシュされる。ディレクトリ接頭辞のクレーム（`src/generated/`）を含む、完全なクレームの忠実度 |
| `evidence-only` | 検証可能なマニフェストがない。クレームは evidence のリストの正確なパスキーにフォールバックする（接頭辞のクレームは失われ、クレームされたディレクトリ下の新しいファイルは `unattested` として現れる） |
| `manifest-unverified` | マニフェストは存在するが evidence に対して検証できない（例: evidence が欠けている）。パスは依然として帰属するが、内容はチェックできない |

## 5. committed reviewed-source evidence

レビュー時、engine は unit の reviewed-source スナップショットを二重に書きます。

- **コミットされた evidence**（解決にとって権威的）: intent レコード内の `<record>/construction/<unit>/<stage>/reviewed-source-<hash12>.tsv`。`<hash12>` はフィンガープリントの最初の12桁の16進です。レコードはコミットされているので、evidence はすべてのクローンとともに移動します。
- **ローカルのスナップショット**（従来から存在）: `<record>/.aidlc-engine/source-review/<stage>/unit-<unit>-<hash12>.tsv`。マシンローカル（無視される）で、完了時の鮮度チェックのために保持されます。これは解決の検証ソースでは **ありません**（§6）。gitignore されたバイトを honour すると、判定がどのマシンで実行したかに依存してしまいます。

swarm の worktree 内でレビューされた unit は、両方のファイルをそこから持ち出します。finalization がメインのレコードに転送する reviewed-record スナップショット（`aidlc-swarm.ts` の `captureReviewedRecordSnapshot` / `mergeReviewedRecordSnapshot`）は、unit の `source-manifest.json` **と** その `reviewed-source-<hash12>.tsv` を含み、転送の前にレシートのフィンガープリントと照合してハッシュチェックされ、レコードのアーティファクトと同じ all-or-nothing のトランザクションで書かれます。コミットされた evidence が存在する前にレビューされた進行中の swarm については、finalization が、バイト単位で同一の、レシートに束縛されたローカルのスナップショットを、そのコミットされたパスに昇格させます。改変された、または欠けているローカルの evidence は依然として fail closed します。したがって swarm で構築された unit は、アップグレード後に再レビューを必要とせずに、インラインのものと全く同じように解決します。

両方のファイルは **バイト単位で同一の内容** を保持し、レシートの `Unit Source Fingerprint` は、まさにそれらのバイトの SHA-256 です。2つ目のフィンガープリント方式はありません。evidence をコミットしても **新しいフィンガープリントの意味はゼロ** でした。書き込みは content-addressed です。同じフィンガープリントの書き直しは冪等な no-op で、同じアドレスで異なるバイトを見つける書き込みは拒否します（`address collision or corruption`）。

ファイル形式（`aidlc-lib.ts` の `parseUnitSourceListing` / `serializeSourceListing`）は、厳格な TSV 文法です。

```
manifest\t<sha256-of-manifest-bytes>\t-\n
<repo>\t<path>\t<mode>\t<oid>\n        # 0 行以上、キーでソート
```

ヘッダーはマニフェストのバイトを束縛します。各行は、クレームされたパスの repo セレクター（ワークスペースのルートには空）、path、git のファイルモード（`/^\d{6}$/`）、そして 40 または 64 桁の16進の content ID を記録します。content ID は、通常のファイルのバイトの SHA-256（テキストは CRLF を LF として読む）、シンボリックリンクのターゲットテキストの SHA-256、またはサブモジュールの gitlink（モード `160000`）のコミット ID です。フィールド内の `\t`、`\n`、`\r`、`\\` はバックスラッシュでエスケープされます。重複したキー、末尾の改行の欠如、不正なフィールドは、ファイル全体を拒否します（パーサーは null を返し、evidence は存在しないものとして扱われます）。有効なヘッダーのあとの空のリストは有効です（レビューが残存パスをクレームしなかった unit）。

## 6. 解決 — `aidlc attest resolve`

```
aidlc attest resolve [<commit>|--commit <rev>] [--diff <base>..<head>]
                     [--repo <name>] [--space <name>] [--intent <dir>]
                     [--record-ref <ref>] [--require-trust <level>]
                     [--fail-on <statuses>]
```

読み取り専用です。resolve は決して書かず、監査イベントを出さず、`SOURCE_COMMITTED` アンカーを読みません。モード: 単一の `<commit>`（位置引数か `--commit <rev>`。両方は不可）はそのコミットの first-parent デルタを解決します（デフォルトは `HEAD`）。`--diff <base>..<head>` は範囲の端点を直接解決し、3点形式の `<base>...<head>` はマージベースを使います。各動詞は自身のフラグだけを受け入れます。`resolve --reconcile` と `anchor --record-ref` は使い方のエラー（exit 1）で、暗黙に無視されることは決してありません。クローンが shallow のために親が欠けているコミットはエラーで、ツリー全体の diff ではありません（§10）。デルタ内のすべての変更パスが分類されます。

| ステータス | 意味 | 失敗可能 |
|--------|---------|:--------:|
| `verified` | レビュー済みの unit が所有し、コミットされた blob OID がレビューされた evidence と一致する | — |
| `drifted` | レビュー済みの unit が所有するが、コミットされた内容がレビューされたものと異なる | ✓ |
| `unattested` | どのレビュー済みの unit もそのパスをクレームしない | ✓ |
| `unverifiable` | レシートがパスをクレームするが、その内容を束縛するコミットされたバイトがない。evidence がレコードソースから欠けている、レシートのフィンガープリントにハッシュされない、または gitignore されたローカルのスナップショットにのみ存在する。**fail closed** で、暗黙に検証されることは決してない | ✓ |
| `indeterminate` | レシートの順序が曖昧。異なるシャードの、または両方がそのパスをクレームする異なるレコードの、同じタイムスタンプの READY レシート。**fail closed** | ✓ |
| `excluded` | フレームワークのシェル（リポジトリが運ぶ場合の `aidlc/` / `.aidlc/`）、intent レコード下の `.aidlc-engine/` ディレクトリ（およびレガシーの `.aidlc-sensors/` ディレクトリ）、そして（ワークスペースのシェルを運ぶリポジトリでは）範囲のベースツリーですでに確立されたハーネスのシェルディレクトリ（`.claude/`、`.kiro/` …。コミットされた `<dir>/tools/data/harness.json` で識別される）。ヘッドが導入したマニフェストは、自身やその兄弟を除外できない。決して帰属せず、決して失敗可能でない | - |

`--fail-on` は、4つの失敗可能なステータスのカンマ区切りのサブセットを取ります。一致すると exit **3**（0 = クリーンに解決したか何も一致しなかった、1 = 使い方/環境のエラー）します。`unverifiable` を省くゲートは、レビューされた内容を何もチェックできないパスを通すので、厳格なゲートは4つすべてを名指しします。`--require-trust <level>` も、達成された `trust.level` が不足するとき exit 3 します（§2）。この2つのフラグは直交します。`--fail-on` は *変更のどれだけが attested されているか* を縛り、`--require-trust` は *レポートがどれだけ信頼できるか* を縛ります。

レポートは stdout 上の JSON です。`paths[]`（パスごとの status/unit/intent/reason）、`units[]`（所有するレシートの詳細。stage、iteration、`evidenceSource`、`claimsSource`、記録されたバイパス、evidence を最後に書いたコミットの `evidenceCommit`/`evidenceSignature`、勝ったレシートを運んだ監査シャードと *それ* を最後に書いたコミットの `receipt`/`receiptCommit`/`receiptSignature`、そしてクレームされたすべてのパスが `head` でそのレビューされた OID にランディングしたかを示す `fullyLanded`）、ステータスごとの `summary` カウント、エコーされた `failOn`、`trust{}`（§2。`level`、`required`、`satisfied`、`recordSource`、`recordRef`、`recordCommit`、`recordPinned`、`recordPathsChangedInRange`、`selfAttested`、`signatures[]`）、そして `warnings[]` です。

`warnings[]` は、どの単一パスの分類も変えずにレポート全体を歪めうる条件を名指しするので、それ自体でゲートを失敗させることは決してありません。`.gitattributes` によるリポジトリのバイト形式の変換（§10 を参照）、コミットされた intent レコードをまったく運ばないレコードソース（そのため何も帰属できず、そうでなければ「何も attested されていない」と同一に読まれる）、そしてワーキングツリーのレコードへのフォールバック（§4）です。

unit ごとの evidence は、検証されるには **コミットされ**ていなければなりません（`evidenceSource: "committed"`）。レガシーのローカルスナップショットは依然として見つけられ、診断として報告されます（`evidenceSource: "local"`）。二重書きが存在する前にこのマシンでレビューが起きたことを教えてくれます。しかしそのバイトがパスを検証することは決してありません。それらの unit は `unverifiable` で、evidence をコミットする再レビューを指す理由が付きます。これにより、どのマシンが尋ねても、コミットごとに1つの判定が保たれます。マルチルートワークスペースは、呼び出しごとに1つの repo を解決します。デフォルトではワークスペースのルート、または `--repo <name>` で記録された repo です。プロジェクトディレクトリ自体が git リポジトリでなく、記録された repo がちょうど1つそうである場合、その repo が自動で選ばれます（そしてそう言うノートが付きます）。1つもない、または複数ある場合は、`--repo` が必要です。

## 7. アンカー — `SOURCE_COMMITTED`（enrichment のみ）

```
aidlc attest anchor [--commit <rev>] [--reconcile] [--max-commits <n>]
                    [--repo <name>] [--space <name>] [--intent <dir>]
```

`anchor` はコミット（デフォルト `HEAD`）に対して解決を実行し、レビュー済みのクレームがランディングしたとき、関係する intent ごとに `SOURCE_COMMITTED` の監査イベントを追記します。監査証跡の中の、人間が読める前向きのポインタ（「このコミットはこれらの unit を運んだ」）です。これは厳密に **enrichment** です。resolve は決してアンカーを読まないので、ユーザーが常に手動でコミットし、決して `anchor` を実行しないリポジトリが失うのは、監査証跡の読みやすさだけです。

フィールド: `Commit`、`Repo`（記録されたセレクター、またはワークスペースのルートには `-`）、`Units`（カンマ区切り、ソート）、`Attributed Paths`（カウント）、`Observed`（直接の呼び出しには `session`、履歴のスイープには `reconciled`）。意味:

- **重複排除** は intent ごとに `(commit, repo)` で行われます。すでにアンカーされたコミットの再アンカーは、重複ではなくスキップとして報告されます。
- **swarm 対応** — `SWARM_SOURCE_MERGED` イベントの `Merge commit` によってすでに束縛されたコミットはスキップされます（swarm レフェリーがより豊かな文脈ですでにそれをアンカーしています）。
- **上限付きの reconciliation** — `--reconcile` は、以前のアンカーに関わらず、最後の `--max-commits` の first-parent コミット（デフォルト 100）を歩きます。重複排除はコミットごとなので、すでにアンカーされた領域の後ろのアンカーされていないギャップも埋め戻されます。各コミットを anchored、skipped、unattributed、または shallow の `boundary` として報告します。
- **shallow 安全** — shallow クローンの境界コミットには到達可能な親がないので、そのデルタは不明です。1つに対する単一コミットの `anchor` はエラーになります。`--reconcile` はそれを `boundaries[]` の下に列挙して進み、ツリー全体を、その中のパスをかつてクレームしたすべての unit に帰属させることはしません。
- **曖昧さに静か** — 所有が曖昧なパス（§6 の `indeterminate`）はアンカーされません。曖昧さの報告は resolve の仕事です。
- **CLI で保護** — `SOURCE_COMMITTED` は `CLI_PROTECTED_EVENT_TYPES`（`aidlc-audit.ts`）にあります。所有するツールだけがライブラリのパスを通じてそれを追記します。agent が監査 CLI を通じてそれをでっち上げることはできません。*マージ保護ではありません*。シャードのマージは、他のどのイベントとも同じくそれを運びます。
- **ワーキングツリーのレコード** — `anchor` は設計上、レコードをワーキングツリーから読みます。ローカルのリポジトリを今の状態で観測し、その出力はどの判定も依存しない enrichment です。§4 のツリー読み取りの決定論性を必要とするのは `resolve` だけです。

アンカーは **デフォルトで明示的** です。アンカーは解決が決して読まない enrichment なので、それを書くことはオペレーターが求める行為です。`aidlc attest anchor [--reconcile]` です。コマンドを覚えずに監査証跡にランディングしたコミットを名指ししてほしいチームは、**`AIDLC_SESSION_ANCHOR=1`** を設定して、セッション開始時のスイープにオプトインできます。すると、セッション開始時の hook（`hooks/aidlc-session-start.ts`）が、実際のセッション開始時に 25 コミットに上限を付けた、ベストエフォートの `runAnchor` reconcile を実行します（人は主にセッションの *間* にコミットするので、次のセッション開始が自然な観測点です）。intent ごとの重複排除が、毎セッションの再実行を冪等にします。スイープは起動をブロックすることは決してなく（非 git ワークスペースのような失敗は飲み込まれます）、コンパクトな resume と再束縛のプローブではスキップされます。スイッチが未設定（デフォルト）だと、セッション開始は来歴アンカーの行を書かず、来歴の作業をしません。それでも `SESSION_STARTED` または `SESSION_RESUMED` の行は記録します。明示的な動詞は、新しいチェックアウト、hook が無効なハーネス、セッションの上限（`--max-commits`、デフォルト 100）より深い履歴をアンカーする方法のままです。

## 8. 保証とエッジケース

- **squash/rebase の安定性。** 帰属はコミットの祖先ではなく内容（リストの content ID）をキーにします。他のものと squash されてランディングするレビュー済みの変更も依然として検証され、revert されたファイルをレビューされたバイトに戻すと `verified` に戻ります。
- **アップグレード前のレコード。** evidence の二重書きの前にレビューされたレコードには、コミットされた evidence がありません。次の unit ごとのレビューが evidence を二重書きするまで、どこでも（素のクローンと全く同じく、著述したマシンでも）`unverifiable` です。fail closed で、何が欠けているかを述べる理由が付きます。
- **1つの除外実装。** 任意のコミットのリストは `gitCommitSourceListing`（`aidlc-lib.ts` からエクスポート）から来るので、コミット側とレビュー側は、ドリフトする2つのコピーではなく、単一の除外実装を共有します。ハーネスシェルの規則（`isHarnessShellManifest`）も同じく1つの関数で、ここではツリーの blob に、レビュー時にはディスク上のファイルに適用されます。バイト形式の意味は **共有しません**。§10 を参照してください。
- **改ざんの非対称性。** 検証は、レシートの `Unit Source Fingerprint` にハッシュされるバイトを必要とするので、evidence を壊すことはパスを *失敗* させる（`unverifiable`）ことしかできず、パスを誤って検証することは決してできません。コミットされた evidence を壊しても、ローカルのバイトは検証しないので、無傷のローカルコピーによってそれが隠されることはありません。*チェックアウト* でそれを壊しても不活性です。意味を持つバイトは、レコードツリーの blob です。
- **レコードの読み取りは git 呼び出し1組。** ツリーに裏打ちされたレコードビューは、レコードのサブツリーを一度リストし（`git ls-tree -r -z --full-tree`）、必要なすべての blob を単一の `git cat-file --batch` でバッチ処理するので、履歴からレコードを読むコストは、ディスクから読むのとおおよそ同じです。

## 9. 信頼のセットアップ

2つの形が、ほとんどのチームをカバーします。

- **保護されたブランチのレコード。** レビューシステムが、それだけが動かせる ref（`refs/heads/aidlc-records`、またはミラー）にレコードコミットをプッシュします。検証者は `resolve --diff <base>..<head> --record-ref aidlc-records --require-trust independent --fail-on drifted,unattested,unverifiable,indeterminate` を実行します。自身のレシートを書く変更は何も得ません。そのレシートは固定されたツリーにありません。
- **署名されたレコード。** レコードコミットは署名され、ブランチは署名を要求します。`--require-trust signed` は、レコードソースもクエリされた範囲から独立しており（レコードはその前に書かれたか、`--record-ref` で固定されている）、evidence ファイルだけでなくレシートシャードを含む、依拠するすべての入力が署名されたコミットで届いたときにのみ成り立ちます。自身のレコードのパスを書く範囲は、それらを含むレコードから読まれる場合、署名がどうであれ `reproducible` のままです。署名できる変更の作者は依然として自己承認できることに注意してください。署名はキーを名指しするのであって、役割を分離しません。したがってこの形は帰属と否認防止に適し、固定 ref の形は職務分離に適します。両方のために両者を組み合わせてください。

どちらのアンカーもなしで実行することは、正当な3つ目の形です。その場合 `resolve` は、何がランディングし、それがレビューと一致するかを教える報告ツールで、`trust.level` がまさにその限界を記録します。

## 10. 限界

- **信頼のルートはここで確立されません。** `resolve` は、読んだレコードの来歴を報告します（`trust{}`）。ref を信頼できるものにするのは、ホスティングプラットフォームのブランチ保護、署名ポリシー、アクセス制御です（§2、スコープ外）。
- **署名はコミットレベルです。** 権限を持つ各ファイル（レシートの監査シャードと、それが選ぶ evidence ファイル）を最後に書いたコミットの `%G?` が、利用できる最も強いシグナルです。承認ごとの署名はなく、*どの* 識別情報が承認できるかという概念もありません。git が受け入れるどのキーからの有効な署名（`G`、または信頼されないキーからの有効な署名には `U`）も、署名済みとして数えられます。キーリングを設定し、区別が重要なときは `trust.signatures[]` を読んでください。
- 解決は、*ランディングした内容* を *レビューされた内容* に照らして分類します。レビューされたバイトが到達可能でなければ（evidence は content ID を記録するのであって、ファイルの本体ではありません）、drift したパスの reviewed-vs-actual の **diff** を示せません。diff が欲しいチームは、レビューされた blob を生かし続ける ref をプッシュするか、それらを帯域外に保存しなければなりません。
- 呼び出しごとに1つの repo です。ワークスペースをまたぐレポートは、`--repo` セレクターにわたるループです。
- `--fail-on` はパスのステータスだけでゲートします。「`docs/` の下では unattested でよい」のようなポリシーは、ツールではなく exit コードの周りのパイプラインに属します。
- **ワーキングツリー対リポジトリのバイト形式。** レビューの evidence はワーキングツリーのバイトをハッシュします（`stableFileSha256`）。コミット側のリストは、チェックアウトのフィルターを意図的に無効にして、生のリポジトリの blob を読みます。両側は、Git 自身のテキストの規則により CRLF テキストを LF として読むので、`core.autocrlf`（Windows チェックアウトのデフォルト）はドリフトを起こしません。clean/smudge フィルターやワーキングツリーのエンコーディングがアクティブな場所（例えば Git LFS）では、両側が同じ内容を異なってハッシュし、変更のないパスが `drifted` を報告します。初期化されたサブモジュールは、その gitlink（モード `160000`、そのコミット ID）に加えて、そのファイルのエントリとして列挙されます。初期化されないままのサブモジュールは gitlink だけを持つので、そのファイルは帰属しません。`resolve` はコミットされた `.gitattributes` を `warnings[]` でフラグします。それらの機能を使うリポジトリは、ゲートが使えるようになる前に、バイト形式を調整する必要があります。それらを統一するとフィンガープリントの入力が変わるので、別個の変更です（`docs/roadmap.md` を参照）。
- **shallow クローン。** `resolve <commit>` と単一コミットの `anchor` は、ルートツリーに対して diff してチェックアウト全体を分類するのではなく、shallow の境界コミットを実行可能なエラー（クローンを深くする。パイプラインでは `fetch-depth: 0`）で拒否します。`anchor --reconcile` はそのようなコミットを `boundaries[]` に記録します。`--diff` で解決される範囲は、両方の端点とそのマージベースが存在する必要があります。
- **クエリ対象のリポジトリの外のレコード。** レコードのルートがテスト対象のリポジトリの中にないマルチルートワークスペースでは、その repo のどのツリーもレコードを含まないので、ワーキングツリーが唯一の利用可能なソースです。レポートは `informational` で、警告を運び、`--record-ref` は暗黙に無視されるのではなく、honour できないものとして拒否されます。
