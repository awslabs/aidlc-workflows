# ステージ定義

この章は、AI-DLC ステージ定義の**ファイル形式**を扱います。YAML フロントマターのコントラクト、
3 区画の本体モデル、そしてそれらのソースを `stage-graph.json` に変えるコンパイルパイプライン
です。ランタイムの振る舞いのコントラクト（承認ゲート、質問フロー、状態追跡）を扱う
[Stage Protocol](04-stage-protocol.md) を補完します。この章は、ステージファイルが何を*含む*か
についてです。Stage Protocol の章は、ステージが何を*する*かについてです。

貢献者は、形式を理解するためにこれを読みます。ステージファイルを書く、または編集するときは、
`core/aidlc-common/protocols/stage-definition.md` の権威あるコントラクトを参照してください。
そのファイルが正規の仕様です。この章は、叙述と「いつ使うか」のガイダンスを足します。

---

## 2 つの読み手、1 つのファイル

すべてのステージ `.md` ファイルは、2 つの読み手に奉仕します。

- **パーサー**（`core/tools/aidlc-lib.ts` の `parseStageFrontmatter`）。YAML フロントマターを
  素のレコードに読み込み、その後 `validateStageFrontmatter`（`core/tools/aidlc-stage-schema.ts`）
  がそれを検査します。本体には触れません。
- ステージを実行する **LLM エージェント**。本体を読み、散文の指示に従い、アーティファクトを
  生成します。フロントマターには触れません。

両方を 1 つのファイルに保つことは、貢献者がグラフのエッジと実行ステップを並べて見ることを
意味します。それらを別々のファイルに分割すると（グラフ用の YAML 1 つ、エージェント用の散文
1 つ）、ステージをレビュー可能にするインラインの可視性が壊れます。

## なぜ Variant A3

形式は "Variant A3" と呼ばれ、それに向けて検討された 3 つのオーサリングバリアントの 3 番目です。

- **1 ファイルは分割ファイルに勝ります。** 1 つの `.md` のフロントマターと散文は、グラフ構造と
  実行ステップを一緒に保ちます。ステージを読むレビュアーは両方を見ます。
- **grep に優しい。** プレーンテキストです。バイナリ形式も、オーサリング時の YAML 対 JSON の
  変換もありません。
- **diff に優しい。** フィールドの追加、改名、本体の編集はすべて、コードレビューできれいに
  現れます。

却下された代替案は、散文だけのステージを持つ中央グラフファイル（手で編集する `stage-graph.json`）
でした。その散文を編集しながらステージがどのアーティファクトを生成するかを知る、インラインの
可視性を失います。

## オーサリングのフロー

```
Edit stage YAML
      |
      v
bun scripts/package.ts
      |
      +--> ignored dist/<harness>/<harness-dir>/tools/data/stage-graph.json
      |
      +--> ignored dist-release/<harness>/<harness-dir>/tools/data/stage-graph.json
                    |
                    v
             loadStageGraph()
```

YAML が権威を持ちます。JSON は生成されたビルドアーティファクトです。リポジトリのパッケージング
はそれをソースから再生成します。インストール済みのランタイムは、プラグイン合成後にそれを
再コンパイルすることもあります。

`aidlc-graph compile` と `compile --check` は、ランタイムと診断のサブコマンドのままですが、
リポジトリの貢献者は、コンパイル済みの JSON コピーをソース管理に保ちません。YAML を編集し
`bun scripts/package.ts` を実行します。パッケージングは新しい無視されるプロジェクションを
作り、`bun scripts/package.ts --check` は一時ルートで 2 回再ビルドして、ジェネレーターの
決定性を検査します。

## フィールドリファレンス — いつ使うか

権威ある仕様には、型と制約を持つ完全なフィールド表があります。このセクションは、判断を要する
フィールドについて叙述を足します。

### `requires_stage`

依存エッジをエンコードします。2 つの役割があります。

1. **意味的なデータ依存。** 「私はアーティファクト X を消費し、それはステージ Y が生成する」→
   `Y` を `requires_stage` に足す。
2. **提示順のエッジ。** 同じフェーズの 2 つのステージで、意味的な依存はないが固定の順序がある
   もの（たとえば Ideation の `feasibility` の前の `market-research`）。計算されるステージ
   `number` が安定して着地するよう、弱いエッジを足す。

コンパイルステップのスラッグのアルファベット順のタイブレークは、安全網です。特定の順序で着地
しなければならないステージについては、アルファベット順の偶然に頼るのではなく、エッジを明示的に
オーサリングしてください。

### `for_each`

そのインスタンスが反復を駆動するアーティファクトを名指しします。ステージはインスタンスごとに
1 回走ります。

今日のユースケース: 5 つの Construction ステージ（`functional-design`、`nfr-requirements`、
`nfr-design`、`infrastructure-design`、`code-generation`）がユニットごとに 1 回走ります。
それぞれが `for_each: unit-of-work`（`units-generation` が生成するアーティファクト）を宣言します。

明日のユースケース: 環境ごと、テナントごと、リージョンごと、コンプライアンス管轄ごとに走る
ステージ。このプリミティブはワークフローエンジンとして汎用です。Construction がたまたま最初に
それを行使します。

**集約は宣言されず、推論されます。** `for_each` ステージが生成するアーティファクトを消費する
ステージで、自分の `for_each` を宣言しないものは、定義上、集約ステップです。`build-and-test`
が正規の例です。5 つの Construction `for_each` ステージがすべてユニットにわたって反復した後に
1 回走り、それらの集約された出力を消費します。明示的な `fan_in` や集約フィールドはありません。
グラフの走査がそれを見抜きます。

**ユニット単位のステージは 1 つのブロックとして走ります。** エンジンは、ステージを実行順で
歩きます。番号順ですが、フェーズのユニット単位のステージは、その最初のユニット単位のステージが
立つところで一緒に走ります。各ユニットはブロック全体を歩き、すべてのブロック承認はその後の
最初のインテント単位 1 回のステージの前に来ます。次のステージ、最後のユニットの後のチームの
進行、ゲートの "Continue to" はすべてその順序に従います。コンパイルは `stage-graph.json` を
実行順で書きます。プラグインの新しいステージは、そのフェーズの最高番号を過ぎたところに番号
付けされるので、Code Generation の後にユニットごとに走るプラグインステージは、Build and Test
と CI Pipeline の後に番号付けされ、やはりそのユニットとともに走ります。ユニット単位のステージ
は、ブロックが始まった後にインテントごとに 1 回走るステージを要求できません。コンパイルは
そのエッジを拒否します。

### `summary_confirmation`

ステージの質問フローの、決定的な生成前チェックポイントを制御する任意の enum です。

- `required` は、すべての実行が、アーティファクト生成の前に質問ファイルを作り、統合された
  **Looks correct** の確認を得なければならないことを意味します。
- `if-present` は、条件付きの質問フローが質問ファイルを作ったときだけ同じ強制を適用します。
  現在の試行でそのサマリー決定または確認が記録されると、そのファイルを削除しても義務は
  なくなりません。質問と確認を復元するか、明示的なライフサイクルリセットを使って新しい試行を
  始めてください。

受領は markdown だけからは推論されません。`aidlc-log.ts` は、一致するプロンプト記録とその
記録の後の人の返信の後に、予約された `SUMMARY_CONFIRMATION_RECORDED` イベントを記録します。
エージェントがプロンプトを記録する前にサマリーを示したとき、そのチャットでのその記録の前の
最新の返信が、質問ファイルがステージの最後の質問や答えの後かつその返信の前に書かれ、返信と
プロンプトの間に他の質問が記録されなかったなら、`--message` なしで同じように数えられます
（エージェントがその返信の後に `[Answer]:` にその選択を書くことは、サマリーの書き込みでは
ありません）。エージェントは、`--message <id>` でメッセージを名指しすることもできます
（このクローンの監査がそのプロンプトの前、またはその返信の前に記録する、質問ファイルの最後の
書き込みの前に送られたメッセージは名指しできません。サマリーがそこに見えていなかったからです。
ステージゲートの承認は、ステージの出力に対して同じルールを読みます）。受領はその言葉を
`Person Reply` として保ち、それを質問ファイルのダイジェストとその記録された `Hash Scope` に
結び付けます。新しい受領は `confirmed-content-v2` を使います。変わらない raw-content の
SHA-256 アルゴリズムは、CRLF/単独の CR を LF に正規化し、セクションをファイル順に保ち、
結果の内容から末尾の空白を一度トリムします。すべての見える Q<n> とフィードバックのセクション
は結び付いたままです。サマリー後の 1 つの `Assumption Confirmation` セクションは、トップレベル
の `## Q<n>` またはフィードバック見出しとして綴られた行まで除外されます。`Q<n>` または
`Assumption Confirmation` の見出しは、claim-sources センサーのルールにより、先頭の絵文字装飾の
有無にかかわらず数えられます。保たれる内容のコメント、コード、HTML、先頭の BOM は、やはり
ダイジェストに影響します。見出しと答えの認識は今、`markdownBlocks` と `visibleMarkdownLines`
経由で組み込みの `Bun.markdown` パーサーを使います。raw HTML ブロックの内容は、見出し、答え、
タグに決してなりません。`Looks correct` の受領は、`Summary Authorization Id`（試行、ステージ、
ユニット、ワークフロー、質問パス、確認済みの内容、選択のダイジェスト）も運び、それがスコープの
アクティブな認可になります。write-audit hook は、その id を、ステージの出力のその後のすべての
`ARTIFACT_CREATED`/`ARTIFACT_UPDATED` 行にスタンプします。完了は、欠けている、または stale な
受領、変わった確認済みセクションや禁じられた見出し、または最新のネイティブ書き込みが現在の
受領の id を運ばない宣言済みアーティファクト（出力が現在の確認から派生していない）を拒否します。
同一の再確認は同じ id を発行するので、繰り返される `Looks correct` は取り消すのではなく再確認
します。変わった答えは新しい id を発行するので、出力はその下で再び保存されなければなりません。
受領と書き込みが着地した順序は、何も決めません。id のないレガシーな受領も、受領の後のネイティブ
書き込みを要します。スコープのない進行中の受領は、許される追記が受け入れられる前に、スコープ
付きの受領を作るために再確認されなければなりません。ユニット単位のステージは、適用される
ユニットごとに 1 つのユニットスコープの受領を要します。隔離された実行は、その
`single-stage:<slug>` ワークフロー同一性で同じ検査を使います。

`confirmed-content-v1` は、同じダイジェストアルゴリズムと、以前の手書きの可視性ルールを持つ、
サポートされるレガシースコープのままです。v1 の受領は、その記録されたダイジェストが現在の v2
ダイジェストに等しいとき受け入れられるので、影響を受けないドキュメントは、再確認なしにバイト
同一の同一性を保ちます。v1 の不一致は `SUMMARY_CONTENT_SEMANTICS_CHANGED` で拒否します。受領が
Markdown パーサーのアップグレードに先立つので、確認済みの内容が確認後に変わったか、v1 が確認
済みテキストとして扱った raw HTML 内容がもはやその一部でないかのいずれかです。raw HTML の
見出しと制御タグは今、Markdown 認識から除外されます。サマリーを再提示して再確認し、v2 を記録
してください。拒否は編集を主張することは決してありません。v2 の不一致は、既存の
`SUMMARY_CONTENT_STALE`「確認後に変わった」拒否を保ちます。スコープのない受領は、ファイル全体の
SHA-256 と既存の復旧テキストを保ちます。未知のスコープは、やはり `SUMMARY_HASH_SCOPE_INVALID`
で拒否します。以前と同一の確認のパスも、v2 のハッシュ関数を使って v1 の受領を比較します。
保存された受領は書き直されません。

### `workspace_requires`

ブール値、既定 `false`。インテント単位の記録ディレクトリの下の計画ドキュメントだけでなく、
**ワークスペースルートにソースコードを**書かなければならないステージに `true` を設定します。

なぜ存在するか: ステージの `produces[]` アーティファクトは通常、記録ディレクトリの下に解決
されます。ただし Reverse Engineering のリポジトリ単位の codekb のようなスペースレベルのストア
は例外です。そのため「produces は存在するか」の検査は、`code-generation-plan.md`、
`unit-test-instructions.md`、`code-summary.md` を書いたが実際のコードを 1 行も出さなかった
`code-generation` ステージでも満たされます（issue #366）。`workspace_requires: true` はその穴を
閉じます。ステージ完了のアーティファクトガード（`aidlc-state.ts` の approve/advance/finalize/
complete-workflow）は、ステージが完了できる前に、`aidlc/` ワークスペースツリーとハーネス
ディレクトリの外の、本当のソース作業の証拠も要します。

codekb ステージについては、同じガードがアクティブインテントの記録されたリポジトリ集合に従います。
記録された各リポジトリは、その正規の `aidlc/spaces/<space>/codekb/<repo>/` ディレクトリに
少なくとも 1 つの宣言済みアーティファクトを持たなければなりません。名前の間違った、または
記録されていないディレクトリは数えません。記録されたリポジトリのないインテントは、レガシーな
任意リポジトリディレクトリのフォールバックを保ちます。

「ソース作業」の検出方法はワークスペースによります。
- **Git ワークスペース** - ガードは git に尋ねるので、このセッションのコードを、brownfield
  リポジトリの既存の `src/` から区別できます。コミットされていない、または追跡されていない
  非ドキュメントの変更（`git status --porcelain`）があるか、最後のコミットが非ドキュメントの
  パスに触れた（`git diff --name-only HEAD~1 HEAD`）とき通ります。2 つ目の節は、コミット後承認
  （クリーンな作業ツリー、最後のコミットのコード）もやはり通ることを意味し、#366 Update 3 の
  クリーンツリーの誤ブロックを閉じます。
- **非 git ワークスペース**（または任意の git エラー）- ガードは、シェルなしのファイルシステム
  存在検査にフォールバックします。`aidlc/` ワークスペースツリーとハーネスディレクトリの外に、
  少なくとも 1 つのファイルが存在しなければなりません。
- **ワークスペース自身の git の外に保たれるコード** - コードは、インテントの記録されたリポジトリ
  の 1 つ（そのレジストリ行の `repos`）、作業開始後に作られた子リポジトリ、クローン、worktree、
  それらのいずれかのリンクされた worktree（`git worktree list` が名指しするもの）、または
  ワークスペースの git が追跡しないチェックアウト（たとえば、プロジェクト外に保たれ、その中の
  gitignore されたフォルダに置かれたリポジトリの worktree。各追跡されない、または無視される
  フォルダの 3 レベル下まで、リンクをたどらずに見つかる）に存在するかもしれません。ガードは、
  それぞれに、ワークスペースに尋ねるのと同じ質問をするので、新しいコードのない brownfield
  チェックアウトも通りません。検査が走るときに見つかるチェックアウトは、レビューがそのコード
  変更を見られるところ、つまりソース歩行が AI-DLC 自身の外でその下のファイルを列挙するところ
  だけで数えます。ハーネスフォルダ（Claude Code の `.claude/worktrees/` など）、プロジェクト外、
  または別のドライブに保たれるコードは数えません。なので、作業がそのチェックアウトを記録
  （`intent add-checkout <path>`。エージェントがレビューの前に実行する、またはハーネスフォルダ
  の worktree 内のユニットの主張。レビュー要求時に記録）しない限り、下の行とともに人へ行きます。
  記録されたチェックアウトは、レビューがそれ自身のルートとして歩き、そのファイルを
  `<label>@checkout/<path>` として列挙するので、尋ねられて見つかります。レビュー後のそこの
  変更は stale なレビューです。git は、本物の `.git` エントリを持つフォルダ（人が作ったクローン、
  サブモジュール、init、worktree）でだけ尋ねられます。単にリポジトリの形をしただけのコミット
  されたフォルダは、ファイルシステム検査を得るので、そのコミットされた git config は決して
  走りません。`.aidlc/` の下の AI-DLC 自身の Bolt worktree は、swarm 自身の証拠に委ねられます。
- **コードがコミットされ、その後レコード** - レコードだけの最後のコミットは、ステージで
  以前にコミットされたコードを隠すので、ガードはソースをステージ試行の `Source Baseline` とも
  比較します。ステージが始まって以降の AI-DLC 自身のファイルの外の変更が、ソース作業です。

ガードが、調べたどこにもソース作業を見つけないとき、Guard Policy off は作業を続けさせ、人は
一度「AI-DLC found no source changes under <調べた場所>」と聞きます。strict または relaxed では、
エージェント自身の最初の報告が拒否され、いつも機能する進み方が名指しされます。もう一度報告し、
承認の質問がその行とともに人へ行きます（「If your code is somewhere else, approve as usual; if
it is missing, ask for changes.」）。その人の承認は、それを `Source Work` としてその言葉の隣に
記録します。strict または relaxed では、承認が人のゲート後の返信にならないところ（自律
Construction ゲート、human-presence 検査がオフ、無人の実行）、そしてエージェント自身の
`advance`、`finalize`、`complete-workflow` については、拒否が残ります。各結果は、ステージ試行
ごとに 1 回、`SOURCE_WORK_NOT_FOUND` 行として記録されます。

今日は `code-generation` だけがそれを宣言します。そのユニット単位のレビューはさらに
`<record>/construction/<unit>/code-generation/source-manifest.json` を要します。作成、変更、
削除されたすべてのアプリケーションソースパスの厳格な帰属インデックスです。エンジンは、マニフェスト
のバイトと主張された内容をユニット受領に結び付け、すべての新しいユニットを内容アドレスの
ステージエントリのベースラインと比較し、新しい主張の和集合の外の変わったパスを拒否します。
ディレクトリの主張は後の追加をカバーします。メインの複数リポジトリのワークスペースでは、すべての
エントリがその記録されたリポジトリを名指しします。一方、Bolt のマニフェストは、その選ばれた
1 つのリポジトリに対して相対的です。リポジトリを記録しないワークスペースでは、プロジェクトに
ネストしたチェックアウト（その git が追跡しない worktree やクローン）の中のエントリは、その
チェックアウト自身の git で判定されるので、そのフォルダに対するワークスペースの `.gitignore`
はそれを拒否しません。プロジェクト外のチェックアウトへのリンクやジャンクション経由のエントリ
（`wt-link/src/`、またはその全部には `wt-link/`）も同じで、ソース歩行がそのリンク経由で列挙する
ものをカバーします。作業の記録されたチェックアウトの 1 つの中のエントリも、そのチェックアウトの
git で判定され、その列挙名で鍵付けされます。プロジェクト外のチェックアウトはそのように名指し
され（`<label>@checkout/src/`）、リポジトリを記録する作業でも `repo` なしで、作業が記録して
いない列挙名は、それを記録するステップとともに拒否されます。欠けているアップグレード前の
フィールドは、文書化された移行の証拠としてのみフェイルオープンします。存在するが結び付け
られない、または破壊された現代の証拠は、Guard Policy strict でフェイルクローズします。relaxed
または off では一度記録され、作業は続きます。自分のコードや設定を出すステージ（コントラクト
ジェネレーター、IaC 実行器）を足すチームは、ワークスペースガードが適用されるよう
`workspace_requires: true` を設定すべきです。CI のためには `AIDLC_SKIP_ARTIFACT_GUARD=1` で
それを回避します。その switch は、レビュー時の必須出力存在検査も回避します。ソースの結び付けと
帰属は、`AIDLC_SKIP_SOURCE_FRESHNESS=1` で別途回避します。

### `produces_kinds`

`for_each: unit-of-work` ステージの任意のマップです。各キーはステージの `produces` または
`optional_produces` のアーティファクト名の 1 つ、各値はそのアーティファクトが適用されるユニット
**kind** のリストです。kind は、units-generation のエッジブロックでユニットごとに宣言され
（[Runtime graph](13-runtime-graph.md) の `bolt_dag.units[].kind` を参照）、
`service | spec | ui | packaging | library` のいずれかです。

```yaml
produces:
  - performance-requirements
  - security-requirements
  - scalability-requirements
  - observability-requirements
produces_kinds:
  performance-requirements: [service, ui]
  scalability-requirements: [service]
  observability-requirements: [service]
```

なぜ存在するか: 4 つの construction design ステージは、すべてのユニットに同一に適用される固定の
produces リストで走ったので、spec ユニットがスケーラビリティのドキュメントを、packaging ユニットが
ビジネスロジックモデルを負っていました。人間が書かねばならない N/A のスタブです。`produces_kinds`
は、エンジンがユニットごとにマトリクスを剪定できるようにします。ユニットが `kind` を運ぶとき、
エンジンは、その kind を含む kind リストを持つ produces エントリだけを保ちます。マップに列挙
**されていない**アーティファクトは、すべての kind に適用されます（kind 固有のものだけを注釈
します）。kind の**ない**ユニット、または `produces_kinds` マップのまったくないステージは、
完全なマトリクスを保ちます。なのでこれは、既存のすべてのワークフローで不活性です。

剪定は対称的です。run-stage ディレクティブの `produces` パス（conductor が書くもの）と、ユニット
単位のカバレッジ検査（approve パスのガードが要するもの）の両方をフィルタします。`optional_produces`
と合成されます。ディレクティブのパスは両リストの kind フィルタされた和集合で、カバレッジは必須の
`produces` だけで鍵付けされたままです（任意のアーティファクトは、適用されない kind のために
ディレクティブから剪定され、いずれにせよカバレッジ免除のままです）。必須集合が**空**に剪定される
ユニットは、定義上カバーされています。ステージはそれに適用されません。そして、*すべての*ユニットが
空に剪定されるユニット単位のステージは、アーティファクトガードでデッドロックするのではなく、
no-op として承認されます。4 つのステージの既定の kind マトリクスは、ステージフロントマターの
データで、エントリごとにレビュー可能で元に戻せます。間違ったエントリを削除すると、そのアーティ
ファクトの完全なマトリクスが復元されます。

標準の NFR ステージは、`observability-requirements` と `observability-design` の両方を service
ユニットに対応付けます。

1 つの信頼の注記: `kind:` 値は units-generation ゲートで enum 検査されます（`required-sections`
センサーが綴り間違いで大きく失敗します）が、コンパイル済みのランタイムグラフはその後信頼され
ます。エンジンは、`bolt_dag.units[].kind` を読むとき kind を形状検査するだけです（コンパイル済み
のバッチを信頼するのと同じです）。コンパイル済みのグラフで有効だが間違った kind に手で編集された
ユニットは、その間違った kind の集合に静かに剪定されます。

### `consumes[].required`

consume エントリごとのブール値です。意味的に**アクティブなプランにスコープされ**、アーティ
ファクトがどこかに常に存在するというグローバルな主張ではありません。

> `required: true` は、*「生成側ステージがアクティブなプランで走るなら、この consume は満た
> されなければならない」*を意味します。「生成側が常に走る」を意味**しません**。スコープが
> 生成側を除外するとき（たとえば `bugfix` は `units-generation` をスキップ）、その生成側の
> アーティファクトのすべての `required: true` consume は無意味になります。要するものが
> 何もありません。

**なぜスコープされた読み方か。** `enterprise` と `feature` だけがすべてのステージを実行します。
他のすべてのスコープは、意図的に上流のステージをスキップします。フラットでグローバルな
`required: true` は、それらのスコープを構造上無効にしますが、それは誤りです。それらは正当な
運用モードです。本当のコントラクトは条件付きです。「上流が走るなら、下流に私を供給せよ」。
ステージ本体は、不在のケースをすでに優雅に扱います（「if available」のような散文の指示や、
コンテキストからのフォールバック）。

**doctor lint から見た意味。** lint は各アクティブスコープを歩き、「このスコープ
でアーティファクト Y の生成側が SKIP なので、ステージ X のアーティファクト Y の `required: true`
consume は無意味」と報告します。それは勧告であって、ブロックではありません。ユーザーは、スコープ
を選ぶことで、切り詰めにすでにオプトインしています。

**`when:`（受け入れられるが、まだ評価されない）。** ステージは `when:` 述語を宣言してもかまい
ません。今日、スキーマは `producer-in-plan` だけを受け入れ、その形を検査し、まだ何もそれに作用
しないので、ステージはそれが不在であるかのように `scopes:` の下で走ります。`required: true` +
`conditional_on: brownfield|greenfield` のペアが、エンジンが今日評価する 2 つの次元をカバー
します。`when:` はそれを一般化することを意図しています。

### `consumes[].conditional_on`

brownfield/greenfield の分割を捉えます。例: `reverse-engineering` は brownfield モードでのみ
アーティファクトを生成します。それらのアーティファクトを消費するステージは、スコープリゾルバに
「この consume は brownfield のときだけ必須」と伝えるために、consume を
`conditional_on: brownfield` とマークします。

無条件の consume については、**フィールドを完全に省きます**。`always` 値はありません。無条件の
consume は、単に `conditional_on` キーを持ちません。

### `consumes[].cited`

consume 上の任意のブール値です。`cited: true` は、その入力が存在するときは常に、ステージの
成果物がそれを引用すると言います。`upstream-coverage` 検査は、成果物に、存在する必須の各
consume を引用するよう求めます。任意のもの（`required: false`）は未検査のままにします。任意の
入力は出力に情報を与えていないかもしれないからです。ただし、consume が `cited: true` とマーク
されている場合は除きます。Requirements Analysis は `intent-statement` と `scope-document` を
マークします。両方ともそこでは任意です。Ideation のないスコープはどちらも生成せず、それらが
存在するとき要件はそれらの上に築かれるからです。

コンパイルは、マークされた consume をステージの `cites` として `stage-graph.json` に列挙し、
コンパイル済みの `consumes` エントリをそのまま保つので、1 つをマークまたはアンマークしても、
すでに終わったステージの記録は変わりません。フラグは、トップレベルのリストではなく consume に
座ります。2.8.0 から 2.11.0 のプロジェクトが、独自のツールで新しいリリースに更新し、それが
consume 内のキーを受け入れ、知らないトップレベルのキーを拒否するからです。

```yaml
consumes:
  - artifact: intent-statement
    required: false
    cited: true
```

### `optional_produces`

`produces:` と並行の、素の kebab-case 文字列リストです。ステージがユニットごとに書く**かも
しれない**が、**要求されない**アーティファクトを名指しします。不在はなしを意味します。それを
必要とする 1 つのステージ（`functional-design`、`frontend-components` のため）だけが宣言する
ので、コンパイル済みの `stage-graph.json` は最小限のままです。

なぜ存在するか: ユニット単位の Construction ステージ（`for_each: unit-of-work`）は、すべての
`produces[]` アーティファクトがそのユニットの記録ディレクトリの下にディスク上に存在するときだけ、
ユニットについて COVERED です（`aidlc-orchestrate.ts` のユニット単位のカバレッジ検査）。一部の
アーティファクトは、真にユニットに条件付きです。`functional-design` は、ユニットが UI を持つ
ときだけ `frontend-components` を書きます。それを `produces:` の下に列挙することは、バックエンド
だけのユニットに、カバレッジを満たすためだけに N/A のスタブを書くことを強い、それをするまで
ステージゲートを到達不能にしました。それらを `optional_produces:` に移すと、それらを免除します。

- **カバレッジ免除。** `optional_produces` エントリは、ユニット単位のカバレッジループに無視
  されます。ユニットは、その**必須**の `produces[]` アーティファクトが存在すればカバーされます。
  任意のものは、`next` の進行や `approve` のコミットを決してブロックしません。
- **やはり conductor には解決されます。** run-stage ディレクティブの `produces` パスは
  `produces` + `optional_produces` を和集合にするので、ユニットが条件付きのアーティファクトを
  書く*とき*、conductor はそれがどこに着地するかをやはり知ります。ステージが `produces_kinds`
  も宣言するとき、その和集合は解決される前に kind フィルタされます（上の `produces_kinds` を
  参照）。なので、任意のアーティファクトが適用されない kind は、そのパスを決して見ません。
- **やはり語彙にあります。** `artifactsRegistry()` と `producersOf()` は両リストを和集合に
  するので、アーティファクト名とその生成側ステージは登録されたままです。

**ペアリングの慣習。** すべての `optional_produces` エントリは、ステージ本体の散文（と
`outputs:` 文字列）に、いつそれを書くかをエージェントに伝える `(CONDITIONAL - ...)` マーカーを
持た**なければなりません**。フロントマターキーはエンジンのカバレッジビューです。散文はエージェント
の指示です。それらを同期させてください。

**警告。** `optional_produces` とマークされたアーティファクトは、ユニット単位のカバレッジ台帳に
不可視です。エンジンは、ユニットがそれを生成したことを証明できません。真にユニットに条件付きの
アーティファクトにだけそれを使い、ステージがユニットごとに常に書くべきアーティファクトのカバレッジ
を静かに緩めるために決して使わないでください。

### `mode`

ステージの**通信トポロジー**。本体が走る間、誰が誰と話すかです。5 つの値、4 つがアクティブです。

- `inline` — conductor が自分のコンテキストでステージを走らせます。サポートエージェントは、それが
  採用する視点（声）です。ディスパッチはゼロです。短いステージ、速く実行でき、コンテキストの
  圧力なし。
- `subagent` — ハブアンドスポーク。リードが新しいサブエージェントのコンテキストにディスパッチ
  されます（conductor のコンテキストを吹き飛ばすような長いステージ、たとえば Construction の
  コード生成）。ステージが `support_agents` も宣言するとき、それぞれがリードの返したドラフトに
  対して本物のスポークとしてディスパッチされ（互いに盲目のブリーフが、アーティファクトをパスで
  運び、ステージのルールを `stage-protocol.md` § "For subagent stages" step 2 に従って配信）、
  リードがもう一度ディスパッチされて統合します。
- `pipeline` — チェーン。リードがドラフトを作り、各サポートエージェントが宣言された順序で豊かに
  し、すべてのリンクがドラフトと以前のすべての貢献を見ます。順序が要点です。空でない
  `support_agents` を要し、リードとサポートチェーンにわたるすべてのエージェントが一意でなければ
  なりません。
- `mob` — メッシュ。上限付きのラウンドとして走ります。すべてのサポートエージェントがリードの
  ドラフトに対して並列に貢献し（互いに盲目）、リードが統合し、未解決の反対者が、他の参加者の
  立場とともに confirm-or-maintain のラウンドを 1 回得ます。維持された反対は、ゲートで原文の
  まま引用されます。空でない `support_agents` を要します。出荷されるショーケースは
  `user-stories`（Product Manager のリード。Design、Developer、Quality の協力者。Product Lead の
  レビュアー — mob 精緻化の儀式）です。
- `agent-team` — **予約**。メッシュ協調の将来のネイティブバストランスポートです。Anthropic の
  実験的な `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` プリミティブが安定すると、ライブのピア
  メッセージングルームが、conductor が運ぶラウンドなしに `mob` の意味を運べます。`mob` が
  移植可能なモードです。どのステージも `agent-team` を宣言しません。

すべてのトポロジーで、conductor がバスです。エージェントは互いを呼ぶことは決してありません。
conductor だけが委譲します。書き込みモデルは、本物の作業セッションをミラーします。誰もが自分の
作業を書き、オーナーが照合して編集します。ディスパッチされた各サポートエージェントは、貢献
ファイル（`contributions/<agent-slug>.md`、identity マーカーが最初の行の `stage-protocol-collaborators.md`
の形）を書きます。リードだけがステージの `produces[]` アーティファクトを編集します。pipeline の
リンクは、代わりにアーティファクトを直接進めます。mob とサポート付き subagent のステージでは、
貢献ファイルが完了の証拠です。1 つでも欠けていると、エンジンは承認を拒否します。レビュー
ループはモードでは**ありません**。`reviewer` + `reviewer_max_iterations` が、任意のモードの上に
2 者の批評トポロジーを届け、NOT-READY はリードだけを再び呼びます。

**消費側のコントラクト。** `mode` フィールドを読むオーケストレーターコードは、`agent-team` を
明示的に扱わなければなりません。最低限「mode agent-team not yet implemented」を投げます。既定の
実行パスにフォールスルーしないでください。enum 拡張での静かなフォールスルーは、既知の罠です。

**swarm トリガーの結合。** 自律 Construction swarm は、`for_each: unit-of-work` + `mode: subagent`
で発火します。ユニット単位のビルドステージをモード変更すると、静かにそれを swarm パスから外し
ます。`aidlc-graph compile` は、その形を見ると stderr の勧告を出します。

### `lead_agent` と `support_agents`

リードエージェントがステージを所有します。リードのペルソナ（スキル、ナレッジ、ツール許可リスト）
はステージ開始時に読み込まれます。サポートエージェントは視点を足します。ステージは、要件作業で
`aidlc-product-agent` をリードにしつつ、キャパシティの現実チェックのために `aidlc-delivery-agent`
をサポートとして読み込むかもしれません。

両フィールドとも、アクティブなハーネスのエージェントディレクトリを読む `loadAgents()` 経由で、
`.claude/agents/*.md` に対して動的に検証されます。`aidlc-graph.ts compile` は、発見された
エージェントスラッグを `validateStageFrontmatter` に渡すので、一致するファイルのないエージェントを
名指しする `lead_agent` または `support_agents` の値は、実行時に未登録サブエージェントの `Task`
エラーとして現れるのではなく、コンパイルを大きく失敗させます
（`lead_agent "<name>" has no matching .claude/agents/*.md`）。1 つの免除は、予約された
`orchestrator` 擬似エージェント（conductor 自身。ブートストラップ初期化ステージで `lead_agent`
として名指しされる）です。設計上、エージェントファイルを持ちません。スキーマにハードコードされた
enum はありません。エージェントを足すことは、その `.md` ファイルを必須のフロントマターとともに
`.claude/agents/` に置くことを意味します。[Contributing: Adding an Agent](11-contributing.md#adding-an-agent)
を参照してください。pipeline ステージはさらに、チェーンの他の場所で繰り返されるサポート
エージェント（サポートとして繰り返されるリードを含む）を拒否します。リンク受領が、宣言された
1 つの位置を、その一意のエージェントで識別するからです。

### `reviewer`、`review_artifact`、`reviewer_max_iterations`、`review_class`

任意。`reviewer` は、ステージ本体がそのアーティファクトを生成した後、承認ゲートの前に呼ばれる
品質ゲートエージェントを名指しします（[Stage Protocol](04-stage-protocol.md) を参照）。今日
2 つのレビュアーが出荷されます。`aidlc-product-lead-agent` と `aidlc-architecture-reviewer-agent`
です。コンパイルは、`lead_agent` が検証されるのと同じく、発見されたエージェントロスターに対して
値を検証します。

すべてのレビュアーを伴うステージは、`produces[]` の 1 つの必須 Markdown エントリ、つまりレビュー
の対象となるアーティファクトを名指しする `review_artifact` も宣言しなければなりません。レビュー
記録はそれに鍵付けされ、ゲートはそれを名指しし、`--reject-finding` / `--reopen-finding` /
`--fix-finding <artifact>#R-NN` がその指摘にアドレスします。レビュアーはそれに決して書きません。
リストの順序やプラグインが足した出力は、それを変えられません。ユニット単位のステージでは、
ターゲットは、いずれかの必須出力が適用されるすべてのユニット kind に対して適用可能なまま
でなければなりません。さもないとグラフコンパイルが失敗します。`traceability.json` のような
構造化出力は、レビューのターゲットにできません。

`reviewer_max_iterations` は、ワークフローが未解決の指摘とともにゲートへ進む前の、レビュー／改訂
ループに上限を定めます。`reviewer` が宣言されているが上限が与えられないとき、**既定で 2** です。
与える値は正の整数でなければならず、他の値はコンパイルの前にスキーマ検証に失敗します。
`reviewer` を宣言しないステージではフィールドを省きます。コンパイラは、`reviewer` なしで宣言
された `reviewer_max_iterations` を拒否します（スキーマエラー `reviewer_max_iterations requires
a reviewer` がグラフコンパイルを失敗させます）ので、静かに無視されることは決してありません。

`review_class` は、レビューのコントラクトを選びます。`adversarial`（上の refute-and-repair
ループ。`reviewer` がクラスなしで宣言されたときの既定）か、`advisory`（1 回の通常フローのパス。
その指摘を、人間の承認ゲートがエンジン所有の指摘リストから示す。修復ループなし。有効な反復
予算は 1）です。その終端受領を無効にする後の書き込みは、次の序数で 1 回の上限付き復旧要求を
許します。人が求めるレビューは決して拒否されません。出荷される分割: 8 つの人間ゲートの
ideation/inception 散文ステージは `advisory` を宣言します。5 つの Construction design/build
ステージは既定で `adversarial` です。`none` は意図的にステージの値ではありません。レビューを
望まないステージは、その `reviewer:` 行を削除します。`none` は、スコープの `review_cap` と
実行ごとの `--review` 上書きに存在し、ステージを編集せずに宣言されたレビュアーを黙らせられます。
ランタイムでの有効なクラスは、ステージ宣言を 1 つの天井で下げたものです。設定されているとき
作業ごとの `--review` 上書き、さもないとアクティブスコープの `review_cap`（出荷される `bugfix`、
`poc`、`classic`、`workshop` のスコープは `advisory` に上限を定め、`express` は `none` に上限を
定めます）。天井はクラスを下げられますが、ステージの宣言を超えて上げることは決してありません。
作業に設定された上書きはスコープの天井を置き換えるので、上限を定めたスコープでの
`--review adversarial` は、各ステージ自身のクラスを走らせます。自律 swarm のレビューは、上限と
上書きから免除されます。Bolt の中では、レビュアーが唯一のマージ前検証なので、宣言されたクラスが
常にそこで適用されます。上限と同じく、`review_class` は `reviewer` を要します（スキーマエラー
`review_class requires a reviewer`）。

スコープフロントマターは、5 つの ceremony スイッチ、それぞれ `on` | `off` も受け付けます
（不在は on を意味します。ただし `collaborators` は `enterprise` でのみ on で出荷されます）:
`sensors`、`learnings`、`summary_confirmation`、`plan_approval`、`collaborators`（off は
すべてのステージをリードだけで走らせます。レビュアーは影響を受けません）。最後のものは、ステージ
の `summary_confirmation: required | if-present` とは別です。スコープ／インテントの方針が、その
チェックポイントがそもそも適用されるかを決めます。`/aidlc --sensors on|off`、
`/aidlc --learnings on|off`、`/aidlc --summary-confirmation on|off`、`/aidlc --plan-approval on|off`
は、インテントのスコープ既定を上書きします（プラン承認をオフにするのは人だけです）。
`AIDLC_DISABLE_SENSORS=1`、`AIDLC_DISABLE_LEARNINGS=1`、`AIDLC_DISABLE_SUMMARY_CONFIRMATION=1`、
`AIDLC_DISABLE_PLAN_APPROVAL_GUARD=1` は、それぞれの ceremony をオフに強制します。classic は
センサー、learnings、プラン承認を有効にし、サマリー確認を無効にします。bugfix は learnings と
サマリー確認を無効にします。express と poc はプラン承認を無効にします。各コードプランを尋ねず
に作るプラン承認オフを除き、ステージ承認、human-turn 権限、監査、チーム書き込み保護は有効な
ままです。

### `ars`

任意。ステージの**composer 選別の事前情報**。`tools/data/ars-priors.json` の 1 エントリと同じ
4 つの事実を、ステージ自身のフロントマターに書いたものです。

```yaml
ars:
  targets: [ve, r]            # ARS components the stage reduces: iae | csu | ve | r | ua
  cost: 4                     # 1 (trivial) .. 5 (heavy); null = never numerically screened
  role: structural            # optional: initialization | core | phase-gate | structural
  project_types: [brownfield] # optional: mirror a condition: that restricts the project kind
```

リストはインライン（`[a, b]`）です。ブロックは次のトップレベルキーまで走るので、その中の空行と
`#` コメント（末尾のものを含む）は許されます。

なぜ存在するか: `aidlc-graph ars`（[CLI commands](../guide/12-cli-commands.md) を参照）は、各
ステージの EXECUTE/SKIP を、コストの事前情報とそれがターゲットにするコンポーネントから選別
します。出荷される事前情報はコアステージだけを名指しし、プラグインはそのファイルを編集できない
ので、プラグインステージは、composer が判断でしか決められない `no-prior` 行として着地していました。
スキーマは、事前情報ファイルのエントリと同じくブロックを検証し、`aidlc-graph compile` はそれを
ノードにコピーし、`ars` サブコマンドは、ファイルエントリとまったく同じくそれを選別します。
`role: core` は常に実行し、`structural` と `null` のコストはゲートでの判断に委ねられ、
`project_types` は他のプロジェクト種別でステージを選別外にし、`--completed` ステージはすべてに
勝ります。事前情報ファイルには、ステージブロックが宣言できない 1 つの役割、`project-type`
（Reverse Engineering）があります。スコアが何であれ、自分のプロジェクト種別でステージを走らせる
ので、その種別では、プラグインステージの `project_types` はやはりそのコンポーネントによります。

3 つのルールが選別を予測可能に保ちます。

- **事前情報ファイルが勝ちます。** スラッグがファイルエントリと `ars:` ブロックの両方を持つとき、
  ファイルエントリが使われるので、ステージ側の編集でコア選別が変わることは決してありません。
  コアステージは `ars:` を宣言しません。
- **空の `targets` は機械的に実行されません。** 数値コスト付きの `targets: []` は合法ですが、
  `role` なしでは何も閾値を越えられません。行は SKIP で、そう言う理由が付きます。
- **コストには閾値がなければなりません。** `cost` は composer ペルソナの `1..5` スケールに
  とどまります。`aidlc-graph ars` は、値が読み込んだ事前情報ファイルに `evThresholds` エントリを
  持たないとき、ステージを名指しして exit 1 します。

各選別行の `priorSource`（`shipped`、`stage`、`null`）が、その事前情報がどこから来たかを言います。

## エージェントフロントマターとの関係

ステージとエージェントは、同じ YAML 優先の規律に従います。エージェントフロントマター
（[Agent System](05-agent-system.md#frontmatter-contract) を参照）は*誰か*を宣言します。
エージェントの名前、許されるツール、層です。ステージフロントマターは*何か*を宣言します。
ステージがどのアーティファクトを生成し消費するか、どのエージェントに委譲するか、どう実行するか
です。

両方の形式は:

- そのドメインの権威ある情報源です（並行してハードコードされたマップはありません）。
- 型付きの構造を返す `loadX()` ヘルパーとともに出荷されます。
- ハードコードされた enum ではなく、ファイルシステムに対して動的に検証します。

新しいステージを足すことは、新しいエージェントを足すのと同じ形です。`.md` ファイルを置き、必須の
フロントマターを足すと、ヘルパーがランタイムにそれを拾います。

## ワークサンプル

正規の例は `scope-definition` です。規範的な YAML ブロックは
`core/aidlc-common/protocols/stage-definition.md` に存在します。ここで重複させるのではなく、
そこを参照してください。

例は、構造化された形で、今日の散文が説明するものをエンコードします。

- `requires_stage: [intent-capture]` は、散文の指示「intent statement をインテントの
  `ideation/intent-capture/`（その記録ディレクトリの下）から読む」をエンコードします。パーサーは
  散文を気にしません。グラフのエッジを見るだけです。しかし人間の読み手は、それらを同期させる
  べきです。
- `consumes: [{artifact: intent-statement, required: true}]` は、このステージが
  `intent-statement` が存在するまでブロックされると言います。スコープのリゾルバが
  `intent-statement` の生成側を見つけられないと、doctor の生成元欠落検査が失敗します。
- `produces: [scope-document, intent-backlog, scope-definition-questions]` は前方のエッジです。
  「誰が `scope-document` を生成するか」を探す他のステージが、`aidlc-graph.ts producersOf()`
  経由でこれを見つけます。
- `for_each` フィールドなし。`scope-definition` はワークフローごとに 1 回走ります。

## 3 区画の本体モデル

ステージファイルの本体には 3 つの区画があり、この順序で宣言され、出荷されるすべてのステージが
3 つすべてを埋めます。

| 区画 | ここに入るもの |
|-------------|----------------|
| `## Steps` | エージェントが従う命令形の散文 |
| `## Sensors` | コンパクトな出力場所、インポートされたセンサー、上流ターゲットの要約。ステージ固有の例外はローカルに残る |
| `## Learn` | 共有の section 13 学習ループコントラクトとそのブートストラップ例外へのコンパクトなポインタ |

固定の順序は、ステージのセンサー結び付きと学習ループのポインタが、常に自分自身の場所を持つ
ことを意味します。`## Sensors` の結び付きの意味と pull インポートのモデルについては
[Sensor System](07-sensor-system.md) を参照してください。共有のセンサーの振る舞いは
`stage-protocol-sensors.md` で一度定義されます。一方 `stage-protocol-learnings.md` の section 13
は、`directive.protocol_modules` が `learnings` を列挙するときだけ日記と儀式を定義します。
さもないと両方をスキップします。`## Sensors` と `## Learn` の見出しは、33 ステージすべてにわたって
`t87-stage-compartment-headers` が検査します。`## Steps` はすべてのステージにありますが、独自の
テストは持ちません。

## パーサーとエミッター

`parseStageFrontmatter` と `emitStageFrontmatter` は `core/tools/aidlc-lib.ts` に存在し、YAML
のみです。`bun scripts/package.ts` がすべての生成ツリーに対して実行する `aidlc-graph.ts compile`
が、YAML を `stage-graph.json` にコンパイルします。リポジトリは、無視されるプロジェクションの
中でのみそのファイルを生成します。コミットされたコンパイル済みファイルのドリフト検査ではなく、
パッケージの決定性が、ソースツリーのゲートです。

## 既知の限界

- **`for_each` は Construction だけが使います。** 5 つのユニット単位の Construction ステージが
  `for_each: unit-of-work` を宣言します。他の 28 ステージはフィールドを省きます。
- **`when:` は受け入れられますが評価されません。** 上のフィールド注記を参照してください。
- **コンパイルで検証されるのはフロントマターだけです。** 本体の散文はパースされません。その
  `## Sensors` と `## Learn` の見出しはテストスイートが検査し、エンジンのランタイムガード
  （たとえばステージの必須作業の完了検査）は、その散文ではなく、ステージが生成するものに作用します。

## 将来の拡張 — 予約された名前空間

仕様は、AI-DLC がおそらく後のリリースで足すプリミティブの名前を予約します。スキーマは未知の
キーを拒否します。ここで名前を予約することで、将来の貢献が場当たり的な追加と衝突するのを防ぎます。

| キー | 予約先 | それが何をするか |
|-----|--------------|------------------|
| `on_failure` | ループドライバー | 宣言的なエラー復旧: 「このステージが失敗したら X に戻る」や「調整した入力でリトライ」。改訂の意味を `stage-protocol-recovery.md` の散文の外に移す |
| `blocks_on` | Construction の worktree | データ読み取りなしの完了依存: 今日の過負荷の `requires_stage`（「あなたの出力を消費する」と「あなたの後に走る」を混同する）を分割する |
| `timeout` | センサー結び付き | 実行予算（デッドライン）。ステージフロントマターではなく、センサー結び付きに置く |
| `retry` | ループドライバー | 失敗時のリトライ方針。ステージフロントマターではなく、ループ設定に置く |

`when` はもう予約されていません。スキーマは `producer-in-plan` 述語でそれを受け入れ、その形を
検査します。その評価はまだ来ていません（上の `consumes[].required` を参照）。

設計の根拠: Claude Code 自身のタスクプリミティブ（TaskCreate ファミリーと `/loop`、cron）は、
依存、ブロック、リトライ、タイムアウトを省きます。すべての複数ステップのオーケストレーションは
クライアント側のコードに押し出されます。この実装はその選択をミラーし、実行の振る舞い
（リトライ、タイムアウト、失敗処理）を、ステージ仕様ではなく、ループとセンサーのサブシステムに
置きます。上のフィールドは、消費側が現れれば、新しいパラダイムではなく、控えめな構造拡張に
なるでしょう。

予約された名前空間のパターンは、監査分類（[State Machine](12-state-machine.md)）に先例があります。
それは、イベントを出すコードが出荷されるまで、`Reserved` の Emitter セルでイベント名を事前登録
でき、廃止された名前を `Reserved (retired name)`（今日は `CHANGE_CONTROL_SET`）として保ちます。
