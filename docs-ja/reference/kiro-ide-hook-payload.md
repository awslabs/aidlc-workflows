# Kiro IDE フックペイロード — 実測リファレンス

Kiro IDE がコマンドフックへどのようにコンテキストを渡すかを、0.12-main（stdin、argv、環境全体をダンプするプローブ `.kiro.hook` ファイル）、1.0.165（プローブ v2 フック JSON ファイル。上流の #543/#555）、1.0.242（Windows 上の UserPromptSubmit と PreToolUse のプローブ）でライブに記録したものです。これは `harness/kiro-ide/` アダプターの根拠となる証拠です。CLI ハーネス（`harness/kiro/`）は、kiro-cli の形をした別の stdin 機構を使います。

編集済みのネイティブ Windows の before/after キャプチャは、[`research/kiro-windows-output-encoding/`](research/kiro-windows-output-encoding/) に保持されています。

## チャネルは IDE の世代ごとに変わった

| | Kiro IDE 0.12 | Kiro IDE 1.x (≥1.0.1xx) |
|---|---|---|
| フックの登録 | `.kiro/hooks/*.kiro.hook`（`{"version":"1.0.0","when":{...},"then":{...}}`） | `.kiro/hooks/*.json` の v2 スキーマ（`{"version":"v1","hooks":[{name,trigger,matcher,action}]}`、PascalCase のトリガー）。レガシーの `.kiro.hook` ファイルは**静かに無効化**され、決して実行されません。 |
| コンテキストチャネル | `USER_PROMPT` 環境変数（JSON 文字列） | **stdin**（JSON、書き込まれてクローズされる）。`USER_PROMPT` は空で届きます。 |
| stdin の挙動 | 開かれるが書き込み／クローズは決してされない — 素の read はハングする | 書き込まれてクローズされる — read はすぐに解決する |
| フィールドの命名 | camelCase: `{ toolName, toolArgs, toolResult, toolSuccess }` | snake_case: `{ session_id, hook_event_name, cwd, tool_name, tool_input, tool_response }` — **success フラグなし** |

ライブの 1.0.165 PostToolUse キャプチャ（フィールドはそのまま）:

```json
{"session_id":"sess_…","hook_event_name":"PostToolUse","cwd":"/path/to/project","tool_name":"execute_bash","tool_input":{},"tool_response":"Output:\n…\nExit Code: 0"}
```

アダプターは、空でない `USER_PROMPT` をただちに使います（0.12 のチャネルで、その stdin は決してクローズされません）。その変数が空のときは、1.x のチャネルのために Kiro がクローズするまで stdin を読むので、Kiro が遅れて渡すメッセージ（ビジーなマシン）でも丸ごと読めます。Kiro 自身のコマンドフックのデフォルト予算である 60 秒という安全上の上限は、決してクローズしないチャネルだけを終わらせます。正の `AIDLC_IDE_STDIN_TIMEOUT_MS` の値は、診断とテストのためにミリ秒単位でそれを上書きします。どちらのチャネルにも何もないまま上限を過ぎると、`record-human-turn` はターンもメッセージも記録しません（人が何も入力しなかったとは記録に残らず、Kiro 自身のものかもしれないメッセージに presence は発行されません）。`kiro-adapter.drops` の行が `doctor` 向けにそれを示し、エージェントは人へ伝えるための 1 行を得ます。「このチャットの最後のメッセージが AI-DLC の記録に届きませんでした。もしそれが質問の 1 つに答えていた場合、その質問が改めて尋ねられます」（誰が送ったかにかかわらず真です。ペイロードがなければ、それが人のものか Kiro が作ったものかは誰にもわかりません）。どちらのフィールドのつづりも受け付けられます。取得は、ペイロードに依存するターゲットに限定されます。これには `plan-approval-guard`、`review-freeze`、`state-transition-guard`、2 つのターミナルコマンドターゲット、さらに新しい `session_id` を得るための `session-start` と `continue-workflow`、そして正確な承認応答を得るための `record-human-turn` が含まれます。ほかのすべてのターゲットはどちらのチャネルにも触れず、ゼロレイテンシーのパスを保ちます。

レガシーの環境変数名は、生のユーザーテキストを意味しません。実測された 0.12 の契約は camelCase の JSON です。したがって `prompt` フィールドを持たない promptSubmit ペイロードは、レガシーのターンクロックだけを進めます。ターミナルユーティリティは、後に対応する preToolUse イベントの `toolArgs.command` から認識されます。生の `/aidlc ...` テキストは、それを直接公開する新しい Kiro の世代では引き続き受け付けられますが、0.12 の互換性の主張ではありません。

`VSCODE_IPC_HOOK` ／ `VSCODE_PID` は、IDE のフックプロセスにも存在します（CLI にはありません）。エージェント自身のシェルコマンドはどちらも持たず、`TERM_PROGRAM=kiro` と `KIRO_SESSION_ID` を持ちます（Kiro IDE 1.2.37、#2167 で実測）。これが、エンジンの「answer was not recorded」の行とその hooks-off のステップが、自分が Kiro IDE の中にいると知る方法です。別の `TERM_PROGRAM`（VS Code のターミナル内の Kiro CLI は `vscode`）は、VS Code 自身の `VSCODE_PID` の隣にあっても Kiro IDE を除外します。レガシーの Plan Approval は、それらの実測されたホストインスタンスの値をランタイムのセッション同一性にハッシュ化するので、1 つのワークスペース内の 2 つの IDE ウィンドウは challenge/response ファイルを共有しません。ほかのアダプターのルーティングは、依然として上記のペイロードチャネルをキーにします。

## イベントごとのキャプチャ

結果の散文は、どちらのチャネルでも同一です（0.12 では `toolResult`、1.x では `tool_response`）。

| イベント | ツール名 | ツール入力 | 結果の散文 | 復元可能か |
|-------|-----------|-------------|--------------|--------------|
| UserPromptSubmit (1.0.242) | n/a | `{prompt:""}` | n/a | prompt: 不可。session id: 可 |
| UserPromptSubmit (1.2.37, Workflows on) | n/a | 人のメッセージにも、Kiro 自身のものにも `{cwd, hook_event_name, prompt, session_id}`。ワークフロー作成者の `<original_user_request>` ブリーフ（チャットの session_id）、各ステップのブリーフ（ステップ自身の session_id。環境変数 `KIRO_SESSION_ID` はチャットのものにとどまる）、`A workflow you launched (...) completed. ...` の完了通知（チャットの session_id。Kiro の記録はそれを `syntheticUserMessageReason: agent-initiated-prompt` と印づける） | n/a | 誰が送ったか: 記録またはその文から（後述） |
| PreToolUse (shell, 1.0.242) | `execute_pwsh` | `{command,cwd,run_in_background,timeout}` | n/a | command: 可 |
| PostToolUse (write) — create | `fs_write` | `{}`（空） | `Created the <PATH> file.` | path: 結果の散文からのみ |
| PostToolUse (write) — edit | `str_replace` | `{}`（空） | `Replaced text in <PATH>` | path: 結果の散文からのみ |
| PostToolUse (write) — append | `fs_append` | `{}`（空） | `Appended the text to the <PATH> file.` | path: 結果の散文からのみ |
| PostToolUse (shell) | `execute_bash` | `{}`（空） | `Output:\n<stdout>\n\nExit Code: 0` | command: 復元**不可**（stdout のみ） |

UserPromptSubmit が入力されたフェンスや Guard Policy の切り替えを運ぶとき、アダプターはそれをコアの human-turn フックへ転送します。コアのフックはそのメッセージをペイロードのセッションの下に記録し、何も適用しません。エージェントは `next` が指定するセッターを実行し、シェルのセッターはアダプター内では実行されません。

人の入力が `/aidlc` 単独、または `/aidlc` に続けて単語だけ（エンジンが取るフラグや動詞がない）で、かつこのチャットのワークフローにまだ記録がないとき、`verb-intercept` メンバーは最初のステップ `engine orchestrate next` を名指す 1 行のコンテキスト行を出力します。これにより、aidlc スキルを自らの判断でのみロードする Kiro の Default エージェントが、その行に自分で答える代わりに AI-DLC を開始します。エンジンの `next` は、記録された行を読みます（takePersonsOwnLine）。プラン名だけを入力した場合（`/aidlc bugfix`）も、`engine orchestrate next <plan>` を名指す同じ行が付きます。素の `next` は単独で名指されたプランを読まないためで、これは aidlc エージェントのスキルがそのために取るステップです。そのステップは、作業が何のためかを尋ねます。メンバー自身が実行するユーティリティ（`/aidlc --status`）、フラグ付きの行、`/aidlc-<runner>` のエントリ、普通の単語、チャットのワークフローが記録済みのときに入力された単語（その場合、素の `next` は作業の続行となり記録された行を読みません。ステージの未解決の質問への素の返信は別で、aidlc エージェントのスキルがその単語を自分で渡します）には、そのような行は付きません。

メンバー自身が実行するユーティリティではない `/aidlc` の行で、かつチャット自身の記録（`~/.kiro/sessions/<workspace>/<session>/session.json`、ペイロードのセッション）が `agentMode` を `vibe` または `default-v2` と示すとき（Kiro の Default と Default v2 のエージェントで、Kiro は各 AI-DLC コマンドの承認を人に求めます）、`verb-intercept` メンバーはチャットごとに 1 回（チャットのターミナルフォルダ内の `default-agent-noted` マーカー）、エージェントが人に伝えるための行も出力します。チャットが Kiro の Default エージェント上にあり、エージェントメニューで aidlc を選ぶと、AI-DLC 自身のコマンドに対するそれらの承認カードが止まる、という内容です。ほかのエージェント上や、読み取れる記録がないときは何も言いません。人が AI-DLC のコマンドに Always allow を選んだときも何も言いません。それは、Kiro の `permissions.yaml` または `permissions.json`（`~/.kiro/workspace-roots/<workspace>/`（This workspace）または `~/.kiro/settings/`（All workspaces）配下）で、パターンが `<invoke> engine orchestrate next` をカバーする素の `{capability: shell, effect: allow, match: [...]}` ルールです。それらのファイルは読まれるだけで、決して書かれません。

Kiro が作ったプロンプトは人のターンではありません。Kiro 自身のチャット記録（`~/.kiro/sessions/<workspace>/<session>/messages.jsonl`、ペイロードのセッション）が `_meta.kiro.syntheticUserMessageReason` で印づけるメッセージ、または Kiro が印をつけないまま残す Workflows のブリーフ（その冒頭の文が丸ごとアンカーされていることで判別される）は、`origin: {kind: "host"}` で転送されます。コアのフックは `HOST_TURN` を記録し、人のものは何も記録しません。アダプターはそれに対してセッションを開始せず、チャットを覚えず、ターンを開きません。チャットのターンがいったん閉じると、ターミナルコマンドの同一ターンの保留を終わらせます（後述）。記録が `_meta.kiro.userMessageTag` でタグづけするメッセージは、その言葉が何であれ人のものです。未知のものはすべて同様で、これにはチャットの `KIRO_SESSION_ID` と異なるペイロードの `session_id` 単独も含まれます（その変数は、ステップのプロンプトに対してもチャットを名指していたので、メッセージがどのタブから来たかを名指すとは限りません）。

IDE 1.0.242 のような空プロンプトのビルドでは、ターンごとの `prompt-empty` マーカーにより、アダプターはシェルコマンドの引き下げを拒否します（stderr とともに exit 2）。これには環境変数を前置した呼び出しとサマリー確認 `off` が含まれ、`verb-intercept` はセッションに 1 回の capability note を出し、そのビルドではアクティブな作業を引き下げられないと説明し、プロンプトに対応した IDE への更新か、より低いデフォルトスコープからの新しい作業の開始を人に促します。サマリー確認とプラン承認については、どちらも、作業の実行中にも効く人のプロジェクト全体のターミナルコマンド `<invoke> config flags --bypass AIDLC_DISABLE_SUMMARY_CONFIRMATION --local --yes` または `--bypass AIDLC_DISABLE_PLAN_APPROVAL_GUARD`（`--clear-bypass` が取り消す）も名指します。`strict` への引き上げ、フェンスやサマリー確認の `on` への切り替えは、引き続き利用できます。

空プロンプトを転送する前に、アダプターは、引退した `Change Control: relaxed|off` の行が唯一ある場合、その値やソースラベルを変えず、ポリシー監査行も付けずに、自動で `Guard Policy` へ改名します。一部のビルドはコアのフック出力を捨てるので、移行の注記は自分で出力します。

### 重大な制限

1. **PostToolUse の write/shell キャプチャは、どちらのチャネルでもツール入力が空です**。したがって、書き込まれたパスは結果の散文から解析しなければならず、シェルコマンドは欠落します（stdout + 終了コードだけが存在します）。これは普遍的な IDE のルールではなく、配信は世代をまたいで一様ではありません。後の 1.x のビルドは、一部の PreToolUse と委譲の入力を埋めます（#543）。Issue #763 は、Kiro IDE 1.0.309 が PreToolUse のサブエージェントディスパッチに `prompt` と `explanation` を、shell/write のマッチャーに `command`、`cwd`、`run_in_background`、`timeout` を、そして PostToolUse の入力も埋めたと報告しています。その 1.0.309 の観測は、このリポジトリで実測したものではなく報告されたものです。実測の基礎は、上で述べた 0.12、1.0.165、1.0.242 のキャプチャと、下の「ツール呼び出しのブロック」にある 1.1.14 の PreToolUse キャプチャです。
2. **1.x は success フラグを運びません。** 0.12 チャネルの明示的なブール値 `toolSuccess: false` だけが、整形された書き込みを監査から外します（#417）。フィールドが欠落した 1.x のペイロードは、パスのチェックへ落ちていきます。そのチャネルは失敗を構造的に報告できないので、1.x での失敗した書き込みはエラーの散文としてのみ届きます。そこでアダプターはログ記録の前に分類します。失敗と認識された散文は `hookDebug`（フックのデバッグが有効なときだけ書かれる）へ送られます。監査する成果物がないので、転送しないのが正しく、劣化ではありません。認識されない表現は、依然として目に見える hook-drop を記録します。それが本当の劣化を知らせるケースです。レガシーの 0.12 チャネルでは、明示的な `toolSuccess: true` は依然として決定的で、失敗散文の推論を迂回します。null でない値を持つが実行時の型が誤っているペイロードフィールドは、不正形式として扱われます。advisory フックは成功で終了し、目に見える drop を記録し、監査やサブエージェントのイベントを転送しません。`null` は、利用できないフィールドと同じように扱われ、そのチャネルの既存の「値なし」の契約に合致します。
3. **結果の散文内のパスはワークスペース相対です**が、コアのフックは絶対的な記録ルートと比較します。そこでアダプターは、転送の前にそれらを絶対パスへ解決します。

### ツール呼び出しのブロック（PreToolUse）

Kiro IDE 1.1.14（Windows）で、`execute_pwsh` と `fs_write` のプローブフックを使ってライブに実測しました。

| フックの出力 | ツール呼び出し | モデルが受け取るもの |
|-------------|-----------|-------------------------|
| reason を stderr に、exit 2 | Kiro の承認カードより前にブロック | stderr のテキストが、Kiro の「Tool ... was intercepted by PreToolUse hooks before execution」メッセージの中に入り、ツールは実行されなかったと示す |
| reason を stdout に、exit 2 | 承認カードの後に実行される | フックからは何も届かない |
| stdout と stderr、exit 2 | ブロック | stderr のテキストのみ |
| reason を stderr に、exit 1 | 実行される | フックからは何も届かない |
| `{"decision":"block","reason":...}` または `hookSpecificOutput.permissionDecision: "deny"` を stdout に、exit 0 | 実行される | フックからは何も届かない |

したがって、拒否は理由全体を stderr に置いて exit 2 しなければなりません。ツール呼び出しを拒否するすべてのアダプターのルートはそうしており、転送されたコアのフックの stderr は、それが exit 2 するときに中継されます。PreToolUse フックの stdout は決してモデルに届きません。複数の PreToolUse フックはファイル名順に次々と実行され、先のフックがブロックした後でもすべてが実行され、2 つのフックの間にあるフックからのブロックも、その理由を届けます。Kiro IDE はフックの実行ごとに 1 つの「Run Command Hook」カードを表示するので、AI-DLC は 4 つのツール呼び出しチェックを 1 つのフック `aidlc-guard-tool-call` として登録し、Kiro が別々のフックを実行したのと同じように実行します。同じ順序（`plan-approval-guard`、`review-freeze`、`state-transition-guard`、`terminal-command-guard`）で、それぞれ自身の登録が選んだツールに対して、先の 1 つが拒否した後でもすべてを実行します。いずれかのチェックが拒否すると呼び出しは拒否され、各拒否のテキストが 1 回ずつ付き、通過させたチェックからは何も付きません（#2022）。そのマッチャーは、アダプターのツール名テーブルにある読み取りだけを除外します。それらは承認に答えることもワークスペースを変えることもできません。テーブルが知らない名前、たとえば Kiro 自身のバックグラウンドの `memory` ツールは、依然としてチェックに届きます。1.1.14 では、PreToolUse の `fs_write` の入力は `{path, text}` で、シェルの入力は上の 1.0.242 の行と一致します。

### 書き込みやコマンドの後: 次のカードまでに完了する

Kiro IDE 1.2.37 は、フックの stdout を、exit 0 の `SessionStart` と `UserPromptSubmit` に対してのみエージェントへ渡し、その stderr は、`PreToolUse`、`UserPromptSubmit`、`PreTaskExec` のフックが exit 2 するときのみ渡します（そのフック実行器の終了コード表）。`PostToolUse` フックが出力するものは、エージェントにも人にも届きません。そのため、AI-DLC が書き込みの後に行う作業（監査行とセンサー）と、コマンドの後に行う作業（下の 2 つの監査末尾フック）には、固有のカードがありません。`aidlc-guard-tool-call` が呼び出しを通過させると、それを `aidlc/.aidlc-sessions/kiro-ide-pending/` の下に記録します。監査対象の書き込みについては、対象ファイルを当時の状態で（サイズ、時刻、内容のハッシュ）、コマンドについては、そのコマンドと、すべてのスペースの記録フォルダを記録します。とにかく次に実行されるカード（次のガード、人の次のメッセージ、またはターンの終わり）が、その作業を最初に、`catch-up` の中で行います。ファイルが変わった書き込みは、after-write カードが与えたのと同じ入力と、書き込み自身の `session_id` とともに `write-audit-log` と `run-sensors` へ送られます。ファイルが変わらない書き込みは、別の呼び出しが始まる間、後のカードを待ち（まだ書き込み中かもしれません）、メッセージかターンの終わりで破棄されます。コマンドは、`aidlc-after-shell` の 2 つのフックを同じフロントゲートの背後で実行し、実行中に現れた記録フォルダは `Intent created: <record> (space: <space>)` としてリビルドへ渡されます。記録された各呼び出しは、そのファイルを改名することで要求済みにされるので、2 つのチャットのカードがそれを二重に行うことはありません。フックファイルがまだ `aidlc-write-audit-log` や `aidlc-after-shell` を登録しているプロジェクトは、それらのカードにその作業をさせ続け、ガードはそれらに対して何も記録しません。

## 各フックへの影響

- **write-audit-log / run-sensors** — 復元可能: 結果の散文からファイルパスを拾い、絶対パスへ解決し、Claude の形をした `{tool_input:{file_path}}` をコアのフックへ渡します。パスを抽出できないときは、アダプターは両方をログに記録するのではなく 2 つのケースに分けます。**失敗**した書き込みと認識された散文は `hookDebug`（フックのデバッグが有効なときだけ書かれる）へ送られ、成果物が存在しないので転送されません。この推論は、ペイロードに構造化された success フラグがないときだけ実行されます。明示的な `toolSuccess: true` と、ほかのどのマッチしない表現も、目に見える hook-drop を記録します（決して黙ったままの no-op ではありません）。それが、drop ログの存在理由である「見えない劣化」のケースです。これらを混同すると、`--doctor` が健全なワークスペースで劣化を報告してしまいました。
- **rebuild-stage-graph** — シェルコマンドは復元不可能なので、IDE のパスはコマンドフィルターを捨て、監査末尾だけでゲートします（残っている遷移、たとえば `WORKFLOW_COMPLETED` の後が、後続のシェルコマンドごとに再コンパイルしないよう、mtime の冪等性ガードを伴います）。シェルの結果とセッションの同一性は依然として転送されます。新しいイベントは正確な `session_id` を使い、レガシーのチャネルは SessionStart が保持するホスト由来の同一性を使います。結果が成功した `intent-create` を名指すと、共有フックはそのセッションを作成された記録に束ねます。
- **sync-workflow-state** — IDE はタスクペイロードを渡さないので、監査末尾の最新の `STAGE_STARTED` から現在のステージを導きます。これは**前方向のみ**のミラーです。`Current Stage` を完了済みやスキップ済みのステージへ巻き戻すことは決してなく、ワークフローが `Running` でないときは決して発火しません（終わったワークフローの復活を防ぎます）。また、Unit の再オープンがその `STAGE_STARTED` の後に作業をそこへ戻した場合や、別のクローンの監査ファイルで同じ秒に戻した場合にも、`Current Stage` に手を触れません（再オープンの行は `Moved From` を運びます）。その移動は自身の開始を書かないので、最後の開始が、作業が去ったステージを名指します。どちらの監査末尾フックも、`execute_bash`、Windows の `execute_pwsh`、`shell` のエイリアスにマッチします。IDE は、同期が解析できるタスクイベントを一切公開しません。
- **2 つの監査末尾フックのフロントゲート**: それらはシェルコマンドごとに 1 回、次のカードの `catch-up` で実行されます（または、フックファイルが古いプロジェクトでは `aidlc-after-shell` カードとして）。そこで `catch-up` とディスパッチャーの `engine adapter kiro-ide` ルートは、エンジンをロードせずにまず見ます（`core/tools/aidlc-hook-front-gate.ts`）。いずれかのフックが、ある記録のファイルから行うべき作業を見つけられないとき、その記録の `.aidlc-engine/hooks-health/` に `<hook>.noop` を残します。ゲートがフックをスキップするのは、すべてのスペースのすべての記録が、そのフックがそこで読むすべて（監査シャードと状態ファイル、加えてリビルド用の `runtime-graph.json`）より少なくとも 5 秒新しいそのマークを持つときだけです。スキップされたリビルドは、完全なフックと同じように、既存の `rebuild-stage-graph.last` ハートビートを書き直します。リンク、スペース以前の平坦なレイアウト、フックのデバッグ、クロックより先のタイムスタンプ、マージン内の変化は、完全なフックを実行します。カードがスキップされるのは、両方のフックがスキップされるときだけです。ガード、書き込み、プロンプト、ほかのすべてのターゲットは、常に完全に実行されます。
- **log-subagent** — ペイロードに依存します。IDE 0.12 は `invoke_sub_agent` を送り、1.x（1.0.89-1.0.138）は代わりに `subagent_<agent>` を送り、それぞれの前に空の `subagent_response` シェル（`"Response recorded."`）が付きました。そのため登録のマッチャーは広く（`^(?!subagent_response$)(subagent_.+|invoke_sub_agent|orchestrate_subagent)$`）、すべての委譲名がアダプターに届く一方で、空のシェルはカードを得ません。アダプターはほかのすべてのエントリーポイントで `subagent_response` を破棄します。そのシェルは散文を運ぶが同一性を持たないので、転送すれば `Agent Type: unknown` の `SUBAGENT_COMPLETED` 行をでっち上げてしまいます。同一性は、構造化された 1.x の `subagent_<agent>` ツール名を優先し（#543）、それはプラットフォームが提供するので、エージェントが書いた結果の散文が監査行を誤帰属させることはできません。それがないときは、#459 の `**Reviewer:**` ／ `**Agent:**` の結果マーカーへフォールバックします。それが、0.12 の `invoke_sub_agent` の形における唯一の同一性の信号です。
- **review-freeze / state-transition-guard**: それぞれが `aidlc-guard-tool-call` カードの中で、アダプターが転送する書き込みとシェルのツールをちょうど名指す自身のマッチャーとともに実行されます（`write`、`fs_write`、`create_file`、`str_replace`、`fs_append`、`delete_file`、`apply_patch`、`edit_file`、`execute_bash`、`execute_pwsh`、`shell`）。そのため、読み取り、検索、`memory` 呼び出しは、どちらのチェックにも届きません。`create_file`、`apply_patch`、`edit_file` のペイロードは取得されません。それぞれはアダプターが読むパスフィールドでチェックされ、それがないもの（パスがテキストの中にしかないパッチ）は後述のとおり拒否されます。アダプターが認識する書き込みツールは、Write（`fs_write`、`text` を `content` として。kiro-cli 2.6.1 の `write` は `content` をそのまま）または Edit（`fs_append`、`text` を `new_string` として。`str_replace`、`oldStr`/`newStr` を `old_string`/`new_string` として。`delete_file`、`targetFile` をパスとして）として転送され、シェルツールは、呼び出し自身の `cwd` から（およびコマンド内のリテラルな `cd` や `pushd` が残すすべてのディレクトリから。`execute_pwsh` は `aidlc_shell: "powershell"` と印づけられ、どちらもそれを PowerShell として読みます）判断される Bash として転送され、ペイロードの `session_id` も一緒に運ばれます。ほかのすべてのツールは転送されません。Kiro は、委譲されたエージェント自身の呼び出しに対してもプロジェクトの PreToolUse フックを実行し、コンダクターの `session_id` とエージェントの同一性なしで、そこでも exit 2 を尊重します（IDE 1.2.4 で `invoke_sub_agent` の `fs_write` について実測）。そのため、どちらのガードも委譲の呼び出しをコンダクターのものとして判断します。サポートされるビルド（Kiro IDE 1.1.70、Kiro CLI 2.24.1 以降）のすべての PreToolUse ペイロードは、そのツールを名指して入力を埋めます。そのため、どちらのガードも読めない呼び出し（ペイロードなし、不正形式のフィールド、ツール名なし、アダプターが読むパスフィールドのない書き込みツール、コマンドのないシェルツール）は、ワークフロー、Guard Policy、`AIDLC_DISABLE_REVIEW_FREEZE_HOOK` が何であれ、どちらかが実行される前に exit 2 で拒否されます。その拒否は、それらのビルドを名指し、古い Kiro の更新を促します。引数のないレガシーのペイロードは、そのような呼び出しの 1 つです。何も書かない読み取れるコマンドは、依然として転送されます。
- **plan-approval-guard** — 埋められた PreToolUse の引数は、共有のターゲット対応ガードへ転送されます。シェル呼び出しは、上と同じように自身の `cwd` から判断されます。Kiro IDE 0.12 はツールを識別するが空の引数オブジェクトを渡すので、アダプターは媒介された planned-source プロトコルを使います（このガード自身の扱い: この行では、上の review-freeze と state-transition の登録がそのような呼び出しを拒否するので、それが許す計画の書き込みは実行されず、それが開いた書き込みウィンドウは後述のとおり回復ラッチとして残ります）。計画中は、実測された `fs_write` と `str_replace` のツールだけが利用でき、シェル、append、delete、patch、エイリアス、カスタムの変更ツールは承認の前に止まります。正規の計画書き込みの後、アダプターは現在の Testing Contract を注入します。正規の questions 書き込みの後、ターゲットに束ねられた `[Approval Fingerprint]` を置き換え、ライブのワークスペースソースを `[Planned Source]` として記録し（レガシーのチャネルはフィンガープリントコマンドを実行できないので、アダプターが両方のタグを所有します。ワークスペースにソースフィンガープリントがないときは `unbindable`）、予約された decision または answer ツールを自分で呼び出します。ステージの learnings diary、コンポーザーの提案、人の answer テキスト、または人のリクエストを `aidlc/.aidlc-request-text/` に直接書くこと（プランが待つ間に共有ガードが許す記録ファイル）は、計画の書き込みではありません。アダプターはその書き込みウィンドウをクリアし、違反を記録しません。Kiro は PostToolUse の stdout を捨てるので、成功した書き込みフックは黙ったままです。decision または answer のステップが拒否されると、フックはそれを捨てるのではなく、拒否を stderr に付けて exit 2 します。書き込みウィンドウは、人が回復するまでラッチされたままだからです。ワークスペースソースは、answer のパスがチェックするのとまったく同じように、記録された `[Planned Source]` と照合されます。planned source が記録される前は比較するものがなく、いったん記録されると、ドリフトは不透明なツールを「プランを再提示する」という救済とともにブロックし、その間、正規の計画書き込みは開いたままで、その救済が実行できます。呼び出し元の `next` または最後のステアリング `continue` は、Code Generation のディレクティブに 1 つの `legacy_plan_approval_choices` capability を運びます。ランタイムはそのハッシュだけを保存し、平文のラベルはそのチャットのツール結果に残ります。人の後の `promptSubmit` は、正確なラベルを 1 つ運ばなければなりません。無関係なプロンプトは capability を受け取りません。所有権は、受信セッションを通じて調べられるのではなく、アクティブな intent/revision に対してグローバルです。回復は人がゲートします。所有ウィンドウはまず、入力された回復の問いを受け取り、エージェントはそれを平易な言葉で尋ねます。エージェントは、後の `next` が offer や challenge を回転させる前に、人の yes を、どんな言葉であれ `log answer --checkpoint plan-approval --details 'Recover Plan Approval'` で記録します（人の返信が問いの後に来ると、エンジンは自身の選択から応答を書きます）。別のライブウィンドウは拒否されます。置き換えウィンドウが同じ人の回復を要求できるのは、記録された所有者の PID が消えた後、または IPC のみの所有者のエンドポイントが消えた後だけです。乗っ取りは、保留中の challenge を回転させ、その先の応答をクリアします。共有の questions ファイルは正規のままで、監査は選択肢を伏せます。欠落または破損した offer/challenge ファイルは、権限を消しません。pre-write ウィンドウ自身が、PostToolUse が決して届かない場合の orphan-recovery ラッチであり、PostToolUse が実行されるときにマッチする書き込み違反がそのラッチを継続します。新しい公開は、人の回復の yes が記録されるまでブロックされたままです。アダプターは回復の問いを保ち、成功後は、置き換えの offer を削除するのではなく、違反／書き込みウィンドウだけをクリアします。各書き込みの前にラッチが作られ、権威ある `toolSuccess: false` と認識された失敗散文は、変更が起きなかったのでそれをクリアし、未知の結果はそれを保持して回復を要します。引数のない計画書き込みの前に、アダプターは現在のターゲット／リビジョンを保護された書き込みウィンドウに保存します。その書き込みが状態、アクティブマーカー、または別の権限ファイルを削除または破損した場合、PostToolUse は保存されたリビジョンを汚染し、ライブの権限がもはや解析できなくなっても後の変更呼び出しはブロックされたままです。アダプターが所有する `next` の回復は、エンジンが有効な非エラーのディレクティブを返した後にのみ、その汚染をクリアします。生の監査 append には権限がありません。アダプターが所有する回復と decision/answer の媒介は、`aidlc-runtime-paths.ts` の共有 `aidlcEngineCommand` ヘルパーを使い、これはオーケストレーターの state の子も使います。ネイティブモードはコンパイル済みの実行ファイルを解決し（`AIDLC_COMPILED_EXECUTABLE` を尊重）、`engine orchestrate next`/`continue` または `engine log decision`/`answer` を呼び出します。ソースモードは Bun の実行ファイルと、`aidlc-orchestrate.ts` または `aidlc-log.ts` への絶対パスを使います。どちらのモードも、既存のプロジェクト／セッションの引数、作業ディレクトリ、継承した環境を保ちます。失敗した子呼び出しは実際のエラーを保持します。無効な JSON ディレクティブは、レガシーの回復の問いとは別の契約を持ちます。選ばれた救済の `interaction` に従い、求められた人の選択の後に返されたとおり正確に `command` を実行し、`human-input` の Request Changes 救済に対しては別個の正確なフィードバックを集めます。ネイティブの restart/abort コマンドは、構造化された操作に由来します。ネイティブの abort は、正確に発行された引数の形でのみ、Plan Approval の前提条件の例外を受け取ります。所有するツールは、依然としてライフサイクルの受け入れを強制します。[Guard admission and recovery asks](12-state-machine.md#guard-admission-and-recovery-asks) を参照してください。
- **session-start** — 新しい `session_id` を読み、gitignore されたランタイムセッションディレクトリの下に永続化します。レガシーのチャネルは、`VSCODE_IPC_HOOK`/`VSCODE_PID` から安定したホストインスタンスごとの ID を導きます。Kiro IDE 1.1.14（Windows でライブに確認）は、新しいチャットで SessionStart フックを実行しないので、下の record-human-turn のルートが、チャットの最初のプロンプトに対してこの作業を行います。
- **terminal commands** — 送信された `/aidlc ...` プロンプトを公開する新しいビルドは、UserPromptSubmit で決定論的なユーティリティを実行します。IDE 1.0.242 は空のプロンプトを公開するので、フォールバックは PreToolUse で正確な `execute_pwsh` の `aidlc-orchestrate.ts next` 呼び出しを認識し、分類されたユーティリティを 1 回実行し、重複するシェル呼び出しを拒否します。どちらのルートも、イベントの `session_id` をそのセッションとしてユーティリティに渡すので、`/aidlc intent <name>` や `/aidlc space <name>` は、record-human-turn がそのチャットを開始する前にこのフックが実行されても、それを入力したチャットを束ねます。どちらのルートも UTF-8 を明示的にデコードし、プレーンテキストの中継からのみターミナルのプロトコル／制御バイトを除去します。構造化されたフック JSON と無関係な拒否のパスは書き換えません。新しいターン／ラッチの状態は `session_id` のハッシュをキーにするので、同時のチャットが互いの出力を再利用することはできません。セッションの同一性のないペイロードは、ホスト由来の同一性または保持されたセッションを使い、どちらも利用できないときは明示的なレガシーバケットを使います。0.12 の camelCase のフォールバックは、`toolArgs.command` からコマンドを読みます。
- **ターミナルコマンドの後のシェル呼び出し**: 同じターン内で、上のフォールバックは、シェルを通じて再び入力されたターミナルコマンド、引き下げのガード設定、そしてツールファイル `aidlc-orchestrate.ts`、`aidlc-utility.ts`、`aidlc-knowledge.ts` を名指す呼び出しも拒否します。チャットのターンに対してターミナルコマンドがいったん実行されると、エージェントはその出力を中継して止まるよう告げられ、`terminal-command-guard` はそのターン内のそのチャットのほかのすべてのシェル呼び出しも、ツール入力が読めないものも、exit 2 と、出力を中継してターンを終えるよう告げてコマンドが運んだものを何も引用しない 1 つの固定の行を stderr に付けて拒否します。ペイロードが名指すチャットについては、これは固定の呼び出しを求める拒否（単独のキャリッジリターン、ファイルに送られた AI-DLC の返信、cmd.exe が分割する値、引数内の PowerShell コード）より前に決まるので、エージェントは呼び出しを再び実行するよう告げられません。再び入力されたターミナルコマンド、またはツールファイルを名指す呼び出し、または引き下げのセッターは、そのような文字を運ぶときも、フォールバックの拒否とその出力を得ます。人のメッセージを隠すビルドでは、引き下げのセッターは、出口を名指す自身の拒否を得ます。これは、ディスパッチャーまたはネイティブの `aidlc` を、任意の引数、任意のプロジェクト、シェルが実行時に組み立てる名前、AIDLC をまったく名指さない呼び出しでカバーします。コマンドの読み取りが、どの呼び出しが無害かを決めることはありません。シェルでないツールは、このチェックの対象ではありません。ターンが進むのは、人のメッセージ（`UserPromptSubmit`。Kiro が自分で作ったプロンプトは `HOST_TURN` として記録され、ターンを進めませんが、ターミナルコマンドが保留した実行がその Stop で終わると、チャットへのそのようなプロンプトは自身の実行を始めて保留を終えます。その実行が開いている間、またはワークフローステップ自身のセッションについては、保留は残ります）のときだけです。Kiro が人なしで始めるエージェントの実行はターンを保ち、人の次のメッセージがそれを解放します。同一ターンのシェルチェックは、ペイロードの `session_id` が名指すチャットだけを、そのチャットが記録したターンに対して判断します。ペイロードにセッションがない、別のチャットのラッチ、または後のターンのときは、何も拒否しません。ターンカウントは整数としてのみ読まれ、それが再び始まらなければならない（欠落または読み取り不能）たびに、その隣のラッチは落とされます。ラッチを除去できないときは、新しいカウントはそのターンを過ぎたところから始まります。書き込めないカウントはラッチを道連れにするので、そのターンのターミナルコマンドはラッチを残さず、そのシェル呼び出しは実行されます。カウントが書き込めず、かつラッチが除去できないときにのみ、ラッチはマッチし続けます。それは、どちらかが再び変えられるか、人が新しいチャットを開くまでです。ターミナルコマンドの拒否は、ペイロードがどれも名指さないとき、依然としてホストの、または保持されたセッションに従います。これに対するエンジン自身のガード（Branch 0）は、エージェント v1 のプロジェクト全体のラッチだけを読み、これらのチャットごとのものは読みません。エンジンは、プロセスの系統を通じてのみ 1 つのチャットのラッチを別のものと見分けられますが、1 つの Kiro IDE ウィンドウのチャットはプロセスを共有します。
- **cmd.exe のメタ文字**: ネイティブの Windows の `aidlc` は `aidlc.cmd` なので、cmd.exe は Windows PowerShell 5.1 がそのために組み立てるコマンドラインを読みます。スペースを含む値は、自身の二重引用符をそのまま残して二重引用符で囲まれ、cmd.exe は引用符の外の `&`、`|`、`<`、`>`、`^` に作用します。したがって `--details 'Use "R & D" team'`、または `\"` を使った同じものは、`D" team"` を別のコマンドとして実行します。何よりも先に、`terminal-command-guard` は、それらの文字の 1 つが引用符の外で cmd.exe に届く、または値が `%NAME%` のペアを含む（cmd.exe はそれを、引用符の内側でも、その環境変数の値で置き換えます。単独の `%` は通り、`10% and 20%` の中のもののように名前がスペースで始まるか終わるペアも通ります）`aidlc` または `aidlc.cmd` の `execute_pwsh` 呼び出しを拒否します（stderr に理由を付けて exit 2）。理由は、問題のある値を持つフラグ（または「A value」）と、その文字または「a %NAME% pair」を名指す固定の文で、値を決して繰り返さないので、値の中のテキストがそれに行を足すことはできません。`orchestrate next` の後のテキストは、変えるよう告げられることが決してありません。それがそのような文字、`%NAME%` のペア、二重引用符や約物の引用符、改行、またはスペースを含む値の末尾のバックスラッシュを持つとき、理由は代わりにリクエストファイルを名指します。それは、エージェントが `next --request-file` のためにファイルツールで書くもので、フラグの値はファイルを通せないと言います（エージェントは、メタ文字を含む一語の値を単一引用符の内側の二重引用符で書き、自分が書いた値からはほかの文字を外し、人が与えた 1 つについて人に尋ねます）。通るのはその 1 つの形だけです。`next` が任意の値を取るフラグ（`nextTokenKind`）の後に、`%`、二重引用符や約物の引用符、末尾のバックスラッシュを持たない、二重引用符で囲まれた一語（`--report '"scan&review.json"'`）です。一方、`next`（または先頭の `compose`）の後にエンジンが得る単語はフラグとその値で、`--` のマーク、単語、先頭の名詞、エンジンが取らないフラグ、変数、またはエンジンがそのフラグのものとして取らない値（空、`--` で始まる、またはそのフラグが挙げないもの）が、それを終わらせます。`--request-file`、`--project-dir`、`--aidlc-attempt-id` は、エンジンが先に行から取り除くもので、その値とともに読み飛ばされます。ほかのどの単語がリクエストかは、エージェントが知るべきことです。フックはそれを読みません。それは、PowerShell 5.1 の引数渡し（空の引数は落とされ、スペースやタブを含む値は二重引用符で囲まれる）と、cmd.exe の引用符トグルをシミュレートし、`#` コメントと閉じた `<# ... #>` のブロックコメントを読み飛ばし、バックティックの継続（CRLF、LF、CR）で終わる行を次の行へつなぎます。`(...)`、`$(...)`、`@(...)`、`@{...}`、`{...}` のグルーピング内の文も、ネストしているかどうかにかかわらず読まれるので、`(aidlc engine orchestrate next 2>$null | Select-Object -Last 1)` のような `aidlc` 呼び出しも、ほかと同じようにチェックされます。二重引用符で囲まれた文字列の中の `$(...)` はチェックされません。リダイレクト（`2>$null`、`*>$null`、`>$null`、`2>&1`、`> file`）は、決して `aidlc` の値ではありません。PowerShell が `aidlc.cmd` の実行前に解決する人の単語も、チェックが cmd.exe に何が届くかを見られないので、同様に拒否されます。それは、`--details`、`--decision`、`--rationale`、`--reason`、`--user-input`、`--feedback`、`--override`、`--arguments` の値、または `next` の後のリクエストが、`$x` や `$env:X` のような変数、`$(...)` のような式、または `$` やバックティックを含む二重引用符の文字列として与えられた場合です。理由は、値が PowerShell の変数や式から来ると言い、単一引用符でその値そのものを求めます。ほかのどのフラグ、または `continue $obj.receipt` のレシートのような位置トークンの変数は、それ自身のテキストがメタ文字や `%NAME%` のペアを持たない限り、通ります。ほかのどのコマンドの変数も同様です。最後まで読めない文（`--%` の停止解析トークンを使うもの、または未終了の引用符やブロックコメントを持つもの）は、そのプログラムが `aidlc` または `aidlc.cmd` である場合、素で、パスで、または `&` や `.` の後で、その地点より前の単語が示す限り、拒否されます。ほかのどのプログラムを実行する文も、データとして aidlc に言及していても通ります。`bun .kiro/tools/...` の呼び出しやほかのプログラムはチェックされません。
- **stop** — 新しい Stop イベントの `session_id` を読み、ワークスペースグローバルの SessionStart マーカーより優先するので、同時のチャットは自分自身の作成後・切り替え後のハンドオフレシートだけを消費します。レガシーの agentStop と壊れた新しいチャネルは、保持された同一性へフォールバックします。
- **record-human-turn** — 新しい `session_id` と answer ペイロード、またはレガシーの `USER_PROMPT` を読みます。ディレクティブが発行した正確な選択を提出できますが、別のチャットの保護された capability を明かしたり、回転させたり、移したりは決してしません。プロンプトの `session_id` が、最後のイベントから保持されたものでないとき、またはアダプターにそのセッションを開始した記録がないとき、アダプターはまずコアの session-start を実行し（以前にそのセッションを開始したか、セッションがすでに束縛や intent のスタンプを持つときは `resume`、そうでなければ `startup`）、そのコンテキストをプロンプトフック自身のものより前に出力します。そのため新しいチャットも `AIDLC Runtime Session:` の行を得て、以前のチャットへ切り替え直すとそれを再束縛します。記録は、セッションのハッシュ化されたターン／ラッチディレクトリの中の `session-started` ファイルで、session-start が成功した後にのみ、このルートから、または実行された SessionStart フックから書かれます。保持された id だけでは開始の証拠になりません。以前のアダプターは、すべてのプロンプトの id を開始せずに保持していたので、アップグレードをまたいで開いたチャットは次のプロンプトで開始します。開始済みの保持されたセッションからの後のプロンプトは、何も開始しません。
- **session-end / block** — ペイロードを必要とせず、stdin を決して読みません。session-end は SessionStart が永続化した同一性を再利用し、レガシーのライフサイクルのフォールバックは、承認の権限が関わらないところでのみ保持されます。

## toolResult のパス抽出パターン

| toolName | 表現 | 正規のツール |
|----------|---------|----------------|
| `fs_write` | `Created the <PATH> file.` | Write |
| `str_replace` | `Replaced text in <PATH>`（末尾に ` (N occurrences)` を運ぶことがある） | Edit |
| `fs_append` | `Appended the text to the <PATH> file.` | Edit |

抽出器は、マッチの前に末尾の空白／改行をトリムし、`str_replace` の形から末尾の括弧書きを取り除きます。`fs_write` は `Write` に、`str_replace`/`fs_append` は `Edit` にマッピングされます（どちらも既存のファイルを対象にするので、コアの write-audit-log は `ARTIFACT_UPDATED` を記録します）。
