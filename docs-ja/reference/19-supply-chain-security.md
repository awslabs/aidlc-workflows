# リリースのサプライチェーン

AI-DLC は、公開済みのプレビューのソースを選ぶために `.github/workflows/promote-release.yml`、その安定版リリースをビルドして公開するために `.github/workflows/release.yml`、ナイトリーのプレビューを生成するために `.github/workflows/preview-release.yml` を使います。公開にはリポジトリの `GITHUB_TOKEN` を使い、追加の認証情報は不要です。ライブのモデル環境を使うのは、プレビューの Full Suite だけです。

## リリースのトリガー

`main` で **Promote preview** を実行します。空のディスパッチは、公開済みのすべてのプレビューを、そのソース、マニフェストの互換性、警告とともに列挙します。昇格は `preview`、`version`、レビュー済みのリリース `notes`、そして任意で、メンテナーのマシンで作成しスキャンした `contributors` リストを供給します。コマンドは [DEVELOPERS.md](../../DEVELOPERS.md#4-promote-a-preview-to-production) にあります。プレビューの公開は、テストの失敗があっても成功していることがあります。選択はメンテナーの判断で、それらの失敗は依然として記録されます。

`scripts/release-promotion.ts` は、選ばれたリリースが公開済みのプレリリースであること、その注釈付きタグのソーストレーラーがそのコミットとリポジトリと一致すること、そしてそのコミットが `main` にあることをチェックします。リリースコミットを作成したりタグを予約したりする前に、プレビューの `version.json` をダウンロードし、そのプレビューとソースに束縛された、最終アセットの検証器と同じマニフェスト contract を適用します。互換性のない過去のプレビューは、その拒否理由とともにリストに残ります。メンテナーは互換性のあるプレビューを選ばなければなりません。次を伴う1つの子コミットを準備します。

- `core/tools/aidlc-version.ts` と README に書かれた、選ばれた安定版のバージョン。
- すべての以前のエントリを保った、新しい CHANGELOG のエントリ。
- 準備中にチェックアウトされた不変の main スナップショットからの、完全なワークフローツリー、昇格スクリプト、プレビュータグのパーサー、共有のマニフェスト検証器。
- プレビュー、ソース、コントロール、バージョン、notes、日付、記録された警告、以前の安定版バージョン、貢献者リストを束縛する `.github/release-promotion.json`。

ワークフローツリーは、削除を含め完全にコピーされるので、そのファイルはレビュー済みの main の内容と一致し、追加のワークフロー書き込み用トークンを必要としません。製品のソース、依存、ビルドスクリプト、ハーネスは、それ以外はプレビューのものにとどまります。公開のコントロールを運ぶことで、古いプレビューが現在のリリースプロセスを使えます。候補のソースとコントロールのコミットは、両方とも `main` の祖先でなければなりません。リリースコミット自体は `main` にある必要はありません。検証は、その単一の親、変更されたファイルの完全なセット、正確なメタデータの内容、ファイルモード、正確なコントロールの blob をチェックします。署名と公開の前に再び実行されます。`main` の任意のタグがリリースすることはできません。

準備は、安定版タグを force なしでプッシュし、そのタグで `release.yml` を明示的にディスパッチします。`GITHUB_TOKEN` のプッシュは別のプッシュワークフローをトリガーしないためです。タグ付きのワークフローは、イベントの ref、チェックアウト、タグ SHA をチェックします。provenance が見るソースの同一性は、実際の安定版タグとコミットのままです。準備は安定版ビルドとは独立に直列化されます。リトライは、一致する検証済みの予約だけを再利用します。別のプレビュー、notes、貢献者リストがそのタグを要求することはできません。

安定版の昇格は CI や Full Suite を繰り返しません。以前の結果は、選ばれたプレビューに関連付けられたまま、安定版の notes からリンクされます。記録された警告は保たれます。失敗したテストがパスとして付け替えられることはありません。既存の `release` 環境が依然として最終的な公開を制御します。

明示的な手動の `full-suite.yml` ディスパッチは、マージ前に候補のライブジョブを検証するために `live_verification=true` を、または候補のすべての認証情報不要のジョブを実行するために `full_verification=true` を設定できます。この2つは互いに排他的で、どちらの入力も再利用可能な呼び出し元には利用できません。この計画は `workflow_dispatch` と、チェックアウトされたソースと手動で選ばれたワークフローのヘッド（`github.sha`）の正確な一致を必要とします。通常の実行は、マージされていないブランチを含め、要求された ref を受け入れ、その解決された不変の SHA を使ってすべての必須ジョブを実行します。候補ブランチからのディスパッチは、信頼された安定版リリースの証拠として適格ではありません。自動の特権的なブランチプッシュや PR のトリガーはありません。

ライブ検証は、同じ隔離されたライブ準備、環境が所有するロール、低権限のブローカークライアントを使います。意図的にネイティブ、決定論的、production-guard のジョブを省きます。そのアーティファクトは `full-suite-live-verification-result` という名前で、`purpose: "live-verification"` と `complete: false` を記録します。成功した結果は、ライブジョブが成功し、省略が明示的にスキップされることを必要とします。安定版リリースのワークフローは、`main` での検証実行を含め、このアーティファクトを消費しません。

完全な検証は、候補でネイティブ、決定論的、production-guard、Windows release-contract のジョブを実行し、認証情報を受け取るジョブは決して実行しません。3つの `live_prepare_*` ジョブと `live_linux`・`live_macos`・`live_windows` をスキップするので、マージされていないコードが、それらの認証情報に到達できる場所で実行されることは決してありません。すべての Full Suite のチェックアウトは `persist-credentials: false` を設定するので、候補のコードがリポジトリのトークンをディスク上で見つけることもありません。`verification_family` と `verification_test` のフィルターを拒否します。そのアーティファクトは `full-suite-verification-result` という名前で、`purpose: "full-verification"`、`complete: false`、そして `omittedLegs` にちょうど7つのジョブを記録します。前述の6つと、決定論的なジョブがすでにそのテストを実行する `scope_runs` です。成功した結果は、他のすべてのジョブが成功し、7つがスキップされることを必要とします。候補がマージされたあとでも、どのリリースワークフローもそれを消費しません。

手動検証はさらに、`verification_family` を `claude-sdk`、`claude-tui`、`codex`、`copilot`、`opencode` として選べます。デフォルトは `all` です。scope を付けた実行は、同じヘッド正確性の認可を保ち、選ばれたファミリーの既存のシャードだけを実行し、Windows release-contract のカバレッジが明示的にスキップされることを必要とします。結果は `verificationFamily` とその省略を記録します。リリース目的の実行は、scope を付けた選択を拒否し、`passed` やジョブの状態とは独立に `verificationFamily: "all"` を必要とします。特定のファミリーに対して、`verification_test` は正確なリポジトリのファイルを選べます。発見は、未知の、または一致しないファイルを拒否し、その元のシャードの同一性と宣言されたプラットフォームを保ちます。準備はそれらのプラットフォームでのみ実行されます。結果は `verificationTest`、`verificationPlatforms`、省略されたホストジョブを記録します。reducer は、それらの省略がスキップされ、選ばれたジョブが成功することを必要とします。ソースゲートと結果 reducer の両方が、リリース目的の実行に対してこの選択を拒否します。

POSIX の準備は、固定された公式の Node ディストリビューションを取得し、その完全なプレフィックスを、検証された依存のアーカイブとともに運びます。認証情報を持つジョブは、それらの準備されたバイトを展開してコピーするだけで、依存のインストーラーを実行しません。Node と CLI の起動は、runner のディレクトリが保護されたあと、低権限の識別情報のもとで実行されます。収集は、その macOS アカウントの launchd ドメインを引退させ、実行可能なプロセスが残っている間はコピーを拒否します。

ライブのマトリクスは、サポートされるプラットフォームごとに1ファイルを各ジョブに割り当てます。Linux、macOS、Windows のライブジョブは、4、2、3 という別々の並行の上限を持ちます。各ロールセッションは、その実行ステップの直前に 3,600 秒を要求します。ジョブは 80 分、テストステップは 70 分、ライブのファイルと実行は 3,600 秒を許します。モデルの作業は5分のクリーンアップ予備で止まるので、常にセッションが有効なうちに終わり、その後に証拠の収集が続きます。タイムアウトはカバレッジを失敗させます。既存の IAM ロールの期間と認証情報分離の境界は変わりません。

Feature、fix、ドキュメント、refactor、test の PR は、リリースのメタデータを更新しません。昇格が、選ばれたソースでそれを更新します。公開のあと、メタデータのみのブランチと PR が、製品コードを変えたり新しいバージョンをダウングレードしたりせずに、バージョン、バッジ、changelog を現在の `main` と同期させます。

## ビルドと検証

昇格を検証したあと、安定版ワークフローは次を行います。

1. プレビューソースのハーネスディストリビューションを再生成し、決定論性をチェックします。
2. 安定版バージョンで Linux、macOS、Windows のネイティブバイナリをビルドします。
3. ネイティブとインストーラーのスモークテスト、ShellCheck、PSScriptAnalyzer を実行します。
4. ネイティブと手動コピーのランタイムアーカイブ、インストーラー、マニフェスト、チェックサムをパッケージします。
5. 以前の安定版リリースからのインストール、ライフサイクル、更新をチェックします。
6. 公開の前に、ステージングされたリリースのインベントリを検証して証明します。

更新のジャーニーと最終アセットの検証器は、固定された公開コントロールのコミットのツールを使います。ビルドと packager は、選ばれたプレビューのソースを使います。昇格中に PR のテストマトリクスやライブスイートが実行されることはありません。必須の PR チェックは、製品の変更に対して Linux のスモーク、ユニット、決定論的な統合のカバレッジを提供します。ナイトリーのプレビューは、より広いハーネスのカバレッジを提供します。新しくビルドされた安定版候補のライフサイクルとアップグレードの失敗は、依然として公開をブロックします。

リリースのマニフェストは、安定版タグの ref と正確なリリースコミットを記録します。ネイティブのインストーラーは `aidlc-runtime-X.Y.Z.tar.gz` を選びます。手動コピーのユーザーは `aidlc-copy-runtime-X.Y.Z.tar.gz` をダウンロードします。コピーのアーカイブとそのチェックサムの sidecar は、古いクライアントとの互換性のため、マニフェストとメインのチェックサムインベントリの外にとどまります。provenance がそれらを独立に認証します。インストーラーの信頼の規則は変わりません。

## Provenance（来歴）

`publish` ジョブは、build、lifecycle、update-from-the-last-release のジョブがパスしたあとにのみ `id-token: write` と `attestations: write` を受け取ります（プレビューの `publish` は、そこで報告するだけの update ジョブを待ちません）。GitHub がステージングされたアセットの build provenance を生成します。エクスポートされた provenance バンドルは `aidlc-release.intoto.jsonl` として含まれます。

プレビューのワークフローは `main` を `Europe/Lisbon` の毎日 22:00 にスケジュールし、手動のディスパッチを受け入れます。スケジュールされた実行と手動の実行は、アクティブな実行をキャンセルせずに、`release-preview` ワークフローの並行グループを通じて直列化されます。後続の各実行はリリースのリストを読み直します。planner は、ソースコミットが最新の公開済みプレビュー以降変わっていない場合、またはそのプレビューが、この実行のソースの子孫である新しいコミット（リトライまたはキューに入った古い実行）から構築されていた場合は、公開のビルドチェーンをスキップするので、チャネルが後退することは決してありません。Contract チェックと Full Suite は、依然としてそのソースに対して実行されます。最終結果は、validation とリリースのテスト（Full Suite の結果を報告する）が成功し、公開が成功するか意図どおりスキップされることを必要とします。失敗した Full Suite は、重複排除されていてもいなくても、それを失敗させません。同じ UTC 日付で `main` が再び進むと、別のプレビューが次のビルドカウンターで公開できます。

実行は、それが開始されたコミットをテストして公開します。`main` は絶えずマージを受け取り、runner はトリガーのずっとあとに実行を拾えます（Preview Release 36485041152 では 22 分）。そのため、計画、公開、リリースが必要とするのは、コミットが依然として `main` にある（現在のチップの祖先である）ことだけで、それがチップであることではありません。実行の provenance がそのコミットを名指しするので、新しいものに切り替えることはできません。revert はコミットを `main` の履歴から取り除かないので、プレビューがトリガーされたあとに revert されたコミットも、依然として Full Suite の認証情報でテストされ、プレリリースとして公開できます。それを取り下げるには、その Preview Release の実行をキャンセルするか、公開後にプレリリースを削除します。これはメンテナーの判断です（2026-09-29）。

planner は、現在の安定版 `x.y.z` を `core/tools/aidlc-version.ts` から読み、計画時の UTC 日付と、既存のタグまたはリリースレコードが占める id を使って `<x.y.(z+1)>-preview.<YYYYMMDD>.<N>` を割り当てます。次のパッチをメモリ内で計算し、リリースのメタデータを決して編集しません。ドラフトと孤立したタグはその id を予約するので、リトライの計画と同日の後続の公開は、それらの占める id を越えて `N` を進めます。残った `aidlc-staging-*` のドラフトは、publisher が別の候補をステージングする前に、依然として検査と削除を必要とします。

planner は、前回のプレビュー以降の変更から notes を描画します。Contract チェックが認可されたコミットをゲートし、その後リリースのビルドチェーンと Full Suite が並列に実行されます。公開は、検証されたアーティファクトと完了したテストレポートを待ちます。失敗したスイートでも公開は許されます。プレビューの notes は警告で始まり、Full Suite の失敗レポートで終わります。Full Suite は別個に実行され、Preview Release を失敗させずに、その失敗の状態を保ちます。プレビューの Full Suite ディスパッチジョブだけが、その実行を開始して監視するために `actions: write` を加えます。`Release tests` ジョブは、その証拠をダウンロードしてそのジョブを列挙するために `actions: read` を加えます。プレビューは PR CI のテストマトリクスを繰り返しません。PR CI と Full Suite は、同じ `deterministic-tests.yml` のワークフロー定義を異なるマトリクスで使います。PR には10個の Linux ユニットシャードと integration、手動の完全な検証には Linux/macOS/Windows のスモーク/16個のユニットシャード/integration/E2E です。PR CI は、結合された contract と production-guard のチェックジョブで Linux のスモークを実行します。ナイトリー（リリース目的）の Full Suite は決定論的な階層を実行しません。その scope runs と guard マトリクスは、ライブジョブの横で、すべての OS で自身のジョブで実行されます。Integration と隔離された E2E は、新しい runner プロセスの別々のジョブで実行されます。各呼び出しは、供給されたコミットの新しいチェックアウトをテストし、サニタイズされた証拠を保ちます。以前のテスト結果が実行の代わりに使われることはありません。`AIDLC_BUILD_VERSION` は、ソースツリーが安定版の `x.y.z` バージョンを保つ一方で、プレビュー id を射影、バイナリ、`version.json`、両方のバージョン付きランタイムアーカイブ、パッケージされたインストーラーに刻みます。したがって、パッケージされたインストーラーは `latest` を再発見する代わりに、それを運んだリリースをデフォルトとします。プレビューの publisher は、ステージングのドラフトを検証し、ソースリポジトリとコミットを記録する注釈付きタグを作成し、その後 `make_latest: false` でドラフトをプレリリースとして公開します。したがって、安定版の `latest/download` の発見は変わりません。

安定版とプレビューの公開は、それぞれ保護された `release` 環境と無人の `preview` 環境を使います。プレビュー環境は、同じ `main` のデプロイポリシーを保ちつつ、必須のレビュアーは持ってはいけません。マージの承認に加えて contract チェックが、その人間的で決定論的なゲートであり、Full Suite の失敗は、それをブロックするのではなく、プレビューの notes で報告されます。安定版の実行は別の並行グループを使います。プレビューの publisher は、公開の前に完全な候補をステージングしてバイト単位で検証し、可変または不変のどちらのリポジトリリリースでも動作します。

互換性のある GitHub CLI が利用できるとき、インストーラーは `checksums.txt` をそのバンドルと照合して検証し、検証を次に束縛します。

- `awslabs/aidlc-workflows`。
- 安定版バージョンには `.github/workflows/release.yml`、プレビューバージョンには `.github/workflows/preview-release.yml`。
- 安定版リリースにはバージョンタグ、プレビューには `refs/heads/main`。
- `version.json` からの正確なソースコミット。

GitHub CLI が欠けている、または古いバージョンでも、インストールはブロックされません。そのモードでは、オンラインの転送は HTTPS のみのままで、ソースの同一性の検証と SHA-256 のチェックは必須のままですが、クライアントは Sigstore バンドルを認証しません。

## 公開

最終の `release` ジョブは、保護された `release` 環境で実行され、`contents: write` を受け取ります。リリースに人間の承認が必要なときは、その環境に必須のレビュアーを設定します。承認のあと、ジョブは証明された候補をダウンロードし、タグとチェックサムを再チェックし、GitHub Release を作成します。

```bash
bun scripts/release-promotion.ts notes \
  --repository "$GITHUB_REPOSITORY" \
  --tag "$RELEASE_TAG" \
  --out "$RUNNER_TEMP/release-notes.md"
gh release create "$RELEASE_TAG" build/release/* \
  --verify-tag \
  --title "AI-DLC ${RELEASE_TAG#v}" \
  --notes-file "$RUNNER_TEMP/release-notes.md"
```

本文は、検証された昇格レコードから描画された安定版ページです。レビュー済みのエントリ（このバージョンの `CHANGELOG.md` のエントリも供給します）が、Summary、Upgrade、Fresh install、Highlights のもとにレイアウトされ、レコードが貢献者リストを持つときは貢献者のセクション、プレビューのページをリンクする、選ばれたプレビュー/ソースの参照、そして Full Changelog のリンクが並びます。プレビューの記録された validation 警告と失敗レポートは、安定版ページではなく、そのページに残ります。昇格レコードが警告の行を保ち、昇格実行のサマリーがそれらを表示します。ヘルパーは、notes を書く前に昇格を再チェックします。GitHub 自身の生成する notes は使われません。その「What's Changed」リストは、プライベート名のスキャンなしに、貢献するすべてのアカウントをハンドルで名指しします。貢献者リストは、そのスキャンが実行されるメンテナーのマシンで作成され、CI はそれを描画するだけです。

ジョブはその後、ローカルのアセット名を、GitHub Release API が返すアセット名と比較します。欠けている、または余分なアップロードは、ワークフローを失敗させます。

安定版の build と validation のジョブは `contents: read` を保ちます。昇格中に Full Suite が呼ばれることはありません。別個の準備ジョブは、タグを予約するために `contents: write` を、そのビルドをディスパッチするために `actions: write` を持ちます。公開のあと、メタデータの同期はメタデータのブランチをプッシュするために `contents: write` を持ちます。これらのジョブは `GITHUB_TOKEN` を使います。最終的な公開は、保護された `release` 環境に残ります。

## リリースの作成

[Promote a preview to production](../../DEVELOPERS.md#4-promote-a-preview-to-production) を使います。公開済みのプレビューのタグを選び、最終の安定版バージョンを選び、そのリリースノートと、自分のマシンで作成した貢献者リストを供給します。ディスパッチされた安定版ビルドを追い、その後、生成されたメタデータのみの PR を開いて、`main` にバージョンを記録します。

公開の前にビルドが失敗した場合は、失敗したジョブを再実行するか、同じ準備されたタグで Release をディスパッチします。リトライが既存のタグを別のコミットに移すことは決してありません。リリースがすでに存在する場合は、リトライの前にそれを検査します。公開されたアセットを暗黙に置き換えることは決してしません。修正は新しいバージョンで配布します。メタデータの同期は自身のリトライを持ち、公開されたリリースを取り消すことはできません。
