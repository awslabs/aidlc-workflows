# ルールと学習ループ

ルールは、エージェントがあなたのプロジェクトでどう働くかを形づくる、持続する散文の指示です。学習ループは、それらのルールがどう書かれるかです。ワークフローの間にエージェントを直し、ステージの承認ゲートでその修正を確認すると、フレームワークがそれを保存するので、同じ修正が二度要ることはありません。

この章は、利用者向けの案内です。ルールがどこにあるか、五つの層がどう積み重なるか、学習ループがどう修正をとらえるか、そしてセンサーがルールと並んで決定的なもう一つの意見をどう与えるかを扱います。スキーマレベルの仕組みは、各ステップで開発者リファレンスへ相互リンクします。

---

## ルールのあらまし

ルールは、ワークスペースルートの、手で編集できる一つの集合として、アクティブなスペースのメモリ層 `aidlc/spaces/<active-space>/memory/` に Markdown ファイルとしてあり、すべてのハーネスがそのネイティブのインクルード（Claude の `@` インポートのスタブ、Kiro CLI のリソースか IDE の steering、Codex でのエンジンのステップごとのルール配送、Cursor の常に適用される `.cursor/rules/aidlc.mdc` ルール、opencode の `instructions` の glob、Copilot の `AGENTS.md` の `@` インポート）を通じて読みます。各ファイルは、そのスコープにちなんで名付けられます。

```
aidlc/spaces/<active-space>/memory/
├── org.md                 # framework + organization-wide defaults
├── team.md                # your team's affirmed practices
├── project.md             # this project's specialization
└── phases/
    ├── ideation.md
    ├── inception.md
    ├── construction.md
    └── operation.md
```

ファイルの中に `scope:` フィールドはありません。スコープはファイル名から来ます。`org.md` はフレームワークのデフォルト（トランクベース開発、テストの姿勢、walking-skeleton のポリシー）を帯びます。`team.md` は、あなたのチームが確認したものを抱えます。`project.md` は、この一つのプロジェクトに固有のものを抱えます。四つの `phases/<phase>.md` ファイルは、あるフェーズのすべてのステージに当てはまるルールを帯びます。たとえば、inception フェーズのルールは、すべてのアーキテクチャ判断が少なくとも二つの代替案を文書化することを要します。

各ファイルは、話題の見出し（`## Way of Working`、`## Testing Posture`、`## Deployment`、`## Code Style` など）の下の、素の散文です。あなたがそれらを読み、手で編集でき、フレームワークが学習ループを通じてそれらに書き込みます。

スキーマ、ファイル名からスコープへの表、リゾルバの仕組みは、開発者リファレンスの [ルールシステム](../reference/08-rule-system.md) に文書化されています。

## 五層の連鎖

ルールは、すべてのワークフローの開始で、五層の連鎖を通って解決します。

```
org → team → project → phase → stage
```

モデルは **strict-additive** です。当てはまるすべてのルールがエージェントのコンテキストに現れます。実行時に黙って落とされたり上書きされたりすることはありません。org のデフォルト、team のやり方、project の特化が連結されます。合致するフェーズのルールは、ステージがすでにそのフェーズを宣言しているので付きます。（五つ目の層、ステージごとのルールは、今後のリリースのために確保されています。）

これは以前のバージョンからの意図した変更です。`overrides:` ブロックも `enforcement:` キーワードも、もうありません。当てはまるすべての層が一度に現れ、orchestrator は、実行時のリゾルバにそれを調停させるのではなく、受け入れ時に保つ learning の衝突を確認するよう求められます（下の [受け入れ時の衝突の確認](#admission-time-conflict-checks) を参照）。

連鎖の **選択** は、フレームワークがあなたのステージの定義・ルール・センサーを一つのグラフにコンパイルするとき、**一度** 解決されます。ワークフローはそのコンパイル済みのグラフを読みます。グラフは、どのルールファイルが各ステージに当てはまるかを記録します。エンジンが実行の途中でディレクトリの連鎖を歩き直すことは決してありません。ただしファイルの **内容** は凍結されません。各ステージが走る前に、エンジンは選ばれたファイルの現在のテキストを読み、それを届けます。そのコンパイルの境目は、planes モデルが説明するものと同じです。この章の末尾の [Planes: どう噛み合うか](#planes-how-it-fits-together) を参照してください。

## 学習ループ

学習ループは、一度きりの修正を持続するルールに変える仕組みです。ほとんどのステージの実行は何も足しません。それは健全です。ループは、あなたがステージでエージェントを直したとき、または次回に向けて何かを保つよう求めたときだけ入ってきます。

learnings がオンのとき、ループにはあなたが見る三つの瞬間があります。あなたがエージェントを直す（または何かを保つよう求める）、エージェントがその修正を次回に向けて保つかを一度たずねる、そしてフレームワークがあなたが保つものを書きます。何も直されていないとき、あなたは何もたずねられません。ステージはその要約からそのまま承認の質問へ進みます。learnings がオフのとき、これらは何も走らず、日記も保たれません。

### memory.md の日記

learnings の儀式がオンのとき、フレームワークは、ステージが走る間、`<record>/<phase>/<stage>/memory.md` に続いていく観察のログを保ちます。intent の記録ディレクトリ `aidlc/spaces/<space>/intents/<YYMMDD>-<label>/` の下です。Unit ごとに一度走るステージは、Unit ごとに一つを、その Unit の文書の隣の `<record>/construction/<unit>/<stage>/memory.md` に保つので、`construction/` は Unit のフォルダと、一度だけ走るステージ（Build and Test、CI Pipeline）のフォルダを抱えます。それらを動かした更新の前に始まった作業は、そのメモをある場所に保ち、それらは依然として読まれます。エンジンは、run-stage の指示を出すとき、出荷されたテンプレートからそれを作り、orchestrator があなたのためにそれを保ちます。手で編集することはありません。エントリは、四つの標準の見出しの下に入ります。

- **Interpretations** — ステージの散文があいまいなところでエージェントが下した選択
- **Deviations** — エージェントが意図してステージの散文から離れたところと、その理由
- **Tradeoffs** — 考えた代替案と、選んだ理由
- **Open questions** — 次の実行の前に確認すること、またはまだ不確かな文脈

各エントリはタイムスタンプを帯びます。日記は、エージェント自身の推論のステージの記録です。保つものとしてあなたに差し出されることは決してありません。

### 修正の後の質問

エージェントを直したステージの承認の質問の前に、エージェントは、次回に向けて効く各修正について、あなたの言葉でたずねます。

- あなたがステージの承認で変更を求め（Request Changes）、エージェントがそれをした場合: 質問は、承認が再びたずねられる前に来ます。
- または、エージェントが働く間にしたことや前提としたことを、あなた自身の言葉で直した場合。

一度きりの修正（打ち間違い、間違った名前、一つの値）はたずねられません。あなたがエージェントを直したか、そしてそれが次回に向けて効くかは、どの返信も読むのと同じく、あなたの言葉のエージェントの読みです。語のリストがそれを決めることはありません。各修正は一度たずねられます。

エージェントにはっきりと何かを保つよう求めると（「approve, and next time use the shared fixtures」）、エージェントは質問なしでそれを保ち、どこに行ったかを一行で伝えます。チームを名指ししない限りこのプロジェクトのルールなので、動かしたり取り出したりできます。

### どう見えるか

Intent Capture の承認で、在庫の品目を SKU と呼ぶようエージェントに伝えた後（短くし、描画の文字はプレーンテキストで示しています）:

```text
 Keep for next time
 You asked me to call a stock item a SKU in every document, never a product. Keep that for next time?
 > 1. Yes, for this project
   2. Yes, for the team
   3. No
```

**Yes, for this project** で、`aidlc/spaces/default/memory/project.md` が、エージェントがあなたの修正から言葉にしたやり方の行で終わります。

```text
## Corrections
...
- Call a stock item a SKU in every document, never a product. (learned 2026-10-13) <!-- cid:... -->
```

そして監査シャードがそれの行を得ます。

```text
## Rule Learned
**Timestamp**: 2026-10-13T10:41:30Z
**Event**: RULE_LEARNED
**Stage**: intent-capture
**Candidate-ID**: c1
**Content-Hash**: 3a3aa8df...
**Destination**: <project-dir>/aidlc/spaces/default/memory/project.md
**Heading**: ## Corrections
**Source**: user_addition
```

AI-DLC が読む値を設定する保たれた行（`## Testing Posture` の下の `Methodology: tdd` や `Ordering: ...`、`## Guard Policy` か退役した `## Change Control` の下の `Mode: strict`）は、代わりに日付を `<!-- learned 2026-10-13 -->` として帯びるので、値はあなたが保ったものそのものです。

保たれた行は、[次の当てはまるステージから効く](#applies-from-the-next-applicable-stage) が説明するとおり、次のステージから効きます。

### 保つ learning はどこへ行くか

ファイルのパスも見出しも、あなたが選ぶことはありません。あなたが保つ修正は、`aidlc/spaces/<active-space>/memory/project.md`（**Yes, for this project**）か `memory/team.md`（**Yes, for the team**）に、エージェントがそれに選ぶ話題の見出し（`## Corrections`、`## Testing Posture`、`## Forbidden`）の下に、やり方として入ります。

デフォルトのスコープは **project** です。**Yes, for the team** は、教訓がこの一つのプロジェクトを超えて当てはまるとき、保つ learning を `memory/team.md` に広げます。org へ広げる道はありません。org のルールは、フレームワークが出荷するか、別のプロセスを通じて組織が書くので、学習ループが org のスコープで書くことは決してありません。いちばん狭いスコープをデフォルトにすることで、一つのプロジェクトの驚きが、うっかり組織全体のルールになるのを防ぎます。

確認された learning *は* やり方です。practices-discovery が確認するのと同じアクティブなスペースのメモリファイル（`aidlc/spaces/<active-space>/memory/project.md`、`team.md`）に入ります。別の続いていく `*-learnings.md` の面はありません。それらのファイルへの二つの道は、ライフサイクルで違います。practices-discovery はセクション全体を決定的に確認し、学習ループはゲートを通じて、日付のついた話題の見出しのエントリを一度に一つ足します。

保つ learning が、ルールではなく **センサーの綴じ** のとき（新しい決定的な確認がステージの出力で発火してほしいとき）、フレームワークは二つの書き込みのインストールをアトミックに行います。センサーのマニフェストの足場を作り、元のステージのインポートのリストに新しいセンサーの id を足します。質問・あなたの答え・結果のファイルの書き込みは、それぞれ監査行を残すので（書き込みのものは `RULE_LEARNED` か `SENSOR_PROPOSED`）、ルールが黙ってインストールされることは決してありません。

### 受け入れ時の衝突の確認

保つ learning がディスクに入る前に、ゲートのプロトコルは、orchestrator にそれを `memory/org.md` の合致するセクションと比べるよう求めます。これはセクションレベルの LLM の確認です。提案されたエントリが org のルールに反すると、orchestrator は衝突する文をインラインで引用し、エントリを直すか、飛ばすか、org ルールの所有者にエスカレートするかを、あなたに求めます。衝突がはっきりしない、またはユーザーがエスカレートした選択だけが、それから決定的なライターに渡されます。`aidlc-learnings.ts persist` は、`org.md` を独立に見ず、衝突を判断せず、渡された選択を受け入れます。だから org との矛盾のエスカレーションは、リゾルバの入力を一貫して保つための監査の助けであって、強制の境界ではありません。

practices-discovery の確認ゲートは、この org 衝突の確認を走らせません。その昇格は、あなたの確認で正当化される、決定的なセクションの置き換えです。そして org ポリシーが、team や project のルールがすでにディスクにある *後* に変わったとき、`/aidlc --doctor` が求めに応じて、ありうる drift を表に出します。見出しが `org.md` も埋める、埋まったセクションを持つ team や project のファイルそれぞれについて、ファイルと見出しを挙げ、そこの org のセクションの最初の文を引用するので、あなた（またはエージェント）が、二つが食い違うかを判断できます。比べるのは見出しであって、意味までは見ません。doctor の確認は参考で、決してブロックしません。二つの doctor の参考の行は [CLI コマンド](12-cli-commands.md) と [困ったとき](15-troubleshooting.md) で説明しています。

### 次の当てはまるステージから効く

保つ learning は、すでに選ばれたルールファイル（`project.md` か `team.md`）に足され、エンジンは各ステージの配送の前に選ばれたファイルの現在のテキストを読みます。だから learning は、**現在の** ワークフローの次の当てはまるステージでエージェントに届きます。それがとらえられたステージは、会話であなたの修正をすでに得ており、その後のすべての配送が書かれたルールを運びます。後のワークフローもそれを受け取ります。

次のコンパイルを待つのは **選択** です。真新しいルールファイルが連鎖に入り、新しいセンサーが綴じて発火するのは、ステージグラフが次にコンパイルされるときだけです。これは、ルーターが BGP から得る安定性の性質です。コンパイルされた選択は、パケットが飛んでいる途中で再計算されません。選ばれたファイルの中のルールの *テキスト* は各ステージで新しく読まれるので、あなたが保った修正が、実行の残りの間ずっと遊んでいることはありません。

## 実践例: 銀行のプロジェクト

具体的な通し解説が、ループを端から端まで示します。

Sam が銀行のプロジェクトで `/aidlc feature` を実行します。ワークフローは `requirements-analysis` に着きます。Sam は「the transaction shouldn't duplicate on retry」というステークホルダーのメモを書きます。銀行の取引、つまり処理されている支払いの意味です。product agent は「transaction」をデータベースのトランザクションと読み、メモを ACID セマンティクスの要件と解釈します。Sam がそれを直します。エージェントが成果物を更新して続けます。

フレームワークのどこも、これを予測しませんでした。銀行自身の用語についてのルールも、一般的な用語対ドメインの用語の衝突をとらえるセンサーもありません。エージェントは単にあいまいさにぶつかりました。

**1. Sam の修正が効くものです。** Sam の言葉（「transaction」は処理されている支払いを意味する）は、エージェントが前提としたことを、プロジェクト全体で効くように直します。それについてのエージェント自身の日記の行は、ステージの記録に残ります。そこから何も差し出されません。

**2. ステップが一度たずねます。** ステージが終わります。承認の質問の前に、エージェントがたずねます。「You asked me to read 'transaction' as the payment being processed, not a database write. Keep that for next time?」。Sam は **Yes, for this project** を選びます。承認の質問で Sam はまた「approve, and next time always say 'bank customer' for the banking customer entity」と言います。エージェントはそれも、二つ目の質問なしで保ち、それが `memory/project.md` のこのプロジェクトのルールに行ったと一行で言います。

**3. 衝突の確認が走ります。** orchestrator は、両方のエントリを org のやり方（`memory/org.md`）とセクションレベルの LLM の確認として比べます。「transaction」も「bank customer」の用語も org のルールが覆っていないので、両方が通ります。それから決定的なツールが両方の行を、由来とともに `memory/project.md` に書き、監査ログがそれぞれに `RULE_LEARNED` イベントを記録します。

**4. 現在のワークフローがそれらを先へ運びます。** ステージが承認し、ワークフローは `user-stories` へ進みます。`memory/project.md` はすでにこのワークフローのコンパイルされた選択にあり、エンジンは各ステージの配送の前にそのテキストを読み直すので、`user-stories` 以降、新しい行はこの実行の残りの間、エージェントのコンテキストにあります。

**5. 後のワークフローもそれらを受け取ります。** その日の後で Sam が `/aidlc bugfix` を実行します。`memory/project.md` はすべてのステージの選択にある（org・team・project のファイルはすべてのステージに付きます）ので、bugfix ワークフローのステージ一から、エージェントは「transaction」が支払いを意味し、顧客のエンティティが「bank customer」だと知っています。

コストは一度払われ（一つの質問、一つのファイルの書き込み）、ディレクトリの歩きのファイル一つ分の値段で、これからのすべてのワークフローで返ってきます。

## センサー: 決定的なもう一つの意見

ルールは、エージェントが読む散文です。センサーは、エージェントがステージの出力を書くと自動で走る決定的な確認です。ルールが「user stories follow Given/When/Then format」と言うところで、センサーは、必要な見出しが実際にファイルにあることを、バイト単位で検証できます。ルールはエージェントをステージへ前へ送り、センサーはエージェントが実際に生んだものを後ろへ返します。

### センサーがどう発火するか

エージェントがステージの間に出力ファイルを書くか編集すると、PostToolUse フックが、どのセンサーがそのステージに当てはまるかを確かめ、合致する各々を走らせます。合致はファイルの形によります。コード品質のセンサーは `**/*.{ts,js}` を分析すると宣言するので、TypeScript と JavaScript の書き込みでだけ発火します。どのステージの出力でも発火する文書の形のセンサーは、フィルタを省きます。下の表の最初の三つ、ゲートで発火するセンサーは、代わりにステージがその承認ゲートに着くとき、そのステージの宣言された出力ファイルのうちフィルタが受け入れるものごとに一度走ります。その参考の確認は、その前に一度も走ります。ステージの文書が書かれ、そのレビュー（レビューがないときはゲート）へ渡されるときです。エージェントは、まず見つかったものを得て自分のしくじりを直すので、レビューとゲートは整えられた文書を見ます。ゲートが、Construction の自律性の下でツールが自分で承認するものであるとき、そこでブロックするセンサーだけが走ります。参考の指摘は、読む人がいないでしょう。ワークフローの間に手でセンサーを呼び出すことはありません。センサーはステージの書き込みとそのゲートに乗っていきます。

出荷される六つのセンサーは **参考** です。失敗したものは監査行と、何が欠けているかをまさに指す詳細ファイルを生みますが、ステージの承認ゲートをブロックしたり、あなたのワークフローを止めたりはしません。ゲートが開くと、エージェントは、どの確認がまだステージの出力で指摘を報告するか、そして走れなかった確認（スクリプトがクラッシュした・始められなかったので、何も確認しなかった）はどれかを一行で、あなたに伝えるので、あなたはそれを踏まえて決めます。Sensors がオフに切り替えられていると、確認について何も言われません。

あなたが足すセンサーは、代わりに **ブロックする** ものにできます（マニフェストの `default_severity: blocking`）。ゲートでブロックするセンサーが通らないと、ゲートは開きません。エージェントが **Fix findings** か **Override blocking sensors** を申し出て、上書きがあなたの選択として記録されます。自律の Construction では、実行が代わりにそこで止まり、上書きを選ぶと、まず Construction を Bolt ごとにあなたの承認で止まる状態に戻します。[センサーシステム](../reference/07-sensor-system.md) を参照してください。

### 監査ログで何が見えるか

センサーの活動は、intent の `audit/` シャードに `Sensor Fired`・`Sensor Passed`・`Sensor Failed` の行として、そしてスクリプトがクラッシュした・始められなかった確認には `Sensor Could Not Run` として現れます。失敗した行は、具体的なギャップ（欠けた見出し、参照されない上流の成果物、lint のエラー）を挙げる詳細ファイル（たとえば `<record>/.aidlc-engine/sensors/intent-capture/claim-sources-0719478d.md`、その行のセンサーと発火 id にちなんで名付けられる）にリンクします。通る確認は、上の実行からのこのような行を残します。

```text
## Sensor Passed
**Timestamp**: 2026-10-13T10:41:35Z
**Event**: SENSOR_PASSED
**Fire id**: 0d3ee5cc
**Sensor ID**: claim-sources
**Stage slug**: intent-capture
**Output path**: aidlc/spaces/default/intents/261013-inventory-api/ideation/intent-capture/intent-statement.md
**Duration ms**: 190
```

監査ログは [状態と監査](10-state-and-audit.md) で扱います。

### 六つのフレームワークセンサー

六つのセンサーがフレームワークとともに出荷されます。

| Sensor | Fires on | Checks |
|--------|----------|--------|
| `claim-sources` | Intent Capture の記録ディレクトリの出力 | すべての主張が見えるソースタグを持つ。登録された説明・ワークフローのスコープ・メモリのテキストが正式な入力に合う。保たれた前提が明示的な確認に正確に合う |
| `required-sections` | どの記録ディレクトリの markdown 出力も、加えて reverse-engineering の `codekb/` ファイル | あなたのチームが `memory/templates/` に書いたとき、出力がそのテンプレートの `##` 見出しを含む。テンプレートがなければ何も要らない |
| `upstream-coverage` | どの記録ディレクトリの markdown 出力も、加えて reverse-engineering の `codekb/` ファイル | ステージの成果物（集合として評価される）が、ステージが要すると宣言する（`required: true`）か `cited: true` と印す各上流の成果物を、slug・wikilink・生むステージのディレクトリパスで参照する |
| `traceability` | `traceability.json` のステージ成果物 | 安定した上流の ID が宣言され覆われ、ステータスとターゲットが有効で、決定的な下流のターゲットがある |
| `linter` | `.ts` / `.js` のコード出力 | あなたが設定した linter（デフォルトは ESLint）を包む |
| `type-check` | `.ts` / `.tsx` のコード出力 | あなたが設定した型チェッカー（デフォルトは `tsc`）を包む |

各ステージは、どのセンサーがその出力で発火するかを宣言します。自分のセンサーを足せます。`.claude/sensors/` の下にマニフェストを書き、それを走らせるべきステージにその id を足します。ゲートで一つを確認すると、学習ループがあなたのためにセンサーをインストールすることもできます。マニフェストの形式、ステージごとのマトリクス、書く通し解説は [センサーシステム](../reference/07-sensor-system.md) にあります。自分のプロジェクトに足すには [カスタマイズ](13-customization.md) を参照してください。

## Planes: どう噛み合うか

上のすべてを、planes を考えずに使えます。ですが、その土台の設計はネットワーキングから規律を借りており、それを名付けると、コンパイルの境目（ワークフローの開始で固定されるものと、ライブで読まれるもの）がはまります。

現代のルーターは、その働きを三つの plane に分け、AI-DLC はその分け方をなぞります。

- **Control plane** — 何が走るべきかの *スキーマ*。ステージの定義、ルール、センサー。ネットワーキングの言葉では、これは経路の計算です。設定を与えられて、何がどこに当てはまるかを決めます。control plane は、一度走るので、遅くて賢くてよいのです。
- **Data plane** — *実際の実行*。ステージの実行、エージェントの呼び出し、intent の記録ディレクトリのファイル。ネットワーキングの言葉では、これはパケットの転送です。速く、繰り返し、検索で。data plane は解決された答えを読み、それを導き直しません。
- **Management plane** — *観察と設定* の面。`/aidlc --doctor`、監査ログ、`CLAUDE.md`。ここで設定し、ここで問い合わせます。人のペースで。

control plane は、あなたのルールとセンサーをグラフに **一度** コンパイルします。data plane は、実行の残りの間、そのグラフから事前に解決された答えを読みます。コンパイルされた答えは *選択* です。どのルールファイルとセンサーがどのステージに付くかです。選ばれたルールファイルのテキストは配送時に読まれるので、すでに選ばれたファイルの保つ learning は、再コンパイルなしで次のステージに届きます。新しいファイルや新しいセンサーの綴じはトポロジーの変更で、次のグラフのコンパイルを待ちます。結果は、再現できる実行と、再起動後のきれいな回復です。

ユーザーとして、あなたはたいてい一度に一つの横のスライスに触れます。ワークフローを走らせる、learning をとらえる、チームのやり方をカスタマイズする、何が起きたかを監査する。各スライスは、あなたにそれを考えさせずに、下の planes に触れます。完全なモデル、コンパイルの境目、回復の性質は [Plane アーキテクチャ](../reference/02-plane-architecture.md) に、それが生むテレメトリの成果物は [Runtime Graph](../reference/13-runtime-graph.md) に文書化されています。
