# 用語集

AI-DLC の用語の正式な定義です。ユーザーガイドと開発者リファレンスの全ドキュメントは、ここに挙げた用語を一貫して使います。

---

| 用語 | 定義 |
|------|-----------|
| **Agent** | 出荷される 14 のペルソナのうちの 1 つです。内訳はドメイン専門家 11、レビュー専用エージェント 2、そして adaptive-workflows のコンポーザーです。conductor が、専門のステージ・レビュー・構成の役割ごとに各エージェントを起動します。 |
| **Approval gate** | 完了した作業に対する判断です。対象はステージ、検証済みの Unit、または完了した swarm バッチです。human-required なゲートは、あなたの実際の回答を待ちます。checkpoint を有効にしたワークフローは、記録された許可のもとで通常の完了を自動承認する場合があります。ただし Plan Approval、有効な summary 確認、検証コマンドの選択、skeleton の承認は人間の判断のままです。summary 確認は `directive.ceremony.summary_confirmation === "on"` のときにだけ適用されます。初期化と完了のみの記帳は、人間への承認質問を増やしません。 |
| **Autonomy mode** | `Construction Autonomy Mode` として保存される、明示的な承認の設定です。値は `unset`、`gated`、`autonomous` のいずれかです。対象となる checkpoint ワークフローでは、「Continue automatically」が `autonomous` を、「Review each checkpoint」が `gated` を記録します。これは実行順や swarm の選択とは独立に、通常の完了質問を制御します。Plan Approval、有効な summary 確認、検証コマンドの選択、skeleton の承認、そして失敗は、なお人間を必要とします。既存のワークフローは従来のゲート方針を保ちます。 |
| **Bolt** | 1 つ以上の依存関係でつながった Unit にまたがる、計画済みの Construction 配信スライスです。Unit、その worktree、swarm バッチとは別物です。Delivery Planning が、グループ分け、Definition of Done、確度の仮説、所有権を記録します。実行時の順序は Unit の DAG と記録された反復の選択に従い、`bolt-plan.md` はそれらを置き換えません。Build and Test と CI Pipeline は、完了した Unit 作業全体に対して一度だけ走ります。 |
| **Artifact** | ステージが生成し、intent の record ディレクトリ（`aidlc/spaces/<space>/intents/<YYMMDD>-<label>/`）に保存するファイルです。多くは `requirements.md`、`code-summary.md`、`initiative-brief.md` のような Markdown 文書です。`traceability.json` のように JSON のものも一部あります。 |
| **Audit trail** | intent の record ディレクトリ内 `audit/` にある追記専用のイベントログです。clone ごとのシャード（`<host>-<clone>.md`）として書かれ、読み手が glob してタイムスタンプ順にマージします。132 種類のイベントを ISO タイムスタンプ付きで記録し、intent から production まで完全にトレースできます。 |
| **CLI tool** | この実装が実行する外部のコマンドラインユーティリティです。native インストールでは不要です（**Native channel** を参照）。copy チャネルでは `bun` が必要です。Claude Code tools と混同しないでください。 |
| **Claude Code tool** | Read、Write、Edit、Bash、Glob、Grep、Task、AskUserQuestion のような Claude Code の組み込み機能です。エージェントは既定でセッションのツールセット全体を継承します。任意の `tools:` 許可リストで範囲を狭められ、`disallowedTools: Task` が出荷される唯一の制限です。 |
| **Codex** | OpenAI Codex CLI の harness です。今日ある AI-DLC の harness ディストリビューションの 1 つです。ソースビルドは、`core/` と `harness/codex/` から gitignore されたローカル projection を `dist/codex/` に生成します。リリースは `runtime/codex/` 配下に持ちます。`$aidlc` で起動します。[AI-DLC on Codex CLI](harnesses/codex-cli.md) を参照してください。 |
| **Command** | AI-DLC のユーザー向けの呼び出しです。harness のチャットコマンドは、ワークフローに `/aidlc`（Codex では `$aidlc`）を使います。native の `aidlc` コマンドは、プロジェクト、診断、plugin、machine-lifecycle の各ルートを提供します。 |
| **Compaction** | コンテキストウィンドウが埋まったとき、Claude Code が以前の会話コンテキストを自動で要約する処理です。この実装は、`aidlc-state.md` と audit trail を通じて、compaction をまたいで状態を保持します。 |
| **Conductor** | `/aidlc` セッションそのもの（`SKILL.md`）です。薄い転送ループを回します。次の手を **Engine** に問い合わせ、それを実行し（ステージの実行、あなたへの質問、swarm のfan-out）、結果を報告し、これを繰り返します。ルーティングではなく実行品質を担います。[Engine and Skill System](../reference/17-skill-system.md) を参照してください。 |
| **Construction Verification Command** | すべての Unit/バッチ checkpoint で再利用される、intent レベルのプロジェクトチェックです。ツールが所有する `VERIFICATION_COMMAND_RECORDED` レシートが、人間の **Approve**（本人の返信。エージェントが読み、本人の正確な言葉を保持し、質問したチャット、または最新の質問である間は新しいチャットで）を、正規化し trim した 1 行コマンドの SHA-256 に、型付き state setter が記録する前に紐づけます。無関係な返信、**Request Changes**、別の質問への返信は、このレシートを認可しません。state フィールドだけでは実行を認可しません。Delivery Planning がこれを提案するか、greenfield の先送りの後に最初の checkpoint が尋ねます。以後の変更はすべて新しい人間のレシートを必要とします。証跡はダイジェストと表示ラベルを保持し、生のコマンドテキストは保持しません。 |
| **Control loop** | ステージを操舵し検証する、**Rules**（作業前に適用される標準的な判断）と **Sensors**（出力に対して発火する決定的なチェック）の feedforward/feedback の組み合わせです。（**Harness** の CLI ディストリビューションの意味とは別物です。両者はかつて共に「harness」と呼ばれていました。） |
| **Copy channel** | バージョン付きリリースの Bun 形式 `aidlc-copy-runtime-X.Y.Z.tar.gz` から、完全な `runtime/<harness>/` ルートをコピーする手動のプロジェクトインストールです。Bun を必要とし、native の `aidlc` 実行ファイルは必要としません。 |
| **Core** | `core/` にある、手書きで harness 非依存の信頼できる情報源です。engine、stages、agents、rules、scopes、sensors、knowledge、hooks、session skills を含みます。どの harness ディストリビューションもここから生成されます。編集はここで行い、`dist/` では行いません。 |
| **Cursor** | Cursor の harness（cursor.com）です。今日ある AI-DLC の harness ディストリビューションの 1 つです。ソースビルドは、`core/` と `harness/cursor/` から gitignore されたローカル projection を `dist/cursor/` に生成します。リリースは `runtime/cursor/` 配下に持ちます。1 つのツリーが Cursor IDE と Cursor CLI（`agent`）の両方に対応します。14 のペルソナは `.cursor/agents/` の native subagent で、orchestrator・runner・ユーティリティのショートカットは `.cursor/skills/` の native skill です。Cursor は `@` インポートを展開しないため、`.cursor/rules/aidlc.mdc` が標準的なメソッド層を指し、4 つの `aidlc-phase-*.mdc` rule が phase 層を指します。`/aidlc` で起動し、`/aidlc-status`、`/aidlc-jump`、`/aidlc-scope` のショートカットがあります。[AI-DLC on Cursor](harnesses/cursor.md) を参照してください。 |
| **Depth** | 各ステージがどれだけ詳細を生成するかを制御する、3 つの詳細レベル（Minimal、Standard、Comprehensive）の 1 つです。scope には既定の depth があり、任意の approval gate で上書きできます。[Scopes, Depth, and Test Strategy](05-scopes-and-depth.md) を参照してください。 |
| **Directive** | **Engine** が各 `next` で発行する、型付きの指示です（例: `run-stage`、`ask`、`print`、`done`、`invoke-swarm`）。**Conductor** に次に何をすべきかを正確に伝えます。[Engine and Skill System](../reference/17-skill-system.md) を参照してください。 |
| **Distribution** | 1 つの harness 向けに生成された projection です。**Packager** が **Core** から生成します。ソースビルドは、gitignore されたローカルの `dist/claude/`、`dist/codex/`、`dist/copilot/`、`dist/cursor/`、`dist/kiro/`、`dist/kiro-ide/`、`dist/opencode/` ツリーと、native の `dist-release/<harness>/` の対応物を実体化します。リリースは、手動 copy 向けに out-of-band の `aidlc-copy-runtime-X.Y.Z.tar.gz` に `dist/` projection を、native インストール向けに manifest 掲載の `aidlc-runtime-X.Y.Z.tar.gz` に `dist-release/` projection を持ちます。メンテナーが生成物を手で編集することはありません。 |
| **Engine** | 決定的なオーケストレーションツール（`aidlc-orchestrate.ts`。サブコマンドはちょうど 6 つ: `next`、`continue`、`report`、`park`、`team-board`、`wait`。`continue` は内部の steering トランスポート、`team-board` は読み取り専用の Team Construction クエリ、`wait` は dispatch された作業を待つ有界の読み取り専用の待機です）です。ステージ間のルーティングすべて（scope 解決、ステージの順序付け、ジャンプ、resume、ゲート状態）を担い、**Conductor** が実行する型付き **Directive** を発行します。[Engine and Skill System](../reference/17-skill-system.md) を参照してください。 |
| **External tool** | ステージが使うサードパーティのツールまたはサービスです（例: AWS CLI、Maven、npm）。Claude Code tools とは区別されます。 |
| **Fence** | 実行中のワークフローのどのステップも求めない操作を拒否するガードです。5 つあります: plan approval、review freeze、state transition、reviewer read scope、human presence です。最初の 4 つは、1 つの作業単位について `/aidlc config set guard.<fence> off\|on` で切り替えられます。`on` は、方針で下げられた fence を上げられます。reviewer-scope の切り替えは、dispatch された reviewer の read/search の境界に影響しますが、claim された team checkout が別の Unit の `construction/` サブツリーに書けないという必須のルールには影響しません。エージェントは、本人がタイプした lowering 切り替えに対して setter を実行します。`--intent`/`--space`、またはチャットのワークフロー選択を用い、state と audit 行を書き、何が変わったかを示します。存在しない名前の intent は拒否されます。state ファイルが無いとき、行でタイプされた設定（Guard Policy、plan approval、fence 切り替え、その他の intent 設定）は、このチャットが次に始める作業単位に適用されます。本人が自分の言葉で求めるか、ガードの `lower-fence` 選択肢を選ぶと、エージェントが本人の代わりに setter を実行します。CLI の setter は、最後の判断以降に本人のターンが記録にあるとき下げます。すでに off の fence や同一の方針語（source が `you`）には key が不要で、そのターンが無い場合は本人が自分の端末でタイプしたコマンドが本人の行為として下げます。それ以外は、fixture/harness 起動の presence バイパスを通じて `fenceKeyBypassed` のみが CLI の lowering を許します。memory で保持された strict は最初に拒否し、以前の `Guards Off` エントリを上書きします。無人実行は prompt 時の適用を抑制し、CLI の lowering を拒否します。hook は Windows でも走るため、prompt を転送するすべての harness がタイプされた切り替えに対応します。モデルのツールは hook を呼び出せず、`aidlc/.aidlc-sessions/` やいかなる `.aidlc-plan-approval/` ディレクトリにも書けません。これは [state-transition guard](../reference/06-hooks-and-tools.md#pretooluse-aidlc-state-transition-guardts) が強制します。Codex は `/aidlc` の代わりに `$aidlc` を使います。human presence には作業単位ごとの切り替えが無く、`AIDLC_SKIP_HUMAN_PRESENCE_GUARD=1` でのみ下げられます。退いた fence は、audit ledger が存在するとき `GUARD_STOOD_ASIDE` の audit 行を記録します。通知の配信は harness に依存します。**Guard Policy** を参照してください。 |
| **Guard Policy** | intent ごとの設定（`strict`、`relaxed`、`off`）で、1 つの作業単位についてガードがどこまで退くかを決めます。入力の変更がその承認を再開するか、どの fence が保たれるかを決めます。scope の既定（scope ファイルが何も宣言しなければ off）から解決し、次に intent 自身の state 行で解決します。`Mode: strict` を宣言する memory 層があれば両者に優先します。memory 層の `Mode: relaxed` または `Mode: off` は、scope 由来の値を置き換えます。state が `Guard Policy` と廃止された `Change Control` を異なる語で両方持つ場合、次の `next` が、記録上で最後に設定されたと示される一方（それが無ければ本人のもの、scope のもの、より厳しいもの）を唯一の行として保つまで、strict が source `conflicting state lines` で適用されます。両者が一致すれば `Guard Policy` を使い、次の policy 書き込みで廃止された行を削除します。エージェントは `/aidlc --guard-policy relaxed\|off`、または平易な言葉での同じ要求に対して setter を実行します。strict は conductor が直接設定できます。チャットからの明示的な `intent create --guard-policy relaxed\|off` は、scope 既定を下回るとき拒否されます。作業単位を作成し、本人が低い値を求めたときにエージェントが setter を実行します。scope 既定は尋ねずに適用されます。Compose 作成は、plan が走る出荷 scope（マッチした plan の scope、またはカスタム plan のベース）から Guard Policy を読み、scope ファイルは書きません。conductor は `strict` または `relaxed` に `--guard-policy` を渡し、これは低い scope 既定を上げます。`off` には決して渡しません。マッチした提案の Guard Policy を下げると、選んだ値を持つ出荷 scope 上のカスタム plan に変換され、上げると plan はマッチしたままです。どちらの場合も intent 作成がそれを適用し、後からの setter は要りません。composer は進行中の intent の値を変えず、代わりに対応する方針変更ルートを挙げます。以前は Change Control と呼ばれており、古い綴りは 1 リリースの間読まれます。**Fence** を参照してください。 |
| **Guardrail** | Rule ファイル内の本文セクション（`## Forbidden`、`## Mandated`、phase-rule の guardrail 見出し）で、規範的な振る舞いの制約を表します。コンテナは Rule であり、「guardrail」はその中の規範的な内容を指します。**Rule** を参照してください。 |
| **Harness** | AI-DLC core の CLI ディストリビューションです。harness 非依存の **Core** がレンダリングされる、1 つの高性能なコマンドラインエージェントです。集合は開いていて増やせます（今日は Claude Code、Kiro CLI、Kiro IDE、Codex CLI、Cursor、opencode、GitHub Copilot）。*注 — このリポジトリでは「harness」が文脈によって 4 つの意味を持ちます:* (1) **この正式な CLI ディストリビューションの意味**、(2) rule+sensor の **control loop**（古い用法。いまは改名済み。**Control loop** を参照）、(3) `harness/<name>/` のソース面ディレクトリ、(4) `tests/harness/` のテストヘルパーディレクトリです。ユーザードキュメントで「a harness」と言えるのは意味 1 だけです。 |
| **Hook** | Claude Code がイベントに応じて自動実行する TypeScript スクリプトです。この実装は 17 の hook を使い、すべて `settings.json` でプロジェクト全体に登録します。内訳はワークフローの背骨（audit ロギング、sensor dispatch、runtime-graph コンパイル、statusline 同期、token 使用量の折り畳み、compaction 時の state 検証、subagent 追跡、turn-end でのループ強制）に加え、session lifecycle、human-turn mint、正確な dispatch-rule 配信、state-transition、reviewer-scope、review-freeze、plan-approval の各ガード、そして statusline コマンドです。ワークフロー固有の作業は自己ゲートします。session-start はプロセスの祖先関係を記録し、エージェントが実行する setter は、タイプされた lowering 切り替えを選択された作業単位に適用するか、チャットが次に始める作業単位のために保持します。 |
| **Inline execution** | 既定の実行モードで、orchestrator がエージェントのペルソナを読み込み、会話内で直接ステージを実行します。リアルタイムのユーザー対話をサポートします。 |
| **Intent** | space の `intents.json` レジストリの 1 行（`{uuid, slug, dirName, scope, repos, status}`）として追跡される作業単位です。固有の [Record dir] を `aidlc/spaces/<space>/intents/<YYMMDD>-<label>/` に持ちます。`<YYMMDD>` はコンパクトな UTC 日付の接頭辞（例: `260624` = 2026-06-24）で、record が時系列に並びます。`<label>` は要求の本質を表す短い kebab-case です。同日・同 label の衝突は数値カウンタ（`-2`、`-3`、…）で解決します。正式で衝突しない id は、レジストリ行に保存される時系列順の UUIDv7 であり、ディレクトリの接尾辞ではありません。engine は最初の `/aidlc` で最初の intent を自動作成します。明示的なセレクタまたはセッションごとのバインディングが、共有の `active-intent` カーソルより先に選択します。**Space**、**Record dir** を参照してください。 |
| **Kiro** | Kiro の harness です。今日ある AI-DLC の harness ディストリビューションの 1 つです。ソースビルドは、gitignore されたローカル projection を `dist/kiro/`（CLI）と `dist/kiro-ide/`（IDE）に生成します。リリースは `runtime/` 配下に持ちます。AIDLC メソッドは、CLI の agent resource、または IDE で常に含まれる steering のライブ参照を通じて、`aidlc/spaces/<active-space>/memory/` から読まれます。`/aidlc` で起動します。[Running AI-DLC on Kiro IDE](harnesses/kiro-ide.md) と [Running AI-DLC on Kiro CLI](harnesses/kiro-cli.md) を参照してください。 |
| **Knowledge** | ステージ開始時にエージェントが読み込む参照資料です。2 層あります。methodology knowledge（フレームワークに同梱され `.claude/knowledge/` にある）と、team knowledge（ユーザー管理の space レベルのドメイン知識。`aidlc/spaces/<space>/knowledge/` にあり、自由形式で、bootstrap 時は空。space 内のすべての intent で共有）です。 |
| **Ladder prompt** | 「Continue automatically」/「Review each checkpoint」の明示的な選択です。対象となる checkpoint ワークフローでは、skeleton-off なら Construction 入口で、skeleton-on なら本物の skeleton checkpoint の後で、選択が記録されていないときにだけ提示されます。オンデマンドの grant/revoke 要求は引き続き利用できます。従来の最初ステージの ladder は、統合された skeleton が構築された証拠にはなりません。 |
| **Learning loop** | ステージ中の修正を、永続的な practice と Sensor に変える仕組みです。ステージ中、orchestrator は観察を `memory.md` に記録します。approval gate でそれらを提示し、どれを残すかをあなたが確認します。確認された learning は各々、`aidlc/spaces/<active-space>/memory/project.md` に practice として書かれ（ワンクリックで `team.md` に昇格）、現行ワークフローの次の該当ステージから適用されます。あるいは新しい Sensor を scaffold し、それは次の stage-graph コンパイルで bind されます。[Rules and the Learning Loop](09-rules-and-the-learning-loop.md) を参照してください。 |
| **Lifecycle** | AI-DLC メソドロジー全体、すなわち AI-Driven Development Life Cycle です。メソドロジーの 1 回の実行が workflow です。公開の native サーフェスは `config`、`doctor`、`version`、`update`、`use`、`uninstall` です。 |
| **Machine lifecycle command** | ユーザーごとのリリースや設定を管理する native `aidlc` ルートです。常にプロジェクトの `.aidlc-version` ピンに従わず、active なバイナリから走ります。プロジェクトのワークフローデータは変更しません。 |
| **Manifest** | harness の `harness/<name>/manifest.ts` です。**Core** をその harness の **Distribution** にどう projection するかを **Packager** に伝える、宣言的な契約です（ディレクトリマップ、rules の rename、authored ファイル、任意の `emit` plugin）。harness を追加する作業は、ほぼ manifest を 1 つ書くことです。 |
| **MCP server** | プロジェクトルート（`.claude/` の隣）の `.mcp.json` で宣言され、Claude Code セッションに provision される外部ツールサーバーです。この実装は 5 つを出荷します。`context7` に加え、4 つの AWS サーバー（`aws-mcp`、`aws-pricing`、`aws-iac`、`aws-serverless`）です。すべてのエージェントは、セッションの全 MCP サーバーを継承します。エージェントごとの付与はありません。エージェントは、`tools:` 許可リストを特定の `mcp__<server>__<tool>` id に狭めることで、あるサーバーの使用を*妨げられ*ます。認証情報を持たないサーバーは、単に利用不可であり、ワークフローを決してブロックしません。[Harness Primitives Mapping — MCP Servers](../reference/14-claude-features.md#mcp-servers) と [Getting Started](01-getting-started.md#mcp-servers-optional) を参照してください。 |
| **memory.md** | `<record>/<phase>/<stage>/memory.md`（intent の record ディレクトリ配下）にある、ステージごとの観察日記です。learnings の儀式が on のときだけ、engine が run-stage directive を発行する際に作成し、orchestrator が保守します（手で編集しません）。Interpretations、Deviations、Tradeoffs、Open questions を記録します。learning loop が approval gate で読む入力です。 |
| **Mob execution** | 有界のラウンドで動く dispatch 済みの mesh（`mode: mob`）です。lead が draft し、互いに見えない collaborator が並行して contribution ファイルを書き、lead が統合し、未解決の判断は人間に行く場合があります。User Stories (2.4) が出荷される mob です。collaborator が off のとき（`enterprise` を除くすべての出荷 scope）、lead は単独で走り、mob ラウンドはありません。 |
| **Multi-repo intent** | 作業が複数の兄弟コードリポジトリにまたがる intent です。リポジトリ集合は作成時に取り込まれます。`--repos a,b` で明示的に、または兄弟の自動検出（`.git` を持つ workspace ルートの直下の子すべて）で取り込み、intent の `intents.json` 行に `repos` として保存します。Construction は各 git 操作を `--repo <name>` で特定のリポジトリに結び付けます。記録されたリポジトリの無い intent は従来の単一リポジトリのケースです（git はプロジェクトディレクトリで走ります）。[Artifacts Reference](14-artifacts-reference.md) を参照してください。 |
| **Native channel** | 推奨されるユーザーごとのインストール経路です。native の `aidlc` バイナリに加え、machine の versions ディレクトリ配下にバージョン一致の harness runtime を置きます。そのインストーラとプロジェクトの bootstrap は、Bun、Node.js、Git を必要としません。Alpine musl ホストは、まず `apk add libgcc libstdc++` で Bun と Node.js の共有 runtime 前提をインストールします。 |
| **Offline package** | ネットワークアクセス無しでインストールするために、丸ごと転送されるリリース資産の集合です。プラットフォームバイナリ、runtime ペイロード、インストーラ、`version.json`、`checksums.txt`、`aidlc-release.intoto.jsonl` の provenance バンドルを含みます。 |
| **opencode** | opencode の harness（opencode.ai）です。今日ある AI-DLC の harness ディストリビューションの 1 つです。ソースビルドは、`core/` と `harness/opencode/` から gitignore されたローカル projection を `dist/opencode/` に生成します。リリースは `runtime/opencode/` 配下に持ちます。engine ツリーは `.aidlc/` に出荷されます（opencode は `.opencode/tools/*.ts` をカスタムツールとして自動インポートするため、engine はそこに置けません）。`.opencode/` は native の外殻（subagent、`/aidlc` コマンド、hook アダプタの plugin）だけを持ち、AIDLC メソッドはプロジェクトルートの `opencode.json` の `instructions` glob を通じて読まれます。`/aidlc` で起動します。[AI-DLC on opencode](harnesses/opencode.md) を参照してください。 |
| **GitHub Copilot** | GitHub Copilot の harness です。今日ある AI-DLC の harness ディストリビューションの 1 つです。ソースビルドは、`core/` と `harness/copilot/` から gitignore されたローカル projection を `dist/copilot/` に生成します。リリースは `runtime/copilot/` 配下に持ちます。1 回のインストールで両方の Copilot サーフェス（Copilot CLI と VS Code agent モード。同じプロジェクトファイルを読みます）に対応します。engine ツリーは `.aidlc/` に出荷されます。`.github/` は aidlc 名の native 出力（hook 配線の `hooks/aidlc.json`、ペルソナのカスタムエージェント、skills ツリー）だけを持ち、あなたのリポジトリの `.github/` を置き換えるのではなくそこへマージされます。AIDLC メソッドはプロジェクトルートの `AGENTS.md` の `@` インポート行を通じて読まれます。`/aidlc` で起動します。[AI-DLC on GitHub Copilot](harnesses/copilot.md) を参照してください。 |
| **Orchestrator** | ワークフローがどう駆動されるかを表す総称です。次に何が起きるかを決める決定的な **Engine** と、それを実行する **Conductor**（`SKILL.md`）です。`/aidlc` で起動します。[Engine and Skill System](../reference/17-skill-system.md) を参照してください。 |
| **Packager** | `scripts/package.ts` です。**Core** と各 **Manifest** から、gitignore されたローカルの `dist/<harness>/`、`dist-release/<harness>/`、plugin の projection をすべて実体化するビルドです。`bun scripts/package.ts` ですべてをビルドします。`--check` は独立した一時ルートで 2 回ビルドし、結果をバイト比較する CI の決定性ガードです。 |
| **Parallel batch** | `unit-of-work-dependency.md` (2.7) 由来の、依存関係の揃った Unit の実行時グループで、互いに依存せず並行実行できるものです。実行時バッチは Bolt-plan のグループ分けではありません。autonomous な swarm のもとでは、engine が各 DAG バッチを収束させ、その後 Code Generation ステージのゲートを 1 回提示します。中間バッチごとに 1 ゲートではありません。`SWARM_COMPLETED` が各実行時バッチを閉じます。 |
| **Pipeline execution** | dispatch された連鎖（`mode: pipeline`）で、リンクが宣言順に走り、各リンクがすべての上流作業を見ます。戻るたびに永続的な current-attempt レシートを mint し、最後のリンクが artifact を完成させます。Reverse Engineering (2.1) が出荷される pipeline で、登録された各リポジトリごとに完全なレシート連鎖を 1 つ必要とします。 |
| **Phase** | lifecycle の 5 つの主要区分の 1 つです。Initialization (0)、Ideation (1)、Inception (2)、Construction (3)、Operation (4) です。各 phase は 3〜9 のステージを含みます（Initialization 3、Ideation 7、Inception 9、Construction 7、Operation 7）。 |
| **Phase boundary verification** | Ideation、Inception、Construction の最後のステージ（Approval and Handoff、Delivery Planning、CI Pipeline）が `<record>/verification/` に書くトレーサビリティチェックです。下流ステージが積み上げる前に、欠けたリンク、孤立した artifact、不整合を捉えます。それらのステージのどれかをスキップした plan は、その phase のチェックを得ません。[Artifacts Reference](14-artifacts-reference.md#phase-boundary-verification) を参照してください。 |
| **Plane** | ネットワークアーキテクチャから借りた、フレームワークが分離する 3 つの関心事の 1 つです。**control plane**（ステージ定義、Rules、Sensors。何が走るべきかのスキーマで、コンパイル時に解決）、**data plane**（実際のステージ実行、Bolts、audit テレメトリ）、**management plane**（`/aidlc --doctor`、audit クエリ、`CLAUDE.md`）です。ユーザー向けの見取り図は [Rules and the Learning Loop](09-rules-and-the-learning-loop.md) を、完全なモデルは `docs/reference/02-plane-architecture.md` を参照してください。 |
| **Project pin** | engine コマンド向けに、保持された native engine を選ぶ、コミット済みの `.aidlc-version` strict-semver ファイルです。`aidlc config --pin` は、完全なバイナリと一致するプロジェクト harness を検証し、machine ローカルの解決済みターゲットを記録し、`pins.json` にピンを登録してリリースを pruning から保護します。安定したコマンドランチャーは、active な整合性チェック dispatcher を起動し、プロジェクト操作の前にピンされた runtime を検証して選択します。 |
| **Projection stamp** | 生成される `tools/data/aidlc-stamp.json` の識別情報で、projection されたツリーのフレームワークバージョン、ディストリビューション、harness ディレクトリを記録します。起動と doctor が、バージョンのずれを検出するために使います。 |
| **Record dir** | 1 つの intent の artifact、ステージごとの `memory.md` 日記、`aidlc-state.md`、`audit/` シャードを保持する、intent ごとのディレクトリです: `aidlc/spaces/<space>/intents/<YYMMDD>-<label>/`（`<record>/` と表記）。各 intent が自分のものを持ちます。明示的なセレクタまたはセッションごとのバインディングが、共有の `active-intent` ポインタより先に勝ちます。**Space**、**Intent** を参照してください。 |
| **Refresh baseline** | Init が所有する `tools/data/aidlc-manifest.json` で、フレームワーク所有ファイルと型付きのルート貢献のハッシュを記録します。`aidlc config` がこれを使って refresh アクションを分類し、ローカルの編集を検出し、廃止された所有コンテンツを安全に削除し、プロジェクト所有のデータを保持します。 |
| **Release channel** | **Native channel** を参照してください。その `aidlc-runtime-X.Y.Z.tar.gz` ペイロードは、再生成されたばかりのローカル `dist-release/<harness>/` projection から組み立てられ、TLS と SHA-256 で認証され、リリースワークフローによって provenance 証明されます。 |
| **Retained version** | 完全な native バイナリ、リリース manifest、0 個以上の harness runtime を、ユーザーごとの versions ディレクトリ配下に並べて保存したものです。active、rollback、登録済みピン付きのバージョンは pruning から保護されます。 |
| **Root integration** | 宣言された方針のもとで `aidlc config` が調停する、プロジェクトルートのファイル貢献です。方針は managed block、JSON map、JSON array、whole file です。所有は明示的で、無関係なプロジェクトコンテンツは保持されるか、衝突を引き起こします。 |
| **Reviewer** | 品質ゲートのエージェントです。`aidlc-product-lead-agent`（requirements/stories/mockups）または `aidlc-architecture-reviewer-agent`（technical design）で、ステージ本体が artifact を生成した後、別の sub-agent として起動されます。これはステージが `reviewer:` と明示的に必須の Markdown `review_artifact:` を宣言したときです。1 つのレビュー（READY / NOT-READY と findings）を、要求が指定するレビューファイルに書き、artifact には決して書きません。engine はそれをその artifact を鍵とするレビュー記録として記録し、要求時の artifact/source フィンガープリント、厳格な Verdict/Reviewer/Iteration フィールド、安定した完了スナップショットが、変更された作業の認証を防ぎます。敵対的な NOT-READY では builder が再実行し、`reviewer_max_iterations`（既定 2）まで loop した後、未解決の findings を人間の approval gate で提示します。Reviewer は厳格なターン予算のもとで走ります（Claude Code では `maxTurns: 60`、opencode では `steps: 60`、その他は散文）。不完全なレビューは 1 回リトライし、その後 terminal な NOT-READY を記録します。決してブロックしません。人間が常に決めます。[Agents](06-agents.md) を参照してください。 |
| **Rule** | active-space の memory 層（`aidlc/spaces/<active-space>/memory/`）で workspace ルートに一度だけ書かれ、各 harness の native include（Claude の `@` インポート stub、Kiro CLI の resource または IDE の steering、Codex での engine のステップごとの rules 配信、opencode の `instructions` glob、Copilot の `AGENTS.md` の `@` インポート）によってコンテキストに引き込まれる、永続的な振る舞いのルールです。カバーするすべてのステージに適用されます。Rules は strict-additive な 5 層の連鎖（org → team → project → phase → stage）で解決され、該当するすべてのルールがコンテキストに現れます。広い層は決して上書きされず、追加されるだけです。Rules は **control loop** の feedforward 側で、決定的な検証のために Sensor と組になる場合があります。[Rules and the Learning Loop](09-rules-and-the-learning-loop.md) を参照してください。 |
| **Runtime graph** | intent の record ディレクトリにある、ワークフローごとの `runtime-graph.json` 成果物です。構造的な stage graph の data-plane ミラーで、approval gate ごとに audit log から実体化されます。どのステージが走ったか、どの Bolt が分岐したか、どの Sensor が発火したか、`memory.md` のエントリ数を記録します。doctor と learning loop が読む、クエリ可能な実行ビューです。 |
| **Scope** | 11 の名前付き構成（enterprise、feature、mvp、poc、bugfix、refactor、infra、security-patch、classic、workshop、express）の 1 つで、どのステージをどの depth で実行するかを決めます。エージェントが自由形式の intent から 1 つを提案し、あなたが確認します。 |
| **Sensor** | `.claude/sensors/` の manifest で定義される決定的な検証チェックです（例: `aidlc-linter.md`、`aidlc-type-check.md`）。Sensors は、マッチする Write/Edit 呼び出しごとに、または既存の成果物ごとに一度（ステージ全体を読むチェックでは出力フォルダごとに一度）、人間が答える approval gate で走り（Construction autonomy のもとで承認されたゲートは blocking な Sensor だけを走らせます）、`SENSOR_*` の audit 行を記録します。ゲートで発火する binding は advisory または blocking になり得ます。blocking な findings は訂正か、明示的で audit された override を必要とします。ステージは、どの Sensor が発火するかを `sensors:` frontmatter リストで宣言します。Sensors は **control loop** の feedback 側で、Rules が feedforward 側です。[Rules and the Learning Loop](09-rules-and-the-learning-loop.md) を参照してください。 |
| **Test strategy** | 3 つのテスト分量レベル（Minimal、Standard、Comprehensive）の 1 つで、いくつのテストを生成し、どのテスト種別を含めるかを制御します。depth とは独立で、scope が override を宣言しない限り active な depth を既定とします。[Scopes, Depth, and Test Strategy](05-scopes-and-depth.md#the-3-test-strategy-levels) を参照してください。 |
| **Transaction** | 宛先ファイルシステム上で staged され、期待されるライブ状態と照合され、アトミックな rename で commit される、プロジェクトまたは machine の変更です。失敗した commit は roll back します。回復不能な証跡は、doctor が報告する `.aidlc-recovery-*` の隔離に保持されます。 |
| **Session** | あなたの harness での 1 つの会話（Claude Code セッション、Kiro IDE チャット、Codex CLI セッションなど）で、その中で `/aidlc`（Codex では `$aidlc`）を走らせます。ワークフローは resume の仕組みで複数のセッションにまたがる場合があります。 |
| **Skill** | harness がコマンドとして提供する、YAML frontmatter 付きの Markdown ファイルです。Claude Code では `.claude/skills/` で `/` でタイプ、Codex では `.agents/skills/` で `$` でタイプ、各 harness が自分のフォルダを持ちます（[Skills and Runner Commands](17-skills.md) を参照）。AI-DLC の orchestrator は `aidlc` skill として実装されています。ユーザー向けドキュメントでは「skill」より「command」を優先します。 |
| **Space** | workspace 内の team ごとの領域で、`aidlc/spaces/<space>/` にあり、自身の `memory/`、`knowledge/`、intent 記録（`intents/`）を持ちます。明示的なセレクタまたはセッションごとのバインディングが、gitignore された `aidlc/active-space` ポインタ（既定は `default`）より先に勝ちます。単一 team のユーザーは `spaces/default/` しか見ません。**Intent**、**Knowledge** を参照してください。 |
| **Stage** | lifecycle の 33 の離散的なステップの 1 つです。各ステージは lead agent と定義された入出力を持ち、stage protocol に従います。ステージは phase で番号付けされます（例: 1.1、2.4、3.5）。 |
| **State file** | `aidlc/spaces/<space>/intents/<YYMMDD>-<label>/aidlc-state.md`（intent の record ディレクトリ配下）にある、intent ごとの永続的なワークフロー状態です。6 状態のチェックボックス（`[ ]` / `[-]` / `[?]` / `[R]` / `[x]` / `[S]`）で、ステージの進捗、scope、workspace コンテキスト、セッション resume 情報を追跡します。 |
| **Subagent execution** | dispatch された hub（`mode: subagent`）で、conductor が harness の dispatch ツールを通じて別のエージェントコンテキストを起動します。Code Generation (3.5) は 1 エージェントに絞った実行です。Practices Discovery (2.2) は hub-and-spoke です。lead が draft し、互いに見えない 3 つの support contribution、人間へのインタビュー、そして lead による統合です。collaborator が off のとき、lead は spoke 無しで走ります。 |
| **Unit of work** | WHAT です。独立に実装可能な解の一部で、ステージ 2.7（Units Generation）で分解され、`unit-of-work-dependency.md` に列挙されます。1 つ以上の依存関係でつながった Unit が、Bolt の範囲を供給します。 |
| **Walk order** | 新しくソースを生成する solo Unit ワークフローは、既定で unit-major です。次に進む前に、1 つの Unit が該当する per-unit ステージをすべて通ります。明示的な stage-major も引き続き利用できます。対象となる skeleton-on の作業は、どちらの順序でも、後続の Unit より先に最初の統合済み Unit を仕上げます。従来の、design のみの、team 所有のワークフローは、既存の経路を保ちます。実行時バッチは `unit-of-work-dependency.md` 由来で、`bolt-plan.md` は計画のコンテンツです。 |
| **Walking skeleton** | 最小の、動作する統合スライスで、skeleton-on のとき最初の DAG Unit として計画されます。対象となる checkpoint 有効の solo 作業では、その Unit が該当する design ステージと Code Generation を完了し、記録された人間認可の end-to-end 検証コマンドを通り、後続の Unit が始まる前に人間の承認を受けます。従来の最初の Construction ステージのレビューは stage gate であり、動作する skeleton の証拠ではありません。 |
| **Utility command** | `/aidlc` に渡すターミナルフラグで、`--status`、`--config`、`--doctor`、`--version`、`--stage`、`--phase`、`--scope` などです。ワークフローステージを走らせずに、特定のクエリ、設定変更、ナビゲーション操作を行います。 |
| **Worktree** | swarm 実行で 1 つの Unit に使われる git の隔離機構です。そのディレクトリと `bolt-<id8>_<slug>` ブランチがその Unit の作業を保持し、Unit claim と同様に intent レジストリ UUID で範囲付けされます。[Bolt identity](../../core/knowledge/aidlc-shared/worktree-info-schema.md#bolt-identity) を参照してください。実行は guided または自動の完了承認を使う場合があります。worktree は計画された Bolt でも swarm バッチでもありません。 |
| **Workspace** | `aidlc config` がインストールするフォルダ（それを実行したフォルダ、または `--project-dir` で指定したフォルダ）です。harness フォルダ、`aidlc/`、そしてあなたの 1 つのコードリポジトリ（フォルダがリポジトリ）か、`aidlc/` の隣のコードリポジトリを保持します。AI-DLC は git ルートを上方に探さないため、そのフォルダが workspace です。プロジェクトフォルダ、プロジェクトディレクトリ、workspace ルートとも呼ばれます。[Where `aidlc/` lives](03-spaces-and-intents.md#where-aidlc-lives) を参照してください。 |
| **Workflow** | AI-DLC lifecycle の 1 回の end-to-end 実行で、`/aidlc` の起動からステージ完了までです。特定のタスク（feature、bugfix など）に範囲付けされます。 |
| **Workflow profile** | scope に対するユーザーガイドでの呼び名です。Classic、Express、Feature、Bugfix のような、ある種の作業向けに整えられた lifecycle です。選んだ profile が stage route を決め、`aidlc-state.md` に `Scope` として保存される既定値を決めます。[Workflow Profiles](workflow-profiles.md) を参照してください。 |
