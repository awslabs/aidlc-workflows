# 비전 문서 작성 가이드

## 목적

비전 문서(Vision Document)는 AI-DLC 워크플로에 진입하기 전에 프로젝트의 **비즈니스 목표**, **달성 결과**, **범위 경계**를 정의합니다. Inception 단계의 주요 입력으로 작동하며, AI 모델과 팀이 이 프로젝트가 무엇을 달성하고자 하는지, 왜 중요한지에 대해 공통 이해를 갖도록 합니다.

잘 작성된 비전 문서는 Requirements Analysis 단계의 모호성을 줄이고, User Story 품질을 높이며, Construction 단계의 범위 확장(scope creep)을 방지합니다.

## 비전 문서를 언제 작성하나요

- 새 프로젝트 또는 주요 이니셔티브를 시작하기 전
- 새 제품, 기능 세트, 플랫폼을 제안할 때
- 기존 제품의 방향을 전환할 때
- 개발 시작 전에 여러 이해관계자가 목표에 대해 합의해야 할 때

## 문서 구조

### 1. Executive Summary

3~5문장으로 프로젝트의 본질을 담는 짧은 단락입니다. 이 섹션만 읽어도 프로젝트가 무엇인지, 누구를 위한 것인지, 왜 존재하는지를 이해할 수 있어야 합니다.

**템플릿:**

```markdown
## Executive Summary

[Project Name]은 [대상 사용자]가 [핵심 기능]을 수행할 수 있도록 하는 [시스템/제품 유형]입니다.
[비즈니스 문제 또는 기회]를 [접근 방식 또는 차별점]을 통해 해결합니다.
기대하는 결과는 [측정 가능한 비즈니스 결과] 입니다.
```

**예시:**

```markdown
## Executive Summary

OrderFlow는 중견 소매업체가 단일 인터페이스에서 재고를 추적하고, 고객 주문을 처리하며,
공급업체 관계를 관리할 수 있게 하는 웹 기반 주문 관리 플랫폼입니다. 분산된 도구로 인해
발생하는 풀필먼트 지연과 재고 불일치 문제를 해결합니다. 기대하는 결과는 주문 처리 시간
30% 감소와 수동 재고 대사(reconciliation) 제거입니다.
```

### 2. 비즈니스 컨텍스트 (Business Context)

비즈니스 환경, 해결하려는 문제, 그리고 지금 그 문제를 해결해야 하는 이유를 설명합니다.

**포함할 섹션:**

```markdown
## Business Context

### Problem Statement
[이 프로젝트가 해결하는 구체적인 비즈니스 문제 또는 페인 포인트는 무엇인가?
구체적으로 적습니다. "효율 개선"과 같은 모호한 표현은 피합니다.]

### Business Drivers
[왜 지금 이 프로젝트를 진행하는가? 시장 상황, 경쟁 압력, 규제 변화,
내부 요구 등 시기적 적절성을 만드는 요인은 무엇인가?]

### Target Users and Stakeholders
[누가 시스템을 사용하는가? 누가 그 성공에 이해관계가 있는가?
사용자 유형과 간단한 설명을 나열합니다.]

| 사용자 유형 | 설명 | 주요 필요 |
|-----------|-------------|--------------|
| [역할]    | [어떤 사람인가] | [이 시스템에서 필요한 것] |

### Business Constraints
[예산 한도, 규제 요구사항, 조직 정책, 일정 압박, 기타 협상이 불가능한
경계 사항.]

### Success Metrics
[비즈니스가 이 프로젝트의 성공을 어떻게 측정할 것인가?
구체적이고 측정 가능한 기준을 사용합니다.]

| 지표 | 현재 상태 | 목표 상태 | 측정 방법 |
|--------|--------------|--------------|-------------------|
| [지표명] | [기준선] | [목표] | [측정 방식] |
```

### 3. Full Scope Vision (전체 비전)

이 섹션은 제품/시스템의 **장기적이고 완전한 비전**을 기술합니다. 의도적으로 야심찬 모습이며, 처음에 만들 것뿐 아니라 프로젝트가 도달할 수 있는 모든 상태를 다룹니다.

**포함할 섹션:**

```markdown
## Full Scope Vision

### Product Vision Statement
[제품의 장기적 지향 상태를 한 문장 또는 짧은 단락으로 담아냅니다.
이 제품이 완전히 실현되었을 때 세상은 어떤 모습인가?]

### Feature Areas
[전체 기능 집합을 논리적인 그룹으로 정리합니다. 각 영역마다 완전 성숙 시
시스템이 무엇을 할지 기술합니다.]

#### Feature Area 1: [이름]
- **Description**: [이 영역이 다루는 것]
- **Key Capabilities**:
  - [기능 1]
  - [기능 2]
  - [기능 3]
- **User Value**: [사용자에게 어떤 가치]

#### Feature Area 2: [이름]
[동일 구조]

### Integration Points
[성숙 시 외부 시스템, API, 데이터 소스 어떤 것들과 통합되는가?]

- [시스템/서비스] - [통합 목적]

### User Journeys (Full Vision)
[2~3개의 종단간 사용자 여정을 기술합니다. 전체 제품 경험을 반영해야 하며,
MVP가 아닌 전체 범위를 반영합니다.]

#### Journey 1: [이름]
1. [단계]
2. [단계]
3. [단계]
**Outcome**: [사용자가 무엇을 달성]

### Scalability and Growth
[제품은 어떻게 성장할 것으로 예상되는가? 신규 시장, 사용자 유형, 지역,
데이터 볼륨, 기능 카테고리 등.]

### Long-Term Roadmap (선택)
[알려진 경우, MVP 이후의 상위 단계나 마일스톤을 개략적으로 기술합니다.
방향성이며 약정은 아닙니다.]

| 단계 | 초점 | 시기 (알려진 경우) |
|-------|-------|---------------------|
| MVP | [핵심 범위] | [목표 시점] |
| Phase 2 | [확장 영역] | [목표 시점] |
| Phase 3 | [추가 확장] | [목표 시점] |
```

### 4. MVP Scope (MVP 범위)

이 섹션은 **최소 기능 제품(Minimum Viable Product)** 을 정의합니다. 즉, 측정 가능한 가치를 전달하고 핵심 비즈니스 가설을 검증하는 가장 작은 기능 집합입니다. 여기에 나열된 모든 것은 제품 출시 또는 평가 전에 반드시 만들어져야 합니다.

**포함할 섹션:**

```markdown
## MVP Scope

### MVP Objective
[MVP가 증명하거나 전달해야 하는 가장 중요한 한 가지는 무엇인가?
1~2문장으로 유지합니다.]

### MVP Success Criteria
[MVP의 성공을 어떻게 알 수 있는가? 테스트 가능하고 구체적이어야 합니다.]

- [ ] [기준 1]
- [ ] [기준 2]
- [ ] [기준 3]

### Features In Scope (MVP)
[MVP에 포함되는 모든 기능을 명시합니다. 여기에 나열되지 않은 것은
MVP에 포함되지 않습니다.]

| 기능 | 설명 | 우선순위 | 포함 근거 |
|---------|-------------|----------|------------------------|
| [기능명] | [짧은 설명] | Must Have | [왜 미룰 수 없는지] |

### Features Explicitly Out of Scope (MVP)
[Full Scope Vision의 기능 중 MVP에서 의도적으로 제외하는 것을 나열합니다.
각각의 연기 이유를 적어 범위 확장을 방지합니다.]

| 기능 | 연기 이유 | 목표 단계 |
|---------|-------------------|--------------|
| [기능명] | [기다릴 수 있는 이유] | [Phase 2/3/TBD] |

### MVP User Journeys
[MVP가 지원해야 하는 사용자 여정을 기술합니다. Full Vision의 여정의
부분집합 또는 단순화된 버전입니다.]

#### Journey 1: [이름]
1. [단계]
2. [단계]
3. [단계]
**Outcome**: [사용자가 달성하는 것]
**Limitation vs Full Vision**: [전체 범위 대비 단순화되었거나 빠진 부분]

### MVP Constraints and Assumptions
[MVP가 기반으로 하는 가정은? 받아들여진 알려진 한계는?]

- **Assumption**: [내용] - **Risk if wrong**: [결과]
- **Accepted Limitation**: [의도적으로 제한된 것과 이유]

### MVP Definition of Done
[MVP가 완료되어 평가/출시 가능한 상태로 간주되기 위해 충족되어야 하는 조건]

- [ ] 모든 "Must Have" 기능 구현 및 테스트
- [ ] [본 프로젝트 고유의 추가 기준]
- [ ] [배포 또는 접근성 요건]
- [ ] [이해관계자 승인 요건]
```

## 작성 지침

### 할 것

- 구체적이고 측정 가능한 표현을 사용하세요. "주문 처리 시간 30% 단축"이 "더 빠르게"보다 낫습니다.
- Full Vision과 MVP를 명확히 구분하세요. 섞으면 범위 확장으로 이어집니다.
- "범위 밖" 목록을 포함하세요. "범위 안" 목록만큼 가치 있습니다.
- 임원이 아닌 팀을 위해 쓰세요. 마케팅 표현을 피합니다.
- 가정을 명시해 도전 가능하게 하세요.
- 실제로 테스트할 수 있는 성공 기준을 포함하세요.

### 하지 말 것

- 모호한 표현 사용: "월드 클래스", "심리스(seamless)", "직관적", "최상급".
- 기술이나 구현 세부 사항 나열. 그것은 기술 환경 문서에 들어갑니다.
- MVP 섹션 생략. 모든 프로젝트는 정의된 시작 경계가 필요합니다.
- 기능과 사용자 여정 혼합. 기능은 시스템이 무엇을 하는지, 여정은 사용자가 어떻게 경험하는지를 설명합니다.
- 독자가 비즈니스 컨텍스트를 안다고 가정. Problem Statement는 자명해 보여도 작성하세요.

## 이 문서가 AI-DLC에 어떻게 연결되는가

| 비전 문서 섹션              | AI-DLC 단계                       | 활용 방식                                          |
| ------------------------ | -------------------------------- | -------------------------------------------------- |
| Executive Summary        | Workspace Detection              | 프로젝트 분류를 위한 초기 컨텍스트                 |
| Business Context         | Requirements Analysis            | 명확화 질문과 요구사항 깊이 결정                   |
| Full Scope Vision        | User Stories, Application Design | 페르소나 생성, 컴포넌트 식별에 활용                |
| MVP Scope                | Workflow Planning                | 어느 단계가 실행될지, 범위 경계 결정               |
| Features In/Out of Scope | Code Generation                  | 이번 이터레이션에서 무엇을 만들지 정의             |
| Risks and Dependencies   | 모든 단계                          | 리스크 평가, 오류 처리에 반영                      |
| Open Questions           | Requirements Analysis            | 질문 파일의 명확화 질문이 됨                       |
