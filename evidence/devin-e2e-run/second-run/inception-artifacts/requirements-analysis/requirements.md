# Requirements — Todo REST API

**Intent**: build a REST API for a todo app with CRUD endpoints
**Scope**: express | **Depth**: Minimal
**Source**: user request (chat-mode elicitation)

## Intent Analysis

The goal is a simple, locally-runnable REST API for managing todo items. The API exposes the four standard CRUD operations (create, read, update, delete) plus a list-all endpoint over a single `todo` resource. The emphasis is on simplicity: no persistence across restarts, no authentication, no external dependencies beyond Node.js and Express. This is suitable for a demo, a learning exercise, or a prototype backend.

## Functional Requirements

### FR1 — Todo Resource

The system shall manage a single resource, `todo`, with the following fields:

| Field | Type | Description |
|-------|------|-------------|
| `id` | string (UUIDv4) | Unique identifier, server-generated on create |
| `title` | string, non-empty | Human-readable label, required on create |
| `completed` | boolean | Completion flag, defaults to `false` on create |

#### FR1.1 — Create

The system shall expose `POST /todos` accepting a JSON body `{ "title": string, "completed"?: boolean }` and returning the created todo with `201 Created` and a `Location: /todos/{id}` header.

- FR1.1.1 — `title` is required and must be a non-empty string; a missing or empty `title` returns `400 Bad Request` with a JSON error body.
- FR1.1.2 — `completed` is optional and defaults to `false` when omitted.
- FR1.1.3 — `id` is generated by the server and ignored if supplied by the client.

#### FR1.2 — Read (list)

The system shall expose `GET /todos` returning `200 OK` with a JSON array of all todos (empty array `[]` when none exist).

#### FR1.3 — Read (single)

The system shall expose `GET /todos/{id}` returning `200 OK` with the todo JSON for an existing id, or `404 Not Found` with a JSON error body when the id does not exist.

#### FR1.4 — Update

The system shall expose `PUT /todos/{id}` accepting a JSON body with any subset of `{ "title"?: string, "completed"?: boolean }` and returning `200 OK` with the updated todo.

- FR1.4.1 — If `title` is supplied it must be a non-empty string; otherwise `400 Bad Request`.
- FR1.4.2 — Unknown fields in the request body are ignored (not stored).
- FR1.4.3 — A non-existent id returns `404 Not Found`.

#### FR1.5 — Delete

The system shall expose `DELETE /todos/{id}` returning `204 No Content` on success, or `404 Not Found` when the id does not exist.

#### FR1.6 — Error responses

All error responses shall use a consistent JSON shape: `{ "error": string, "details"?: string }`.

## Non-Functional Requirements

### NFR1 — Performance

The API shall respond to any single request in under 100ms on a local development machine under no concurrent load, given the in-memory store.

### NFR2 — Reliability

The API shall start cleanly with an empty todo list on every launch (in-memory store resets on restart). No crash on an empty store.

### NFR3 — Observability

Each request shall be logged to the console with method, path, status code, and response time in milliseconds.

### NFR4 — Maintainability

The codebase shall be structured so the storage layer (in-memory array/map) is separable from the route handlers, allowing a future swap to a persistent store without rewriting the HTTP layer.

## Constraints

- **C1**: Node.js runtime with the Express framework (JavaScript).
- **C2**: In-memory storage only — no database or file persistence.
- **C3**: No authentication or authorization.
- **C4**: Runs locally on a single developer machine; no deployment or hosting configuration required.
- **C5**: JSON request/response bodies only.

## Assumptions

- **A1**: A single process instance is sufficient; concurrent multi-instance coordination is out of scope.
- **A2**: Todo titles are plain UTF-8 strings with no length limit beyond what Express/Node accept by default (no explicit validation cap is required for this scope).
- **A3**: No pagination is needed for `GET /todos` because the dataset is expected to remain small in a local demo context.

## Out of Scope

- Authentication, authorization, or multi-user tenancy.
- Persistent storage (database or file-backed).
- Pagination, filtering, sorting, or search of the todo list.
- Additional todo fields (description, due date, priority, tags).
- Deployment, hosting, CI/CD, or production observability tooling.
- Rate limiting or request throttling.
