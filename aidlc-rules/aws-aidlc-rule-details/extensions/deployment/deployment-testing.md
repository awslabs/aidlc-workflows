# Deployment — Testing Rules

## Overview
These rules define **what** tests MUST be generated and deployed to validate a deployment. They define the test types, their execution context (pipeline or model-driven), and what Construction must produce.

The pipeline executes automated tests (DEPLOY-TEST-001, DEPLOY-TEST-002) as a gate before human approval. Post-Deployment Testing executes model-driven tests (DEPLOY-TEST-003, DEPLOY-TEST-004) that require reasoning about correctness.

**Applies when**: Deployment extension is active (Answer A or B).

**Prefix**: `DEPLOY-TEST-`

---

## Test Execution Context

| Test Type | Generated By | Executed By | When | Gates |
|-----------|-------------|-------------|------|-------|
| DEPLOY-TEST-001 (Canaries) | Construction (observability + deployment rules) | Pipeline Test stage (checks status) | Every pipeline run | Production |
| DEPLOY-TEST-002 (Security boundaries) | Construction (deployment testing rules) | Pipeline Test stage (runs scripts) | Every pipeline run | Production |
| DEPLOY-TEST-003 (Functional correctness) | Model (composes at runtime) | Post-Deployment Testing (model) | After pipeline tests pass | Human approval |
| DEPLOY-TEST-004 (Operational readiness) | Model (queries at runtime) | Post-Deployment Testing (model) | After pipeline tests pass | Human approval |

## Observability Dependency

| DEPLOY Rule | Depends On | Why |
|---|---|---|

When the observability extension is not active, DEPLOY-TEST-001 canary verification degrades to health endpoint checks only. DEPLOY-TEST-004 operational readiness checks for alarms and dashboards are marked N/A. Log the degradation to audit.

### Rule DEPLOY-TEST-001: Canary/Synthetic Tests

**Rule**: Construction MUST generate synthetic canary scripts that exercise the primary user journeys against deployed endpoints. These canaries are deployed as monitoring infrastructure and run continuously after deployment.

The pipeline Test stage (DEPLOY-PIPE-012) gates production by verifying canaries are executing successfully after pre-production deployment.

**Canary coverage MUST include**:
- Every externally-facing API endpoint (at minimum: reachability + authentication flow)
- Every critical user journey identified in requirements (e.g. register, login, submit data, make payment)
- Health endpoint verification (not just HTTP 200 — MUST confirm dependency connectivity)

**Why continuous canaries rather than point-in-time tests**: Canaries run forever. They detect regressions not just at deploy time but continuously. A point-in-time test only proves the system worked at that moment. Canaries prove it keeps working.

**Verification**:
- Canary scripts exist in workspace
- Canary IaC deploys them to the target environment
- Canaries cover every externally-facing endpoint
- Canaries cover every critical user journey
- Pipeline Test stage checks canary status after pre-prod deploy
- Canary failures block pipeline progression

**Cross-references**:
- AIOBS-CLIENT-001 (canary generation — observability extension drives canary requirements)
- DEPLOY-PIPE-012 (pipeline Test stage checks canary status)

### Rule DEPLOY-TEST-002: Security Boundary Tests

**Rule**: Construction MUST generate executable security boundary test scripts that verify authentication and security controls reject invalid requests correctly. These tests are deterministic, require no model reasoning, and MUST execute in the pipeline Test stage on every deployment.

**Security boundary tests MUST cover**:
- Every protected endpoint returns 401 when called without authentication
- Every role-restricted endpoint returns 403 when called with insufficient permissions (where role-based access exists)
- Security headers are present on responses (HSTS, X-Content-Type-Options, X-Frame-Options, CSP — as applicable to architecture)
- HTTPS enforcement (HTTP requests redirected or rejected)

**Script requirements**:
- Scripts MUST be executable via a single command (e.g. `npm run test:security`, `pytest tests/security/`, `./scripts/security-tests.sh`)
- Scripts MUST accept deployment outputs as environment variables (endpoint URLs, CloudFront domains)
- Scripts MUST exit 0 on all-pass, non-zero on any failure
- Scripts MUST output which tests passed and which failed (for model assessment in Post-Deployment Testing)

**Why pipeline-automated**: Security boundaries are deterministic — the same request always gets the same rejection. They should run every deployment to catch regressions. They don't need model reasoning to interpret. They catch authentication misconfigurations before production.

**Verification**:
- Security boundary test scripts exist in workspace
- Scripts cover every protected endpoint (401 test)
- Scripts cover role-restricted endpoints (403 test, where applicable)
- Scripts verify required security headers
- Scripts are executable via a single command
- Scripts accept deployment outputs as environment variables
- Pipeline Test stage executes them after pre-prod deploy
- Any failure blocks pipeline progression

**Cross-references**:
- DEPLOY-PIPE-012 (pipeline Test stage executes these scripts)
- DEPLOY-TEST-001 (canaries cover happy path; these cover rejection paths)

### Rule DEPLOY-TEST-003: Functional Correctness Tests

**Rule**: Post-Deployment Testing MUST verify functional correctness beyond what canaries and security boundary tests cover. These tests require model reasoning to compose and evaluate — they are NOT pipeline-automated.

**Functional correctness tests MUST cover**:
- Error path validation (malformed payloads return appropriate error codes and messages)
- Input validation (oversized inputs, missing required fields, invalid formats)
- Data round-trip verification (write via API, read back, confirm correctness — where canaries do not already exercise this path)
- Edge cases specific to the business domain

**Execution**: The model composes these tests at runtime using deployment outputs and rule requirements. The model executes via `run_command` and records output as evidence.

**Why model-driven**: These tests require reasoning about what constitutes a correct response for a specific business domain. A malformed payment request might return different error messages depending on the validation logic. The model evaluates correctness; a pipeline script cannot.

**Verification**:
- Post-Deployment Testing stage executes these tests against the deployed environment
- Results recorded with command output as evidence in post-deployment-test-report.md
- Failures trigger rework if classified as Construction artifact failure

**Cross-references**:
- Post-Deployment Testing Step 4

### Rule DEPLOY-TEST-004: Operational Readiness Tests

**Rule**: Post-Deployment Testing MUST verify that operational infrastructure is correctly configured — not just present, but configured correctly. These tests require model reasoning about correctness of configuration values.

**Operational readiness tests MUST cover**:
- **Alarm coverage**: Every resource has the alarms required by observability rules, with correct thresholds and correct metric references
- **Dashboard existence**: Required dashboards exist with expected widgets and correct metric references
- **Canary configuration**: Canaries are deployed, running on schedule, reporting to correct locations
- **Health endpoint depth**: Health endpoints verify downstream dependency connectivity, not just return 200
- **Recovery readiness**: ARC readiness checks pass (if recovery extension active)

**Execution**: The model queries CloudWatch and AWS APIs to verify configuration. The model reasons about whether the configuration is correct (e.g. "alarm threshold of 1000ms for a P99 latency alarm — is this appropriate for this API?").

**Why model-driven**: Verifying that an alarm exists is automatable. Verifying that the alarm's threshold is correct for the specific workload requires reasoning about the architecture and requirements.

**Verification**:
- Post-Deployment Testing stage executes these checks
- Results recorded with command output as evidence in post-deployment-test-report.md
- Failures trigger rework if classified as Construction artifact failure

**Cross-references**:
- AIOBS-ALARM-001 (alarm coverage requirements)
- AIOBS-CLIENT-001 (canary requirements)
- AIOBS-DASH-001 (dashboard requirements)
- DEPLOY-PIPE-009 (operational readiness informs human approval decision)
