## Architecture Clarification Questions — Packager Integration & Manifest

### CQ-ARCH-001: Default CLI Permission Set for cli.json
- **Priority**: Important
- **Question**: What shell commands should be pre-allowed (and explicitly denied) in `.cursor/cli.json` for safe cursor-agent headless execution?
- **Why it matters**: `cli.json` controls what cursor-agent can execute without prompting. Too permissive (e.g., `Shell(*)`) removes safety; too restrictive causes constant permission dialogs that break agentic workflows. The permission token syntax is `Shell(command)`, `Read(path)`, `Write(path)`. The correct balance affects both day-to-day usability and security posture of the harness.
- **Options**:
  - (A) Minimal allow-list: only `Shell(bun .cursor/tools/*)` + `Shell(bun .cursor/hooks/*)` + `Read(**)` — tight, matches Codex's Starlark rules pattern; most operations prompt
  - (B) Developer-friendly allow-list: adds `Shell(git *)`, `Shell(npm *)`, `Shell(npx *)` — fewer interruptions on typical dev workflows; slightly wider blast radius
  - (C) Start with (A) and document expansion in AGENTS.md — ship safe, let users extend
- **Default if skipped**: Option (A) — `Shell(bun .cursor/tools/*)`, `Shell(bun .cursor/hooks/*)`, `Read(**)` allowed; `Shell(rm -rf *)`, `Shell(git push --force *)` explicitly denied.
- **Why this default**: Matches the principle used by Codex's Starlark rules (only AIDLC bun tool/hook prefixes pre-approved). Cursor users can extend via their own `.cursor/cli.json` additions. The AIDLC orchestrator instruments bun hooks for everything it needs; most other shell commands should prompt.

### CQ-ARCH-002: Always-Apply Rule Composition (Single vs. Split)
- **Priority**: Important
- **Question**: Should the always-apply method layer be one `aidlc-method/RULE.md` combining `org.md` + `team.md` + `project.md`, or three separate always-apply rules (`aidlc-method-org/`, `aidlc-method-team/`, `aidlc-method-project/`)?
- **Why it matters**: Cursor's best-practice limit is 500 lines per rule. If the combined content of `org.md` + `team.md` + `project.md` exceeds ~450 lines, a single rule risks poor model recall of later sections. Splitting adds three rule folders instead of one but keeps each under the limit and allows independent updates.
- **Options**:
  - (A) Single `aidlc-method/RULE.md` — simpler, fewer files, aligns with F-016 (five rule folders total)
  - (B) Three separate always-apply rules — respects size limit; allows independent org/team/project updates without touching siblings
  - (C) Conditional: measure at emit time; combine if under 450 lines, split if over — adaptive but adds complexity to the emitter
- **Default if skipped**: Option (A) — single `aidlc-method/RULE.md` with a comment noting the combined line count. If content exceeds 500 lines after first packaging, revisit with option (B).
- **Why this default**: F-016 specifies five rule folders (1 always-apply + 4 agent-decided), and the three memory files are short enough individually that combined they likely stay under 450 lines. Single file also matches the `{{HARNESS_DIR}}/rules/aidlc-method` naming convention already cited in project context documents.

### CQ-ARCH-003: Phase RULE.md Description Text
- **Priority**: Nice to Have
- **Question**: What description text should each phase RULE.md frontmatter carry for Cursor's agent-decided activation?
- **Why it matters**: The `description:` field is what Cursor's AI reads to decide whether to load the rule into context. A vague description causes under-loading (missed phase context); an overly broad one causes over-loading (irrelevant content in every context). The description should be specific enough for Cursor's AI to make good activation decisions.
- **Options**:
  - (A) Phase name only: `"AI-DLC ideation phase knowledge and stage guidance"`
  - (B) Action-oriented: `"Load when working on AI-DLC ideation: product framing, user research synthesis, problem definition"`
  - (C) Trigger-oriented: `"Load during AI-DLC stages 1.x (ideation phase) for phase-specific methodology and stage protocols"`
- **Default if skipped**: Option (B) — action-oriented descriptions that name the phase and its primary activities. These match how other harnesses' agent-requested rules are described (specific enough to be useful, short enough to scan quickly).
- **Why this default**: Cursor's documentation recommends description text that helps the AI understand when the rule is relevant. Action-oriented descriptions naming both the context (AI-DLC ideation) and the domain (product framing, user research) give the AI the clearest signal.

### CQ-ARCH-004: Commands File Content: Authored Static vs. Emitter-Generated
- **Priority**: Important
- **Question**: Should `.cursor/commands/*.md` be authored static `harnessFiles` or generated by `emit()` from the CLI utility handlers in `core/`?
- **Why it matters**: The design in F-016 lists three command files (`aidlc-status.md`, `aidlc-jump.md`, `aidlc-scope.md`). If authored as static harnessFiles, they are simpler but require manual updates when CLI utility logic changes. If generated by the emitter from `core/tools/aidlc-utility.ts` handler descriptions, they stay in sync automatically but require the emitter to parse command metadata.
- **Options**:
  - (A) Authored static harnessFiles in `harness/cursor/commands/*.md` — simpler, readable, directly editable
  - (B) Emitter-generated from core utility handler metadata — stays in sync; one authoritative source
  - (C) Mix: status and scope as static harnessFiles (stable content); jump as emitter-generated (dynamic stage list)
- **Default if skipped**: Option (A) — authored static harnessFiles. The three command files have stable content (they invoke `/aidlc --status`, `/aidlc --stage`, `/aidlc scope`) and don't need dynamic generation. This keeps `emit()` smaller.
- **Why this default**: The CLI commands are thin wrappers (`/aidlc --status` is just "run /aidlc with --status flag"). Static authored files are easier to review, version-control, and extend with Cursor-specific parameter hints (`$1`, `$2` args). The emitter is already responsible for rules, hooks.json, and cli.json — adding commands only adds complexity without clear benefit given their stable nature.
