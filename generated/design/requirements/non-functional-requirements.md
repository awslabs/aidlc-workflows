## Non-negotiable Requirements (P0)

### NFR-001: TypeScript Strict Mode with Bun Runtime

- **Category**: Non-negotiable (P0)
- **Description**: All authored TypeScript files (`manifest.ts`, `emit.ts`, `aidlc-cursor-adapter.ts`, `onboarding.fills.ts`) must use TypeScript strict mode and target the bun runtime.
- **Business Justification**: The entire framework uses TypeScript strict + bun; introducing a different config would break the build.
- **Source**: technical-environment.md — Build System
- **Source Quote**: "Runtime: bun (required for all hooks, tools, and build scripts) ... Language: TypeScript (strict, ES modules)"
- **Acceptance Criteria**:
  - All new `.ts` files compile without errors under the existing `tsconfig.json` (strict: true)
  - Files use ES module syntax (`import`/`export`)
  - No new `tsconfig.json` is added; existing config is reused
- **Dependencies**: None
- **Assumptions**: Existing `tsconfig.json` at repo root covers `harness/cursor/`

### NFR-002: Biome Linter/Formatter Compliance

- **Category**: Non-negotiable (P0)
- **Description**: All new TypeScript and JSON files must pass Biome linting and formatting checks as configured in `biome.json`.
- **Business Justification**: CI enforces Biome; failing lint breaks the build.
- **Source**: technical-environment.md — Build System
- **Source Quote**: "Linter/Formatter: Biome (biome.json config)"
- **Acceptance Criteria**:
  - `biome check` exits with code 0 on all new files in `harness/cursor/`
  - No `biome:ignore` suppressions added without explicit justification
- **Dependencies**: None
- **Assumptions**: Existing `biome.json` at repo root applies to `harness/cursor/`

### NFR-003: Never Hand-Edit dist/

- **Category**: Non-negotiable (P0)
- **Description**: `dist/cursor/` must be entirely generated by `bun scripts/package.ts cursor`; no file in `dist/` may be authored or modified manually.
- **Business Justification**: The CI byte-parity guard detects any hand-edit as a drift failure, breaking the release pipeline.
- **Source**: vision.md — Constraints
- **Source Quote**: "Never hand-edit `dist/` — only `harness/cursor/` and (minimally) `core/` are authored"
- **Acceptance Criteria**:
  - Zero files in `dist/cursor/` contain content that cannot be reproduced by running the packager
  - `bun scripts/package.ts --check` passes on every commit to the feature branch
- **Dependencies**: NFR-007 (determinism)
- **Assumptions**: CI runs `bun scripts/package.ts --check` as a mandatory gate

### NFR-004: Only {{HARNESS_DIR}} Token Substitution in Prose

- **Category**: Non-negotiable (P0)
- **Description**: The only text transformation applied to `.md` files during packaging is substitution of the `{{HARNESS_DIR}}` token with the harness directory value (`.cursor`). No other dynamic transforms are permitted in Markdown prose.
- **Business Justification**: Multiple transforms would complicate the packaging model and risk introducing subtle prose errors in methodology documents.
- **Source**: vision.md — Constraints
- **Source Quote**: "One transform class — only `{{HARNESS_DIR}}` token substitution in `.md` prose"
- **Acceptance Criteria**:
  - `harness/cursor/` `.md` files use `{{HARNESS_DIR}}` where the harness directory name appears in prose
  - No other template tokens are introduced in prose files
- **Dependencies**: None
- **Assumptions**: JSON and TypeScript emitter output is not prose and may perform programmatic generation

### NFR-007: Deterministic Emitter Output

- **Category**: Non-negotiable (P0)
- **Description**: The emitter (`emit.ts`) must produce identical output for identical inputs on every run; no timestamps, random values, or environment-dependent data may appear in generated files.
- **Business Justification**: The byte-parity drift guard requires deterministic output; non-deterministic emitters cause spurious CI failures.
- **Source**: vision.md — Constraints; technical-environment.md — Build System
- **Source Quote**: "Byte-parity — regenerating must reproduce the committed dist exactly"
- **Acceptance Criteria**:
  - Running `bun scripts/package.ts cursor` twice in succession produces byte-identical output
  - No file timestamps, build timestamps, or UUIDs appear in generated file content
- **Dependencies**: None
- **Assumptions**: File system metadata (timestamps) is not part of the byte-parity check — only file content

---

### NFR-008: Conventional Commits with feat(cursor): Prefix

- **Category**: Non-negotiable (P0)
- **Description**: All commits on the `feature/cursor` branch must follow the Conventional Commits specification with the `feat(cursor):` scope prefix for feature work.
- **Business Justification**: The changelog and release automation depend on conventional commits; incorrect prefixes break release tooling.
- **Source**: vision.md — Constraints; customer-context.md
- **Source Quote**: "Conventional commits — `feat(cursor):` prefix for this work"
- **Acceptance Criteria**:
  - All new commits use format `<type>(cursor): <subject>` or `<type>: <subject>` for non-cursor-scoped changes
  - Subject line is in imperative mood, under 50 characters
- **Dependencies**: None
- **Assumptions**: Conventional Commits specification v1.0.0

## Recommended Requirements (P1)

### NFR-100: No Legacy .cursorrules Format

- **Category**: Recommended (P1)
- **Description**: The distribution must not include or generate any `.cursorrules` file at the project root. All Cursor rules must use the new `.cursor/rules/<name>/<name>.mdc` folder format with YAML frontmatter.
- **Business Justification**: The single-file `.cursorrules` is deprecated; the `.mdc`-in-subfolder format is the officially supported format per Cursor documentation (July 2026) and is what the rules engine recognizes.
- **Source**: vision.md — Constraints; cursor-platform-research.md — Rules section; official Cursor docs July 2026
- **Source Quote**: "No .cursorrules legacy format — use only the new `.cursor/rules/*/` folder format" (re-interpreted: the folder format uses `.mdc` extension per official docs)
- **Flexibility Notes**: If Cursor changes the `.mdc` convention in a future version, this constraint would need revisiting.
- **Acceptance Criteria**:
  - `dist/cursor/` contains no `.cursorrules` file
  - All rules are in `<name>/<name>.mdc` format with YAML frontmatter
  - `dist/cursor/.cursor/rules/` contains no `RULE.md` files
- **Dependencies**: FR-003
- **Assumptions**: Cursor 3.11+ is the minimum version target

---

### NFR-101: Security Gate Hooks Use failClosed

- **Category**: Recommended (P1)
- **Description**: Hook entries that gate security-critical shell operations (specifically `beforeShellExecution`) must set `failClosed: true` in `hooks.json`.
- **Business Justification**: Cursor's default hook behavior is fail-open; a hook process crash would silently allow a blocked operation to proceed without explicit opt-in to failClosed.
- **Source**: cursor-platform-research.md — Platform Constraints; customer-context.md
- **Source Quote**: "Hook fail-open default — Hooks fail open unless `failClosed: true` is set; security gates need explicit opt-in"
- **Flexibility Notes**: Non-security hooks (audit, reporting) may remain fail-open if a crash is non-critical.
- **Acceptance Criteria**:
  - `hooks.json` `beforeShellExecution` entry includes `"failClosed": true`
  - Other hook entries may omit `failClosed` if they are non-blocking
- **Dependencies**: FR-006
- **Assumptions**: `failClosed` is a supported field in Cursor hooks.json version 1 schema

## Inferred Requirements (P2)

### NFR-200: Rules Files Stay Under 500 Lines Each

- **Category**: Inferred (P2)
- **Description**: Each generated `.cursor/rules/<name>/<name>.mdc` file must not exceed 500 lines.
- **Inference Rationale**: cursor-platform-research.md documents "Rules size limit — Best practice is under 500 lines per rule; split large rules" as a platform constraint. If the emitter generates oversized rules, Cursor may truncate or behave unpredictably.
- **Source Context**: cursor-platform-research.md — Platform Constraints (#3)
- **Acceptance Criteria**:
  - Emitter validates that no generated `.mdc` rule file exceeds 500 lines
  - If a source document would produce an oversized rule, the emitter splits it into multiple named rules
- **Dependencies**: FR-003
- **Validation Needed**: Yes — confirm Cursor's actual limit if the spec changes post-3.11
